# 2026-04-07 `info/` 文档库 wiki 化可行性评估

## 结论
- 可以搭，而且本机没有 GUI 不是硬阻塞。
- 但按 `llm-wiki` 的口径，当前 `info/` 还不能算完整 wiki，更接近“有总索引的文档仓库”。
- 最小可行路线不是先上 GUI，而是先补三件事：分清 `raw sources / wiki / schema`，新增全局 `index.md` 与 `log.md`，再把页面互链规则固定下来。

## `llm-wiki` 给出的约束
Karpathy 这篇 `LLM Wiki` 把模式定义得比较清楚：
- 三层结构：`Raw sources`、`The wiki`、`The schema`。证据：原文第 `25-34` 行。
- 维护流程不是一次性建库，而是持续做 `ingest / query / lint`。证据：原文第 `35-41` 行。
- wiki 至少需要两个特殊文件：
  - `index.md`：内容导向的总目录。证据：原文第 `43-48` 行。
  - `log.md`：按时间追加的演化日志。证据：原文第 `49-50` 行。
- GUI/图谱不是前置条件。原文明确说：中等规模时只靠 `index.md` 就能工作，规模更大再考虑 CLI 搜索工具。证据：原文第 `47-53` 行。

参考来源：<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>

## 当前项目离 wiki 还差什么

### 1. 已有基础是够的
- `info/README.md`、`info/experiment_ops/README.md`、`info/vllm_analysis/README.md` 已经提供了分目录入口。
- `info/进展.md` 已经承担“总览/主线结论页”的作用。
- 多数分析文档已经有比较稳定的“结论/证据/推断/建议”结构，例如 `info/vllm_analysis/01_vllm_serve启动到server_ready.md` 到 `info/vllm_analysis/08_CPU_attention计算切分、数据放置与Chiplet优化借鉴.md`。
- 当前 `info/` 规模也不大，适合先走“纯 markdown + 总索引”的轻量路线。
  - `2026-04-07 20:48:30 +0800` 本机统计：`info/` 下共 `58` 个文件，其中 `38` 个 `md`、`19` 个 `pdf`、`5` 个 `README*`。

### 2. 还缺 `llm-wiki` 最关键的三类约束
- 层次还没分开：
  - 评估当时的 `info/` 同时放了原始 PDF、研究笔记、目录索引。
  - 例子：当时论文/PPR PDF 与 `info/vllm_analysis/*.md`、`info/experiment_ops/*.md` 混在同一棵树下；当前论文与 uProf 原始资料已收口到 `wiki/原始资料/`。
  - 这不符合 `raw sources` 与 `wiki` 分层。
- 还没有全局 `index.md` / `log.md`：
  - 当前只有各目录 `README.md`，没有一个覆盖整棵 wiki 的内容索引。
  - 当前也没有按时间追加的 ingest / query / lint 日志。
- 页面之间还没有真正形成链接图：
  - `2026-04-07 20:48:30 +0800` 用 `rg --pcre2` 粗扫 `info/*.md` 的内部 markdown 链接，几乎只在 `info/vllm_analysis/11_Qwen3-30B-A3B注意力KV工作集与32MiBL3容量估算.md` 里看到跨页链接。
  - 大部分文档目前更像“被 README 收录”，不是“正文中互相引用”。
  - 用文件名做粗筛时，`info/AMDL3.md` 目前没有被其他 `info/*.md` 提到，属于孤儿页候选。

### 3. schema 只完成了一半
- 现在已有全局行为约束：仓库根的 `AGENTS.md` 明确了回答风格、证据边界、`tasks.json/process.txt/info/README.md/进展.md` 的入口关系。
- 但它还没有定义 wiki 维护规则，例如：
  - 页面有哪些类型
  - 每类页面必须带哪些元数据
  - 新资料 ingest 时必须更新哪些页面
  - lint 时怎么检查孤儿页、过时结论、缺失互链
- 也就是说，当前有“研究协作 schema”，还没有“wiki 维护 schema”。

## 无 GUI 条件下是否可用
- 可以用，而且现在就能跑最小闭环。
- `llm-wiki` 原文把 GUI 相关内容放在 tips 里，不是架构前提；`Obsidian graph view` 只是可选增强。证据：原文第 `55-63` 行。
- 本机现状：
  - 已有：`rg`、`less`、`tree`
  - 没有：`fzf`、`bat`、`glow`、`qmd`、`mdcat`
- 因此当前最稳的无 GUI 方案是：
  - 用 `index.md` 做总入口
  - 用 `rg` 找关键词、页面名、证据路径
  - 用 `less`/编辑器阅读 markdown
- 若后续页数明显增多，再考虑补 `qmd` 这类 CLI 搜索，不需要一开始就上。

## 对当前项目最合适的 wiki 形态
不建议现在大搬家。更适合做“在现有 `info/` 上增量收敛规则”。

### 建议的逻辑分层
- `raw sources`
  - 论文/PPR/PDF：现有 `wiki/原始资料/papers/`、`wiki/原始资料/AMDuProfCLI/`、`wiki/原始资料/AMDuProfPcm/`、`info/AMD_PPR_57883/`
  - 实验原始结果：现有 `test_results/`
  - 源码证据：现有仓库源码路径
- `wiki`
  - 继续用当前 `info/*.md`、`info/vllm_analysis/*.md`、`info/experiment_ops/*.md`、`info/ai-research/**/*.md`
- `schema`
  - 继续以仓库根 `AGENTS.md` 为主，再补一个专门的 wiki 规则文件，例如 `info/WIKI_SCHEMA.md`

### 建议先固定的页面类型
- `overview`：总览页，例如 `info/进展.md`
- `concept`：概念/机制解释，例如 `info/vllm_analysis/*.md`
- `runbook`：实验步骤/执行口径，例如 `info/experiment_ops/*.md`
- `source-note`：单篇论文/单份资料解读
- `synthesis`：跨资料汇总、方向建议、阶段性结论

### 每页建议至少固定 4 个区块
- `结论`
- `证据`
- `相关页面`
- `更新记录`

其中 `相关页面` 至少写出：
- 上游入口页
- 当前页直接依赖的 1~3 个相关页
- 当前页更新后需要一并检查的下游页

## 最小落地步骤
1. 新增 `info/index.md`
   - 覆盖整棵 `info/`，不要再只按目录列 README。
   - 每个页面至少写：页面名、类型、一句话摘要、最后更新时间、关键证据来源。
2. 新增 `info/log.md`
   - 统一前缀格式：`## [YYYY-MM-DD HH:MM:SS +0800] ingest|query|lint | 标题`
   - 后续每次新建文档、重要问答沉淀、lint 巡检都追加一条。
3. 补 wiki schema
   - 不改现有科研约定，只增加 wiki 维护规则。
4. 逐步补正文互链
   - 先从 `info/进展.md`、`info/vllm_analysis/README.md`、`info/experiment_ops/README.md` 指向主干页。
   - 再要求每个新页面正文里显式写“相关页面”。
5. 最后再做 lint
   - 查孤儿页
   - 查没有证据路径的结论
   - 查只在 README 出现、正文从未被引用的页面

## 我建议的判断口径
- 如果按 `llm-wiki` 的严格定义回答：现在还没建成 wiki。
- 如果按“是否具备搭 wiki 的基础”回答：已经具备，而且成本不高。
- 最应该优先补的不是 GUI，而是：
  - 全局 `index.md`
  - 全局 `log.md`
  - wiki 维护 schema
  - 正文互链规则
