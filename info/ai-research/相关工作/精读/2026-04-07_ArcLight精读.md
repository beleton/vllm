# 2026-04-07 ArcLight 精读

## 论文信息

- 标题：`ArcLight: A Lightweight LLM Inference Architecture for Many-Core CPUs`
- 作者：`Yuzhuang Xu, Xu Han, Yuxuan Li, Wanxiang Che`
- 来源：`arXiv:2603.07770v1`
- 日期：`2026-03-08`
- 本地文件：`info/papers/ArcLight.pdf`

## 一句话结论

`ArcLight` 的核心贡献，不是单独发明一个 `NUMA bind` 开关，而是把 many-core CPU 上的 `cross-NUMA memory access wall` 当成首要瓶颈，再把 `内存放置`、`线程组织`、`tensor parallel` 和 `同步方式` 作为一套联合设计来处理。论文证据支持它在作者自有的 `4-NUMA ARM` 平台上，相对 `llama.cpp` 最多提升 `46%` 吞吐；但这组证据还不能直接推出它在当前 `AMD EPYC chiplet + vLLM + CCX/L3` 课题上同样成立。证据：`info/papers/ArcLight.pdf` 第 1-6 页。

## 1. 论文问题与核心观察

### 1.1 论文要解决什么问题

- 作者把 many-core CPU 上的主要问题定义为：`CPU cores` 与 `memory` 被切成多个 `NUMA node` 后，远端访存代价很高，而现有 CPU LLM 框架没有把这个代价作为首要对象显式处理。证据：`info/papers/ArcLight.pdf` 第 1 页摘要和第 1 节。
- 因此，论文目标不是泛泛地“提高 CPU 推理性能”，而是解决“跨 `NUMA node` 扩展时，算力能加上去，但 locality 被破坏”的问题。证据：`info/papers/ArcLight.pdf` 第 1-2 页、第 4 页第 3 节。

### 1.2 他们先观察到了什么

- 论文先做了一个硬件级观察：在他们的 `4-NUMA` 测试机上，本地内存带宽约 `101-103 GB/s`，远端只有 `22-26 GB/s`，本地约为远端 `4x`。证据：`info/papers/ArcLight.pdf` 第 4 页表 1。
- 作者据此把 many-core CPU 的主瓶颈概括成 `cross-node memory access wall`。也就是说，只要工作负载一旦跨 node 扩展，是否本地访问就会直接影响吞吐。证据：`info/papers/ArcLight.pdf` 第 4 页第 3.1 节。

### 1.3 论文对现有框架的核心判断

- 作者认为，问题不在于“框架完全不支持 NUMA”，而在于很多框架只做了线程分布，却没有把 tensor 放置和后续算子执行一起设计。证据：`info/papers/ArcLight.pdf` 第 4 页第 3.1 节。
- 论文点名的例子是 `llama.cpp --numa distribute`：线程会被均匀分到不同 `NUMA node`，但 tensor 不显式绑到特定节点。证据：`info/papers/ArcLight.pdf` 第 4 页第 3.1 节。

## 2. 关键挑战

### 2.1 不是“线程绑没绑”，而是“计算位置和数据位置是否持续对齐”

- 论文强调的问题不是“初始权重能不能 first-touch 到本地”，而是后续连续算子里，计算线程和张量实际位置会不会持续错位。证据：`info/papers/ArcLight.pdf` 第 4 页第 3.1 节、图 7。
- 它的挑战本质是：即使权重分片看起来已经顺着线程落到了各个 node，上游 activation 或下游输出只要没有一起被显式组织，后续 GEMM 仍会反复产生 remote access。

### 2.2 Figure 7 里的具体失配链条

- 论文给出的链条是：
  1. 线程已分散到多个 `NUMA node`
  2. 权重分区也会跟着落到多个 node，这一步作者认为“合理”
  3. 但如果初始 activation 只在 `node 0`
  4. 那么 `node 1-3` 上的权重分区做 `GEMM1` 时，仍然要远程读 activation
  5. `GEMM1` 输出后，activation 又变成跨所有 node 分布
  6. 到 `GEMM2` 时，每个权重分区只有约 `1/4` activation 访问是本地，剩余 `3/4` 仍是远端
  7. 这种模式会持续到后续 GEMM，形成稳定瓶颈
- 论文真正批评的是“只 distribute 线程，不控制 activation / tensor 的后续落点”。证据：`info/papers/ArcLight.pdf` 第 4 页第 3.1 节、图 7。

### 2.3 为什么单个 `NUMA bind` 不够

- 按论文口径，`NUMA bind` 只回答“线程在哪”，并不能自动回答：
  - weight shard 在哪
  - activation 在层间如何流动
  - 多个子图何时并行、何时汇合
  - 同步是否会把部分线程重新拖回全局等待
- 所以论文把问题抬高成一套系统设计，而不是单个运行参数。证据：`info/papers/ArcLight.pdf` 第 2-6 页。

## 3. 系统设计

### 3.1 内存设计：从 UMA 大缓冲改成 NUMA-local 分缓冲

- `ArcLight` 的 memory manager 会在启动时预分配内存池，并在启用 NUMA 时为每个 `NUMA node` 分别分配本地 buffer，而不是像 `llama.cpp` 那样用一个透明的大缓冲。证据：`info/papers/ArcLight.pdf` 第 2-3 页第 2.3 节、图 3。
- 论文明确说这样做的直接收益是“显式 tensor-to-NUMA-node binding 更简单”。也就是说，它不再依赖 OS first-touch 漂移来“碰运气”获得 locality。证据：`info/papers/ArcLight.pdf` 第 3 页第 2.3 节。
- activation buffer 还做了双缓冲，按 layer parity 交替使用，以降低运行时内存占用。证据：`info/papers/ArcLight.pdf` 第 3 页第 2.3 节、图 4。

### 3.2 线程设计：线程池支持多视图 thread group

- `ArcLight` 不是只保留一个“所有线程做同一件事”的线程池，而是在池内引入逻辑 `thread group`，允许运行时拆分和合并。证据：`info/papers/ArcLight.pdf` 第 3 页第 2.4 节、图 5。
- 为了让单图执行和多子图执行共存，论文区分了 `local barrier` 和 `global barrier`。只在需要跨组同步时启用全局 barrier，否则线程组内部各自同步。证据：`info/papers/ArcLight.pdf` 第 3 页第 2.4 节、图 6。
- 这一步不是单独为了线程管理美观，而是为了让后面的并行子图能真正异步推进。证据：`info/papers/ArcLight.pdf` 第 5-6 页第 3.3-3.4 节、图 9。

### 3.3 计算设计：cross-NUMA tensor parallel

- 论文把 `TP` 作为缓解跨 `NUMA` 访存墙的核心机制，而不是只把它当训练里的多设备技术。证据：`info/papers/ArcLight.pdf` 第 4-5 页第 3 节。
- 权重切分规则写得很明确：`Wq/Wk/Wv/Wgate/Wup` 做 row partition，`Wo/Wdown` 做 column partition；其中 `Wq/Wk/Wv` 是按 attention head 切。证据：`info/papers/ArcLight.pdf` 第 5 页第 3.2 节、图 8。
- 论文的核心想法是：既然多 node 扩展已经不可避免，那就把计算图主动切成多个子图，让各 node 尽量在自己的 shard 和本地 buffer 上工作，而不是继续让单图在多 node 上松散漂移。

### 3.4 图执行设计：Scatter / Gather + 异步子图

- 框架层面新增 `Scatter` / `Gather` 两个操作，把单计算图切成多个并行子图，再在结束时汇合回单图。证据：`info/papers/ArcLight.pdf` 第 5 页第 3.3 节、图 8。
- 同步方式上，论文明确比较了“每个 op 都全局同步”和“只有开始/结束做全局同步，中间各子图局部同步”两种方式。结论是后者更好，因为它显著减少 thread idle time。证据：`info/papers/ArcLight.pdf` 第 5-6 页第 3.4 节、图 9。

## 4. 实验设置

### 4.1 平台

- 测试机：`192-core`, `4 NUMA nodes`
- 每个 node：`48 x HUAWEI Kunpeng-920 cores (ARMv8.2)`，`6 x DDR4 memory channels`
- OS：`Ubuntu 22.04`
- 模型：`Qwen3-4B`
- 量化：`Q4_0`
- 指令：`NEON`

证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节。

### 4.2 工作负载

- 主文 decoding 测试：`prompt length = 15`，`generation length = 256`
- 附录补充：`prompt length = 300`，并额外给了 prefill throughput

证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节、第 8 页附录 A.2。

### 4.3 对比口径

- 主 baseline 是 `llama.cpp`。
- 实验分别看：
  - 单 `NUMA node`
  - 多 `NUMA node` 的 `2-node / 4-node`
- 作者关心的是：`ArcLight` 在不跨 node、以及跨 node 后，是否都比 `llama.cpp` 更好；尤其是多 node 时，多出来的收益是否来自其 `NUMA-local + TP + async subgraph` 设计。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节、Figure 10-11。

## 5. 实验结果与证据边界

### 5.1 单 NUMA 的结果

- 单 `NUMA node` 场景下，两套框架吞吐都会随着线程数上升而提升，说明此时吞吐主要跟着单节点内带宽和核心数扩展。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节、Figure 10。
- `ArcLight` 只比 `llama.cpp` 略快。作者解释是：`llama.cpp` 的 buffer 没有 NUMA-aware placement，而 `ArcLight` 明确做了 node-local allocation。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节。

### 5.2 多 NUMA 的结果

- 多 `NUMA node` 场景下，`ArcLight + TP` 明显优于只做线程 distribute、但把内存放置继续交给 OS 的 `llama.cpp`。作者把收益归因为 `cross-NUMA TP` 打破了 `single-node memory access wall`。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节、Figure 11。
- 在这个多 NUMA 结果上，异步子图执行还能再带来约 `5 token/s` 的额外收益。证据：`info/papers/ArcLight.pdf` 第 6 页第 3.4 节和第 4 节。
- “最高 `46%` 吞吐提升”来自摘要和引言中的总括性表述。当前 PDF 正文在抽取得到的文本里没有给出完整数值表，更多是图形展示，所以这里应写成“论文声称/图中总结”，不能写成“本文档自行复算得到”。证据：`info/papers/ArcLight.pdf` 第 1-2 页。

### 5.3 Prefill / Decode 的边界

- 对 `prefill`，附录明确说 `ArcLight` 仍优于 `llama.cpp`，但优势小于 decode；作者给出的解释是 `TP` 主要解决 memory access wall，而 `prefill` 更偏 compute-bound。证据：`info/papers/ArcLight.pdf` 第 8 页附录 A.2。
- 因而论文本身已经暗示：它这套设计的最大收益，不应被默认推广到所有阶段和所有工作负载。

### 5.4 论文直接证明了什么

- 在作者的 `4-NUMA ARM Kunpeng-920` 平台上，跨 NUMA 远端访存显著慢于本地访存。证据：`info/papers/ArcLight.pdf` 第 4 页表 1。
- 显式 `NUMA-local` buffer + cross-NUMA TP + 异步子图执行，能让 `Qwen3-4B Q4_0` 的 CPU 推理吞吐超过 `llama.cpp`。证据：`info/papers/ArcLight.pdf` 第 6 页图 10-11。
- 这套机制对 decode 的帮助比对 prefill 更显著。证据：`info/papers/ArcLight.pdf` 第 8 页附录 A.2。

### 5.5 论文没有直接证明什么

- 没有 `x86` 或 `AMD EPYC` 实测。作者在 limitations 里直接写了当前只在 `ARM` 上评估，`x86` 留待未来工作。证据：`info/papers/ArcLight.pdf` 第 7 页 `Limitations`。
- 没有和 `vLLM`、`DeepSpeed`、`SGLang` 做直接对比；主 baseline 是 `llama.cpp`。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节、第 5 节。
- 没有直接研究 `CCX/L3 slice` 级别的 chiplet 局部性；论文 locality 粒度主要是 `NUMA node + local/remote DRAM`。证据：`info/papers/ArcLight.pdf` 第 1、4-6 页。
- `Scatter/Gather` 仍是初步实现，论文自己承认还要继续优化内存开销和并行效率。证据：`info/papers/ArcLight.pdf` 第 7 页 `Limitations`。

## 6. 与当前 vLLM / 课题的关系

### 6.1 和当前 `vLLM CPU TP` 的关系

- 对当前 `vLLM CPU` 而言，官方文档已经明确建议：
  - `tensor-parallel-size` 对齐 `NUMA nodes`
  - 每个 TP rank 的 CPU 线程绑在同一个 `NUMA node`
  - 每个 rank 的内存预算按 `weight shard size + VLLM_CPU_KVCACHE_SPACE` 看单 node 容量
  证据：`docs/getting_started/installation/cpu.md:192-241`。
- 这说明 `vLLM` 的推荐口径，已经比论文批评的“只 distribute 线程、不管 tensor 放置”的 `llama.cpp` 更进一步。
- 但论文提醒的边界仍然成立：`NUMA 绑定` 不是一句“把 rank 和权重 shard 放到 node 上”就结束了，后续 activation / gather / reduce / KV cache 等运行时数据是否仍跨节点流动，决定了 locality 是否真的被守住。

### 6.2 对当前课题可迁移的点

1. `locality` 需要被框架显式建模，不能只靠 OS first-touch。
   - 这和我们当前已经在做的“显式线程局部域建模”方向一致。当前本地实现已经把线程按 `socket_id + l3_cache_id + numa_node` 组 `subgroup`，并显式维护 `kv_head_to_subgroup`。证据：`info/vllm_analysis/10_CPU_attention_acc_locality新kernel实现说明.md` 第 3-6 节。
2. “先把线程组织改对，再谈并行子图/并行任务”是合理顺序。
   - `ArcLight` 先提供 `thread group + local/global barrier`，再进入 TP 子图异步执行；这和我们先补 `cpu_binding/locality group`、再上 `acc-local-l3` 是同一类工程分层。证据：`info/papers/ArcLight.pdf` 第 3 页第 2.4 节；`info/vllm_analysis/10_CPU_attention_acc_locality新kernel实现说明.md` 第 4 节。
3. `prefill/decode` 不能默认共享同一收益预期。
   - `ArcLight` 里 `TP` 对 decode 更有利，prefill 相对更 compute-bound；我们本地也已看到 `decode_B16_I1_O1024` 的 `L3 Miss %=96.51` 高于 `prefill_B16_I1024_O1` 的 `49.43`。证据：`info/papers/ArcLight.pdf` 第 8 页附录 A.2；`info/进展.md` 第 26-34 行附近。

### 6.3 对当前课题不可直接迁移的点

1. `ArcLight` 的主战场是 `NUMA node` 级远端 DRAM 访问，而我们当前主线是 `AMD EPYC chiplet` 上的 `CCX/L3` 局部性。
   - 本地证据显示，当前候选优化靶点集中在“共享 `K/V` 工作集尽量收进同一 `CCX/L3` 子池”，不是单纯减少远端 DRAM。证据：`info/进展.md` 第 21-25 行；`info/vllm_analysis/10_CPU_attention_acc_locality新kernel实现说明.md` 第 3.2-3.3 节。
2. `ArcLight` 改的是整条 inference engine：内存管理、线程管理、graph builder、scheduler、TP。
   - 我们当前没有重写整个 vLLM CPU runtime，而是在 legacy attention 外围新增 `acc-local-l3` 新 kernel 路径。证据：`info/vllm_analysis/10_CPU_attention_acc_locality新kernel实现说明.md` 第 1-3 节。
3. `ArcLight` 的 TP 是整层权重切分与并行子图调度；我们当前实验还主要停留在 attention kernel/task locality。
   - 因此不能把 `ArcLight` 的整模型吞吐收益，直接映射成我们当前 attention-only 或 `P/D` 分相实验的预期收益。证据：`info/papers/ArcLight.pdf` 第 5-6 页第 3-4 节；`test_results/P2_AttnOnly/Qwen3-30B-A3B/NPS1_TP2/summary.md`。
4. 论文平台和模型规模都不同。
   - 论文是 `ARM Kunpeng-920 + Qwen3-4B Q4_0`；我们当前重点证据来自 `2 x AMD EPYC 9745`、`Qwen3-30B-A3B` 的 `PD_Test` 与 `P2_AttnOnly`。证据：`info/papers/ArcLight.pdf` 第 6 页第 4 节；`info/进展.md` 第 4-5 行、第 36-45 行。

## 7. 对本课题的实际启发

- `ArcLight` 最值得吸收的不是它的代码形态，而是它给出的判断顺序：
  1. 先证明 locality 失配确实是瓶颈；
  2. 再把 locality 从“隐式 OS 行为”提升到“框架显式控制对象”；
  3. 再设计能和 locality 对齐的线程组/并行切分方式；
  4. 最后才看吞吐是否提升。
- 这和我们当前主线是兼容的：本地已经先通过 `PD_Test` 和 `P2_AttnOnly` 把 `Prefill/Decode`、`same-node another CCX`、`local memory / I/O` 的变化测出来，再去尝试 `acc-local-l3`。
- 但当前不能从 `ArcLight` 推出“我们的 `acc-local-l3` 一定有效”。现阶段更稳妥的口径是：它强化了“显式 locality-aware 调度值得做”的信心，却没有替代我们在 `AMD EPYC chiplet` 上继续补 `NPS/TP/batch/length` 实验的必要性。
