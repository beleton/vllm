# 背景
相比单片架构的CPU，Chiplet架构的L3 Cache被物理分片，核心访问本CCX/CCD的L3最快，访问同CPU内其他CCD的L3更慢，呈现类似NUMA的本地和远端的现象。
《ARCAS: Adaptive Runtime System for Chiplet-Aware Scheduling》指出：对多线程程序，当工作集大小超过单个 L3 Cache 时，将线程分散到多个 Chiplet 上可以利用更大的“聚合 L3 容量”，减少访问远端CCX L3 和内存，但论文主要关注图处理、数据库等应用。

# KT相关
## 实验 A
目的：验证ARCAS的结论在CPU LLM推理场景是否同样成立，“线程集中/分散”的绑核策略能否成为kt-kernel的优化点：

### 1.简单的矩阵乘法
计算逻辑：计算 AxB=C，固定B的一个block；7个线程并行计算A的不同block与该B block的乘积。
对比策略：
- 集中：7 个线程绑定在 0-6 核（同一 CCX 内共享 16MB L3）
- 分散：7 个线程绑定在 0,7,14...（分布到不同 CCX，利用多个独立 L3）
结果（A/B/C=4096x4096，随block参数增大使“单线程工作集”增大）：
- 单线程工作集 1.5MB：集中 716.840ms vs 分散 687.276ms（差异不大）
- 单线程工作集 2.75MB：集中 869.978ms vs 分散 692.293ms（分散更快）
- 单线程工作集 5MB：集中 2996.239ms vs 分散 648.342ms（集中显著变慢；同时集中 L3 Miss Rate 升至 43.7%）
结论：矩阵乘法的工作集超过单个L3容量且存在明显缓存竞争/互相驱逐时，把线程分散到多个CCX能显著提升性能

### 2：kt-kernel/bench/bench_moe
配置：qlen=4, hidden_state=7168, Q_K=256，fp16；单个 MoE gate/up/down 分块约 3.5MB。14 线程（每个 CPU 7 线程）。

对比策略：
1. 集中：7 个线程在同一 CCX，共享 16MB L3
2. 分散：7 个线程分散到 4 个 CCX（2+2+2+1）
结果：
- 每迭代时间：集中 178.35ms vs 分散 174.33ms（几乎相当）
- 两者 L3 Miss Rate 都很高（~78.7%），且 miss/latency/bandwidth 等指标差异很小
结论：在该 MoE 配置下，“集中/分散”策略对端到端时间影响很小，负载可能对 L3 不敏感（如权重/激活更接近流式访问、可复用数据很少或被更高层级瓶颈主导），需要进一步用可控手段验证这一点。

### 当前结论
1. 工作集>单L3 + 明显L3复用 + 竞争导致驱逐时：分散策略有收益。
2. 对kt-kernel的MoE计算，分散策略收益不明显，需进一步验证原因。

### 后续计划
1. 评估LLM/MoE对CPU L3的真实需求，如果 MoE 对 L3 不敏感，那么 Chiplet感知的线程分散调度很可能不是主要优化方向
   - 限制程序可使用的L3大小，观察时延是否明显增大。
2. 调研 LLM 相关算子/场景，寻找是否有对L3复用敏感的算子，用于后续的Chiplet优化验证。

## 实验 B
目的：评估LLM/MoE对CPU L3的需求
方法：限制程序可用的L3 Cache大小，测量bench_moe程序性能，主要通过运行/root/zjj/kt/test_kt/restrict_l3.sh脚本来得到数据。
实验配置：56个线程，每个物理核心绑定1个线程，hidden_size为7168，intermediate_size为2048，格式fp16，专家256选8

| 每个CCX的L3缓存大小 | 每迭代时间 |
| ---- | ----- |
| 1MB  | 81.5  |
| 2MB  | 81.05 |
| 4MB  | 81.48 |
| 8MB  | 79.05 |
| 16MB | 76.31 |

| 每个CCX的L3缓存大小 | L3 Miss Rate |
| ---- | ------------ |
| 1MB  | 88.97        |
| 16MB | 85.23        |
### 当前结论
发现在16MB的L3缓存大小下，就已经有85.23%的L3缺失率。
每个CCD上多个核心活跃可能导致对L3的竞争，导致L3 Miss率上升，将线程数从56减少至2，仍有78.8%的Miss Rate

### 下一步计划
1. 未运行LLM推理的核心在空闲时，也会有30-40%的L3 Miss Rate，运行实验时让线程独占1个核心，消除系统其他线程的影响
2. 推测L3 Miss Rate高的原因是LLM推理过程权重远大于L3的大小，权重是一个流式访问的过程，用完即丢。还需要结合内存带宽利用率等数据验证这一推测。

## 实验C
每个CCX上放置不同数量的MoE推理线程
目的：寻找L3 Miss Rate高的原因。上一个实验发现L3大小从16MB限制到1MB,L3 Miss Rate在85-89%，且执行时间变化不大。

| 线程数/CCX | 每迭代时间  | L3 Miss Rate | Ave L3 Miss Latency | 总内存带宽（GB/S) |
| ------- | ------ | ------------ | ------------------- | ----------- |
| 1       | 288.31 | 84.08        | 373.7               | 10.06       |
| 2       | 153.58 | 84.71        | 361.09              | 18.59       |
| 4       | 83.84  | 85.8         | 340.91              | 31.46       |
| 6       | 62.82  | 86.07        | 333.81              | 41.21       |
| 7       | 59.84  | 85.75        | 352.3               | 44.35       |
### 当前结论
考虑L3 Miss来源：要计算A1xB1, A2xB2, A3xB3,...矩阵
1. 计算A1 x B1过程中，出现L3竞争，导致的Miss
2. 计算完A1 x B1之后，加载A2 x B2时的Miss
每个CCX上放置的线程数从1到7，L3 Miss Rate均在85%附近，Miss的主要来源是矩阵加载的缺失。且发现线程数少的时候，内存带宽较低，考虑能否通过预取等策略，让线程数少的时候，可达到较高的内存带宽。
