# 2026-04-08 当前研究 wiki 规范

## 目标
- 只服务当前 `vLLM CPU + Chiplet` 研究库。
- 优先解决两件事：
  - 沉淀资料
  - 追证据
- 文档要求精炼，不写与当前页面问题无关的背景废话。

## 总体形态
- `wiki/` 作为后续研究 wiki 主目录。
- 当前已经进入收口阶段：
  - 新文档优先写到 `wiki/`
  - 旧 `info/*.md` 的有效内容继续并入 `wiki/`
  - `info/` 不再承担 Markdown 主入口，只保留原始资料或少量历史兼容内容

## 目录建议
- `wiki/index.md`
  - 全库总入口，只列一级分类和关键入口页
- `wiki/README.md`
  - 维护 `wiki/` 目录自身的入口
- `wiki/资料总览/`
  - 主题导航页
- `wiki/论文解读/`
  - 单篇论文、博客、外部资料解读
- `wiki/源码分析/`
  - 围绕单个问题的源码分析
- `wiki/实验方案/`
  - 可复现命令、前提、输出路径
- `wiki/实验结果解读/`
  - 绑定具体实验批次或结果目录的结果分析
- `wiki/术语与背景/`
  - 稳定背景知识、硬件背景、工具背景
- 原始证据不并入 wiki 页面：
  - 论文/PDF 继续保留在现有原始资料目录
  - 实验原始结果继续保留在 `test_results/`
  - 源码证据直接指向仓库源码路径

## 页面类型

### 1. 总览页
- 用途：导航，不承担细节证明。
- 适合放在 `wiki/index.md` 或各子目录入口页。

建议结构：
- 本页范围
- 关键入口
- 当前最值得看的页面

### 2. 论文解读
- 用途：沉淀单篇资料的核心内容，并判断与当前课题的关系。

建议结构：
- 问题
- 核心内容
- 分析
- 证据
- 边界
- 可迁移点
- 不可直接迁移点

### 3. 源码分析
- 用途：回答一个明确源码问题，不做泛泛代码导读。

建议结构：
- 问题
- 结论
- 分析
- 证据
- 边界
- 后续验证点

### 4. 实验方案
- 用途：给出可复现步骤。

建议结构：
- 目的
- 前提
- 命令
- 输出
- 注意事项
- 判读口径

### 5. 实验结果解读
- 用途：绑定一批具体结果，解释观察、原因和结论边界。

建议结构：
- 问题
- 观察
- 分析
- 证据
- 结论
- 边界
- 下一步

### 6. 阶段总结
- 用途：把多篇资料或多批实验编译成阶段性判断。

建议结构：
- 当前判断
- 依据
- 边界
- 未解决问题
- 下一步

## 模板原则
- 不搞整库统一死模板。
- 采用“半结构”：
  - 每类页面有推荐块
  - 允许按页面内容裁剪
- 对分析型页面，`证据` 应视为硬约束。
- `相关页面` 可写可不写，不作为强制块。
- 简洁不等于删信息：
  - 删的是废话、重复表述、与当前问题无关的背景
  - 不能删的是支撑理解和复现所必需的内容
- 页面结构只是建议，不是硬模板。
- 如果某些信息虽然不在推荐结构里，但对后续继续研究、复现实验、理解证据边界或追查源码有帮助，就应写进文档，而不是因为“模板里没有这一节”而省略。
- 不允许为了让页面看起来更短、更整齐，而删掉会影响后续研究接续的重要内容。

## 内容完整性要求

### 适用范围
- 下面这些完整性要求，不只适用于本轮 `info -> wiki` 迁移。
- 之后所有对 `wiki` 的：
  - 新建
  - 迁移
  - 改写
  - 精简
  - 重组
  都必须遵守同一原则：删废话，不删重要信息。

### 实验方案
- 实验方案页必须给出完整可执行命令，不能只保留抽象调用样式。
- 若原始文档里已有：
  - 环境变量
  - helper function
  - dry-run 命令
  - profiler / PCM 命令
  - 多组推荐 case
  则迁移到 `wiki` 时应保留这些关键命令，除非它们已经过时且已被同页新命令明确替换。
- 仅写“建议输出到某目录”而不写实际命令，不算完整实验步骤。

### 论文解读
- 论文解读页不能只保留一句话结论和高层启发。
- 至少要交代清楚：
  - 论文要解决什么问题
  - 方法 / 系统设计 / 映射策略是什么
  - 实验平台与对比口径是什么
  - 主要结果在什么条件下成立
  - 与当前课题可迁移和不可直接迁移的边界是什么

### 其他页面
- 源码分析页不能只保留结论，仍需保留关键推理链和足够的源码锚点。
- 阶段总结和背景页可以压缩，但不能删掉：
  - 当前判断成立的条件
  - 明确的证据边界
  - 后续读者继续工作的入口
- 若页面中存在对“下一步研究怎么接着做”有帮助的附加信息，例如：
  - 辅助命令
  - 历史口径差异
  - 旧结论为何被修正
  - 目录或证据去向
  则应保留在文档中，不必拘泥于推荐结构是否有对应小节。

## 命名规则

### 稳定页面
- 不强制带日期。
- 适用：
  - `论文解读`
  - `源码分析`
  - `术语与背景`

建议格式：
- `论文名解读.md`
- `主题_问题.md`

示例：
- `ArcLight解读.md`
- `CPU_attention_任务切分.md`

### 绑定具体批次的页面
- 建议带绝对日期。
- 适用：
  - `实验结果解读`
  - `阶段总结`

建议格式：
- `YYYY-MM-DD_模型名_主题.md`

示例：
- `2026-04-08_Qwen3-30B-A3B_NPS1_TP2_attention结果解读.md`

### 命名约束
- 文件名优先写“对象 + 主题”。
- 标题与文件名可以不完全一致，但文件名必须能反映页面内容。

## 链接规则
- 统一先用普通 Markdown 相对路径。
- 当前不强制使用 `[[wikilink]]`。
- 只有在确实需要承担导航作用，或跨页跳转明显有价值时，再加相关链接。

## 证据书写规则
- 结论必须绑定证据。
- 证据优先写：
  - 源码路径与行号
  - 实验结果目录
  - 日志路径
  - 绝对日期或时间戳
  - 原始资料文件路径
- `证据` 小节只写支撑链路，不重复解释结论。
- 若某句是推断，不是原始资料直接结论，要明确写出“推断”。

## 索引规则
- 只保留两层索引：
  - `wiki/index.md`
  - 各子目录 `README.md`
- `wiki/index.md` 只列一级分类和关键入口，不列出全部文件。
- 各子目录 `README.md` 负责完整索引本目录内容。

## 迁移策略

### 第一阶段
- 从 `2026-04-08` 起，新 wiki 文档优先写到 `wiki/`。

### 第二阶段
- 先迁移高价值目录：
  - 论文解读
  - 源码分析
  - 实验结果解读
- 迁移时优先处理：
  - 命名不稳定的旧页
  - 多主题混在一起的旧页
  - 缺少证据块的旧页

### 第三阶段
- 当 `wiki/` 下入口足够完整后，把 `info/` 收敛成：
  - 原始资料目录
  - 或仅保留少量历史兼容入口
