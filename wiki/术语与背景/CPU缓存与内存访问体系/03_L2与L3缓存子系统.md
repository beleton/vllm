# 03 — L2 与 L3 缓存子系统

## 3.1 L2 缓存

### 组织结构

L2 是**统一缓存**（指令+数据），比 L1 更大、更慢、相联度更高。

| 参数 | AMD Zen 5 | Intel Lion Cove (P-core) |
|------|-----------|--------------------------|
| 容量 | 1 MiB / core | 2.5 MiB / core |
| 相联度 | 8 路 | 10 路 |
| 行大小 | 64 B | 64 B |
| 延迟 | ~12-14 cycle | ~14-16 cycle |
| 查找方式 | PIPT | PIPT |
| 写入策略 | Write-back | Write-back |

L2 使用 **PIPT**（Physically Indexed, Physically Tagged），因为此时物理地址已就绪（L1 miss 意味着 TLB 翻译已完成），不需要 VIPT 的并行优化。

### L1 与 L2 的包含关系

**Non-Inclusive（Intel Core 自 Skylake，AMD Zen 全系列）**：

- L2 不强制包含 L1D/L1I 中的数据
- 从 L1D 驱逐的 line 经**驱逐路径（victim path）**选在 L2 分配
- L2 驱逐时，若该 line 也在 L1 中 → 必须反失效 L1 中的副本（back-invalidation，简称 back-inv）
- 优点：容量利用率更高——L2 不会被与其内容大量重叠的 L1 副本浪费容量
- 缺点：驱逐时的 back-inv 微代码处理增加延迟，一致性协议更复杂

**Inclusive（部分 ARM 设计，Intel Core 较旧代）**：

- L2 强制包含所有 L1 中的行
- Snoop 只需查询 L2 tag：若 L2 中没有，则 L1 中一定没有。简化了监听过滤
- 缺点：L2 容量被 L1 内容重复占用的比例约为 `sum(L1_size) / L2_size`

**Exclusive（AMD 部分旧设计，部分 ARM）**：

- L1 和 L2 之间无重复内容：line 要么在 L1，要么在 L2，不能同时存在
- L1 驱逐 → line 交换到 L2，L2 命中 → line 交换到 L1
- 优点：总有效容量 = L1 + L2
- 缺点：交换开销大，每多一次访问意味着对端失效

### L2 的 MSHR/LFB 与预取

L2 维护独立的 MSHR 集合。当 L1D miss 到达 L2，L2 分配一个 MSHR 条目：

- 若 L2 命中 → 数据返回 L1D（通常以 64 B 全行或 critical-word-first 方式）
- 若 L2 miss → MSHR 发请求到 L3（或更低层），等待完成

### L2 的 Critical-Word-First / Early Restart

L2→L1D 的数据填充通常以 64 B 整行为单位，但**critical word first**机制允许在整行传输完成前，先把 Load 指令需要的 8 字节（或更小）返回：

1. L2 从内部 data array 读出 64 B 行
2. 选择包含 Load 目标字节的那个 8-byte chunk
3. 优先将该 chunk 写入 L1D 并信号通知 Load 完成
4. 剩余 56 B 在后续周期继续填充

这使 L2 hit 的**有效延迟**可能比整行传输延迟低 1-3 cycle。

## 3.2 L3/LLC 的组织与切片

### 为什么切片（Slicing）

单块统一的 L3（如 32 MiB）若设计为一个 monolithic array，面临：

- **端口竞争**：多个核心同时访问 → 仲裁逻辑复杂，延迟高
- **线长问题**：单体大 SRAM 放大面积，访问延迟不可接受
- **带宽不扩展**：每周期最多 1-2 次访问，限制总吞吐

解决方案：将 L3 **切分为多个独立的 bank/slice**（典型 4-16 slices），每个 slice 管理地址空间的一个子集。

### 地址→Slice 映射

哪个 slice 负责给定的物理地址？一般通过一个**哈希函数**（undisclosed hash）决定：

```
slice_id = hash(physical_address) % num_slices
```

哈希的目的是**均匀分布**：避免特定访问模式（如步长=页大小整数倍）总是打中同一 slice，造成该 slice 拥塞而其余空闲。

哈希函数的输入通常包括物理地址的多个位域（bits 以上叠加），确保连续的物理地址分散到不同的 slice。

### AMD Zen 5 L3 特征

| 参数 | 值 |
|------|-----|
| 总容量 | 32 MiB / CCD（每 8 核心共享） |
| 切片数 | 8 slices × 4 MiB |
| 相联度 | 16 路 |
| 类型 | Non-inclusive victim cache |
| 数据流入 | L2 驱逐的脏行或干净行 → L3 |
| 跨 CCX 访问 | 经 Infinity Fabric，延迟 ~110-150 ns |

**Victim Cache 的关键语义**：

- L3 **不主动填充** L1/L2 miss 的数据——数据从内存/远端到达时，直接写入 L1D/L2（即需求缓存 fill），**不途经 L3**
- L3 仅在 L2 **驱逐**时接收行（"victim"）
- 好处：L3 不会因 streaming/扫荡式访问被连续污染——那些一次遍历再不被用的数据，在 L2 中过期后被刷入 L3 才占 L3 容量
- 代价：同一 CCX 中 Core A 的 L2 miss 无法从 Core B 的 L2 直接获取（需要跨私有缓存通信，Zen 通过 L3 snoop 实现间接共享）

### Intel L3 特征（Ring / Mesh）

| 平台 | 拓扑 | 切片 | 延迟 |
|------|------|------|------|
| Client（Alder Lake/Raptor Lake） | 双环 | 每 P-core 一片 + 核显/SA 共同驻环 | 环跳约 4 cycle/hop |
| Server（Sapphire Rapids） | Mesh | 每 tile 多片 | 行列路由，多跳 |

### Ring Bus 详解（Intel Client）

物理上，Ring Bus 由四条单向环组成：

- 请求环（Request Ring）
- 确认环（Acknowledge Ring）
- 数据环（Data Ring，32 字节宽）
- Snoop 环（Snoop Ring）

每个环站（Ring Stop）对应一个 agent（core、LLC slice、System Agent 等）。关键性能参数：

- **环跳延迟**：~4 cycle per hop
- **环带宽**：3-4 GHz 下 ~32-40 GB/s 聚合带宽 (32 B × 频率)
- **最优访问**：相邻 slice 上环仅 1 跳 → 返回 1 跳，总延迟 ~8 cycle（不含 slice 本身 tag/data lookup）
- **最差访问**：对端 slice，环跳 = 站数/2 个 → 增加额外 12-20 cycle

环的实际时延因此成为**分布式的随机变量**：同样是一次 L3 hit，数据在相邻 slice 还是很远 slice 延迟差别明显。

### Mesh 拓扑（Intel Xeon SP / 部分 AMD EPYC）

废弃 Ring 改用 2D Mesh：

- 每个 tile 包含一个核心 + 缓存 slice + 路由节点
- 路由使用 X-Y 维度顺序（先行后列或先列后行）
- 跳数 = |Δx| + |Δy|
- 单跳延迟 ~2-3 cycle（路由逻辑 + 线延迟）

Mesh 的总带宽远高于 Ring（更多并行路径），但平均延迟更长（对端需要多跳）。

### AMD L3 内部互连

AMD CCD 内的 L3 通过一个高带宽的低延迟 crossbar/switch 连接八个核心与八个 L3 slice。由于都在一个 CCD die 上，物理距离有限，延迟主要由开关仲裁和 tag lookup 主导（而非线传输延迟）。此外，Zen 5 的 L3 对 8 核心表现为统一访问延迟（大致均匀），没有 Intel Ring 显著的 "近 slice vs 远 slice" 差异——得益于较小的物理规模。

## 3.3 L3 替换策略

### Intel Adaptive Replacement

- **Quad-Age RRIP**（4 位重引用预测）：比 L2 的 2 位更复杂
- **包含动态策略选择**：监测访问模式，自动切换 "偏向热度" 或 "偏向扫荡"

### AMD L3 替换

AMD 的 L3 替换使用**自适应替换**，结合了 RRIP 和频率计数。通过硬件反馈调整替换决策以匹配工作集特征。详细算法未公开。

## 3.4 L3 作为一致性点（Point of Coherence）

在芯片的缓存一致性层级中，L3/LLC 通常是**片上的一致性序列化点**（Point of Serialization）：

- 同一物理地址的并发请求在到达 LLC 时被**全局排序**
- LLC 负责发起跨核心的 snoop（invalidate / read-for-ownership）
- LLC directory / snoop filter 跟踪哪些核心的私有缓存可能持有某行的副本

### Snoop Filter（Intel）

Intel 的 L3 tag 目录中含有 snoop filter 信息。它是一个**精简的一致性跟踪器**，记录每个 L3 行被哪些核心的 L1/L2 持有（shared）或独占（exclusive/modified）。

**Snoop filter 容量问题**：

- Snoop filter 的条目数等于 L3 的 cache line 数
- 在 non-inclusive 设计下，snoop filter 可能溢出（即 L3 中一行不包含，但某核心 L1/L2 持有）
- 溢出处理：对被逐出的 filter 条目覆盖的所有核心发送**反向失效（Back Invalidation）**，强制那些核心释放该行
- 频繁的 snoop filter 溢出导致多余的 invalidate 消息，增加带宽消耗

### Probe Filter（AMD）

AMD 的等效机制称 Probe Filter。Zen 架构中，Probe Filter 部分位于 L3 tag 中（每个 CCD 内），部分位于 IOD 中（跨 CCD 的全局目录）。与 Intel snoop filter 功能相似，但 AMD 在 Zen 3+ 上使用 Shadow Tag 增强跨 CCD 的一致性跟踪效率。

## 3.5 Target Latency 与 Occupancy

L3 访问的延迟可分解为两部分：

1. **固定延迟**：tag look up（由 SRAM 阵列结构决定）、替换策略判断、数据 array 读出
2. **可变延迟**：队列等待（miss 的请求排满 L3 的请求队列时）、冲突重试（probe filter 命中但需要跨 CCD snoop）

**Occupancy**（占用度）指 LLC 中 MSHR/LFB 类的请求跟踪资源的占用比例。当 occupancy 接近 100%，后续 miss 请求被阻塞或退回 L2。这出现在高带宽 streaming 对 bandwidth saturation 的场景——和延迟的关系是：**带宽饱和导致 occupancy 高企 → 新请求排长队等待 → 有效延迟非线性上升**。

## 3.6 Non-Temporal / Streaming Store 路径

L3 的非时序写入路径处理 WC（Write-Combining）内存类型以及 non-temporal store 指令（如 MOVNTI / MOVNTDQ）。

- 数据不经过 L1D/L2 分配
- 使用独立的 Write-Combining Buffer（WCB，4-10 条目 × 64 B）
- 装满一整个 WCB（= 64 B 连续写入）时，直接将该 line 发送到内存控制器
- 部分写和 fence 也会触发 WCB 冲刷

AMD Zen 上 non-temporal store 经过独立的 Streaming Store Buffer → 直接发送到 IOD（经过 Infinity Fabric）到内存控制器，不污染 L3。

## 3.7 L3 的缓存行状态与写回路径

### Dirty Eviction from L2 → L3

当 L2 驱逐一行 M（modified）状态的 line：

1. L2 将脏行发送到 L3 victim queue
2. L3 分配一条 cache line（若 L3 miss → 可能触发 L3 替换）
3. 数据写入 L3（AMD：victim cache，L3 接受 L2 驱逐；Intel：L3 主动写入）
4. L2 中的该 line 标记为 I（invalid）

### L3 Eviction → Memory Controller

当 L3 驱逐一行脏行到内存：

1. L3 将 eviction 请求排队到 Home Agent（Intel）或 IOD（AMD）
2. Home Agent/IOD 通过内存控制器生成 DRAM 写命令
3. 写操作完成后，L3 释放该条目

在 AMD Zen 上，L3 驱逐的脏行经 Infinity Fabric 穿越到 IOD 的内存控制器。这个跨 die 的额外跳转增加了写回延迟。

## 3.8 关键小节

- L2 的统一性和 PIPT 设计使 L1 miss 的下一步处理流水自然——地址翻译已完成，无需额外转换
- L3/LLC 的切片设计解决了单块 LLC 的端口、带宽和物理延迟瓶颈
- Slice 哈希函数将物理地址映射到切片——均匀性是关键，避免特定步长导致的热点
- 在 multisocket/chiplet 系统上，L3 不仅是一致性检查的第一站，也是跨核心数据的中央交换站（snoop / probe 中心）
- Victim cache 策略（AMD L3）改变数据流入流出的规则：数据只从 L2 驱逐进入，非供给路径直接填充（减少了 streaming 对 L3 的污染）
