# 05 — 乱序执行引擎中的访存

## 5.1 乱序执行基础架构

现代高性能核心（Intel P-core / AMD Zen）的流水线围绕**乱序执行（Out-of-Order Execution）**构建。与访存相关的核心结构包括：

### 关键数据结构

| 结构 | 缩写 | 功能 | 典型容量 (Zen 5) |
|------|------|------|-------------------|
| Reorder Buffer | ROB | 按程序顺序跟踪所有 in-flight 指令，支持精确异常和退休 | 320+ entries |
| Reservation Station | RS / Scheduler | 保存等待操作数的指令，一旦操作数就绪即发射执行 | 96-128 entries |
| Physical Register File | PRF | 实际数据存储，通过寄存器重命名消除 WAW/WAR 伪依赖 | 224+ int + 224+ FP/向量 |
| Load Queue | LDQ | 跟踪所有 in-flight Load，检测内存排序违规 | 72-96 entries |
| Store Queue | STQ | 跟踪所有 in-flight Store，保存地址/数据直到退休 | 48-64 entries |
| Store Buffer | SB | 保存已发射但未排出的 Store 的地址和数据 | 与 STQ 部分重叠或一体 |

### 一条 Load 的生命周期（乱序执行视角）

```
1. 取指与译码
2. 寄存器重命名 → 分配 ROB 条目
3. 分派到 RS，等待地址操作数就绪
4. AGU 计算有效地址 → 同时存入 LDQ + 送 TLB/L1D
5a. L1D hit  → 数据写回 PRF → ROB 条目完成
5b. L1D miss → 在 LDQ 中保持活跃 → 等待数据返回
6. 数据返回 → ROB 条目标记完成
7. 退休（Retirement）→ 架构状态更新
```

## 5.2 Load Queue（LDQ）与 Store Queue（STQ）

### LDQ 的功能

LDQ 跟踪每个 in-flight Load 的**地址、状态和顺序**。每条 LDQ 条目包含：

- **虚拟/物理地址**（地址生成后填入）
- **ROB 编号**（确定程序年龄）
- **完成状态**（地址就绪 / 数据返回 / 已完成）
- **推测标记**（该 Load 是否在未确认的预测路径上执行）

**LDQ 的 CAM 查找**：每次新 Store 的地址就绪时，用其地址对 LDQ 做 CAM 查找——若发现较年轻的 Load 与 Store 访问同一地址，说明该 Load 已经**错误地提前执行**（在 Store 之前读取了旧值），需要触发机器清除（Machine Clear）。

### STQ 的功能

STQ 跟踪每个 in-flight Store。条目按程序顺序（FIFO）排列：

- **地址和数据**就绪后填入
- **退休前**：存储数据保持推测态，不可写入 L1D
- **退休后**：STQ 条目从推测态转为提交态，Store Buffer 等待 L1D 端口写入
- **Store 融合**：相邻地址的 Store 在 STQ 中可以合并为一个更宽的存储操作（如 2 个 32-bit Store → 1 个 64-bit Store），减少 L1D 写入次数

### LDQ 和 STQ 的交互——存储转发（回忆第 2 章）

Load 发射时，不仅查找 Store Buffer，也通过 STQ 查找可能的转发数据。**关键差异**：

- Store Buffer：已发射的 Store（地址和数据已就绪），可以做完整转发
- STQ 中的 Store：可能地址/数据未就绪，只能做部分转发判断（仅地址匹配时知道需要施加延迟）

## 5.3 内存消歧（Memory Disambiguation）

### 问题定义

```
Store [addr_X] ← data_A          // Store A: 地址未知
Load  [addr_Y] → reg1            // Load B: 地址 = addr_Y
...
Store [addr_A] ← data_B          // ← 现在才知道 addr_A = addr_Y
```

如果 Load B 在 Store A 之前执行（因为 Store A 的地址未就绪），而实际上 addr_A = addr_Y，则 Load B 读到了旧值——**内存排序违规（Memory Order Violation, MOV）**。

### 推测性 Load 执行

现代处理器**推测 Load 不依赖未就绪地址的 Store**。默认假设 Load 和未就绪 Store 不冲突（这是最常见的 case），让 Load 直接执行。安全网机制是：

1. Load 执行时，将地址记录在 LDQ
2. 每个 Store 的地址就绪时，**回溯检查（snoop）LDQ**：是否有更年轻的 Load 已经读取了同一地址？
3. 若是 → **触发机器清除**：冲刷 ROB 中该 Load 及所有后续指令，从正确路径重新执行

### 预测器辅助的内存消歧

直接让 Load 盲目推测冲突率很高（尤其在冲突频繁的代码中）会导致代价高昂的重复冲刷。因此引入了**内存消歧预测器**：

- **Store-to-Load Forwarding Predictor**：以 Load 的 IP（指令地址）为索引，预测该 Load 是否可能从 Store Buffer 转发数据
- **Memory Dependence Predictor**：记录 Load 和未就绪 Store 之间的历史冲突模式，对已知有冲突历史的 Load 强制等待最近的 Store 地址就绪

如果预测器某表项记录 "此 Load 历史上和未就绪 Store 冲突过"，则：
- Load 发送到 RS 但不立即发射
- 等待与它有冲突模式的 Store 的地址就绪
- 地址就绪后 → 确定是否真正冲突 → 冲突则等待 Store 完成并转发，不冲突则允许 Load 立即执行

### 4K Alias Check

一个更粗粒度的冲突检测是**4 KiB 别名检查**：

- Load 和 Store 地址的低 12 位（page offset）若不同，则物理地址必定不同（不考虑跨页的 Load/Store 拆分）
- 若低 12 位相同，可能是别名（需额外检查高位）
- 预测器可以在低 12 位不同时跳过等待——快速判定不冲突

## 5.4 Store 的提交路径

Store 不同于 Load，其提交（commit/retirement）过程更为复杂。

### Store 提交流程

```
1. Store 发到 RS，等待地址操作数和数据操作数
2. 两操作数就绪 → AGU 计算地址 → STQ 写入地址 + 数据
3. ROB 退休扫描到达此 Store → 标记为 "已退休，待排出"
4. Store Buffer 获得 L1D 写入端口：
   a. TLB 查询物理地址（若尚未完成）
   b. L1D tag 查找（命中/未命中）
   c. 命中 → 写入 data array → 标记 M（modified）
      miss → 分配 LFB → 从 L2 获取 line → 载入 L1D → 写入
5. STQ 条目回收
```

### 写合并（Write Combining）

内存类型为 WC（Write-Combining）时，Store 不经过 L1D——数据合并到 Write-Combining Buffer（WCB），装满后一次性发送到内存控制器。

**注意**：WC 类型下，Store 的提交语义和普通 WB 存储完全不同——读 WC 类型地址的效果和读顺序**不保证可见性**（取决于写入到 WCB 的时机以及是否已冲刷到内存）。

### Non-Temporal Store

Non-temporal store 指令（如 MOVNTI）提供了一种在 WB 内存类型下避免污染缓存的存储方式。AMD Zen 上，non-temporal store 通过独立的 Streaming Store Buffer 直接提交到内存控制器，完全绕过 L1D-L2-L3 链回填。

## 5.5 访存与 ROB 容量的关系

### ROB 作为延迟吸收器

ROB 的核心功能之一就是**吸收内存延迟**：一条 Load 在等待数据返回时，ROB 继续容纳后续的独立指令（计算、分支、其他 Load/Store），使内存延迟部分或完全被指令级并行（ILP）掩盖。

**有效并发 Load 数**受限于：
1. LDQ 容量（现代 ~72-96）
2. LFB/MSHR 数量（~16-20）
3. 实际指令流中 Load/Store 间的地址/数据依赖链

### ROB 满的影响

当 ROB 满时（最老的指令因 L2/L3/DRAM miss 无法退休，阻塞 ROB 头部），前端停止译码/发射——即使指令窗口中有大量独立指令也无济于事。这导致 **pipeline stall** 而放弃执行更多有用的 ILP。

ROB 容量 "深"（如 Zen 5 的 320+ vs 老式的 192）提供更长的延迟容忍窗口，但边际收益递减——在 ILP 本身有限的代码路径（如稠密依赖链）中更大的 ROB 意义不大。

## 5.6 机器清除（Machine Clear / Pipeline Nuke）

### 触发清除的条件

| 事件 | 描述 | 频率 |
|------|------|------|
| 分支预测失败 | 错误路径上的指令已在执行 | 每 K 条几次 |
| 内存排序违规（MOV） | Load 非法推测超越了冲突 Store | 较低 |
| 负载（Load）地址 TLB miss 后的推测路径错误 | 罕见 |
| 页面错误（#PF） | PTE P=0，操作系统需要介入 | 极低 |
| 自我修改代码（SMC） | Store 修改了已取指的指令 | 极低 |

### 清除的微架构操作

1. ROB 扫描，标记错误路径指令
2. 从分支/违规指令之后的所有 LDQ/STQ 条目失效
3. PRF 中的推测状态被释放
4. 前端重定向到正确路径
5. 从正确路径重新取指、重命名、调度

清除的代价取决于需要冲刷的指令数量——深窗口冲刷可损耗 20-50 cycle。对于 MOV 违规，这是预计时延的主要部分。

## 5.7 Load-Hit-Store（LHS）预测与优化

### 场景

```
Store [A] ← value     (地址已知)
... (若干指令) ...
Load  [A] → reg       (与 Store 同地址)
```

Store-to-Load Forwarding 覆盖此 case——Load 直接从 Store Buffer 获得数据。但只有当 Load 在 Store 地址就绪**后**发射，转发才能发生。微架构优化方法：

- **LHS Predictor**：记录 Load 地址的历史转发来源（该 Load 上次是从 Store Buffer 还是 L1D 得到数据），若预测 Source = Store Buffer，提前阻塞发射直到 Store 地址就绪，避免发射后因冲突等待
- 若预测 Source = L1D，允许 Load 立即发射（大部分情况适用）

## 5.8 关键小节

- OoO 引擎（ROB + RS + LDQ/STQ）将访存从同步阻塞转化为**流水线容忍**——代价是复杂的状态跟踪和恢复机制
- LDQ 做内存排序违规检测的关键：每一 Store 地址就绪时回溯查找 LDQ 中已执行的更年轻 Load
- Memory Disambiguation Predictor 从历史中学习冲突模式，动态减少冲突冲刷带来的过度损耗
- Store 提交路径不同于 Load：Store 在退休后才写入 L1D（通过 Store Buffer 的排出逻辑）
- ROB 容量限制 ILP 对内存延迟的覆盖范围——这是 "内存墙" 在微架构层面的表现之一
