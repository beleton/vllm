# 06 — 硬件预取机制

## 6.1 预取的基本原理

硬件预取器通过**观察历史访问模式**预测未来的数据需求，提前将数据填充到缓存中，使后续需求命中（预取的 hit）。从系统视角看，预取将内存访问的**排串**（一次等一次）转化为**流水线**（预取和计算重叠）。

### 预取三要素

| 要素 | 问题 | 权衡 |
|------|------|------|
| **What** | 哪些地址？ | 覆盖率高 vs 准确度低 |
| **When** | 何时发起？ | 太早：污染缓存 + 占用带宽；太晚：来不及隐藏延迟 |
| **Where** | 放入哪级缓存？ | L1（最低延迟，代价最高）vs L2（折中）vs LLC（保守） |

### 衡量指标

- **覆盖率（Coverage）**：预取命中的访问量 / 总访问量
- **准确度（Accuracy）**：有效的预取量 / 总预取量
- **及时性（Timeliness）**：数据到达与需求时刻的时间差——过早（不必要的驻留）和过晚（部分抵消延迟）都应避免
- **带宽开销**：预取请求占用内存带宽的比例

一个好的预取器需要在上述四者之间找到 Pareto 最优——无简单答案。

## 6.2 各层级预取器

### L1 级预取器

L1 预取器必须在**极低延迟和极小状态**下运行，因此通常是最简单、最保守的。

**Next-Line Prefetcher（相邻行预取）**：

- 触发：缓存行 X 被访问 → 预取 X+1（或 X-1 如果反向流检测到）
- 条件：仅在要求访问（Demand Access）是 L1/L2 miss 且地址等于 X 时触发
- 优点：简单有效（顺序扫描几乎 100% 命中），0 训练器
- 缺点：误预取浪费带宽，稍微不规则 stride 就失效

**IP-Based Stride Prefetcher（指令指针步长预取）**：

- 核心：用 Load/Store 的指令地址（IP）做索引，维护该 IP 的历史访问地址序列，检测其固定步长
- 例：IP=0x401000 连续访问 addr=0xA000, 0xA040, 0xA080 → 检测到 stride=+64（= 1 cache line），预训练完成后对该 IP 的访问自动预取 +64 的前方地址
- 训练：维护一张 IP → (last_address, stride, confidence) 的映射表
- 强度控制：置信度达标才预取，置信度在成功命中时递增，错误命中或从未访问时递减

### L2 级预取器

L2 预取器有更大的资源和稍多的决策时间，可以运行更复杂的模式检测。

**Stream Prefetcher（流预取）**：

- 监测 L1 miss 的地址流（到 L2 的请求流）
- 检测上升（ascending）或下降（descending）的连续行访问序列
- 当发现 N 次（如 2-3 次）连续 miss 后，分配一个 "流"（Stream）并开始超前预取
- 预取距离（Prefetch Distance）：领先当前需求行多远（数十个 cache line）
- 流的终止：预取的行超时未使用则关闭流

**Spatial Prefetcher（空间预取）**：

- 不依赖时间序列，基于空间邻近性
- 当某行被访问，查阅空间历史——"上次有人访问这一行时，后续访问了哪些邻近行"
- 例：若 PC=0x401000 历史上 access 行 X 后，紧随访问了 X+1, X+2。下次再访问 X 时预取 X+1, X+2（即使步长无规律）
- 等效于一个 PC-indexed 的空间位图（Spatial Bitmap），每 bit 记录 X+offset 是否被关联访问

**AMP（Adaptive Multi-Prefetcher，AMD）**：

- AMD 的 L2 预取系统，综合了 stride、stream 和 spatial 逻辑
- 内部包含多个引擎并行训练（stride engine, spatial engine 等）
- 硬件自动评估每个引擎的准确率和覆盖率，动态调权以决定各引擎的预取比例
- 支持预取节流——根据当前 L2 miss 的并发数和 bank 争用，动态缩减预取量

### L3/LLC 级预取器

LLC 预取器视野最大（看到所有核心的聚合访问流），但延迟约束更高。

**BOP（Best Offset Prefetcher，部分 AMD/ARM 设计）**：

- 不追踪任何流，仅维护一张 "最佳偏移量表"
- 对最近访问过的 N 个地址做自相关，计算最佳偏移（使得下一次地址 - 当前地址 = offset 的对数最多）
- 选择评分最高的 offset → 对每个新需求行 X 预取 X+offset
- 优势：极简实现，不需流状态，自然跟踪固定步长

**Feedback-Directed Prefetching（FDP，Intel）**：

- LLC 预取器根据 L2 的反馈信号（预取行是否被使用、是否及时到达）调整预取行为
- 若某模式的准确度下降，自动衰减该模式的预取强度
- 可扩展到跨核心的共享模式检测（检测多个核心共同产生的访问序列）

## 6.3 预取距离与预取度

两个关键参数决定预取及时性和覆盖范围：

### 预取度（Prefetch Degree）

每次触发预取时预取多少行。例如：
- degree=1：每 miss 预取 1 行（保守）
- degree=4：每 miss 预取 4 行（激进）

预取度过高 → 带宽浪费、缓存污染；预取度过低 → 延迟覆盖不足。

### 预取距离（Prefetch Distance）

预取提前量（领先需求行多少层）。决定数据何时到达：
- 距离过大 → 用完前预取数据被驱逐 → 预取浪费
- 距离过小 → 数据未到即被需求 → 没有覆盖延迟

现代预取器**动态调节**距离和度量——基于反馈。如：若预取命中的数据到达时，L2 MSHR 中该地址的 offset 距离为 D，则调整下一个流的目标距离以匹配当前延迟条件。

## 6.4 跨层级协调与反馈

### 层级间的预取信号

```
L1 prefetch →  会向 L2 发出预取请求（标记为 prefetch 而非 demand）
L2 prefetch →  向 L3/LLC 发出请求
LLC prefetch → 向内存控制器发出请求
```

每个层级将预取请求的优先级设为低于需求请求：如果 L2 MSHR 已满，预取请求可能被丢弃（静默丢弃，不会触发重试）。

### 反馈回环

- L1 上的 demand access 命中一个预取填充的行 → 该预取 "有效" → 向发起该预取的引擎发送正面反馈
- 预取的行在 L1/L2 中驻留过期从未被使用 → 负面反馈
- 负面反馈积累到一定额度 → 预取器降低对应模式的置信度

## 6.5 预取器交互与恶化（Prefetcher Interference）

### 共性问题

多个预取引擎同时工作时可能出现：

1. **重复预取**：两个引擎独立预取同一行 → 浪费带宽
2. **相互抑制**：引擎 A 预取的行，引擎 B 的 demand 从未看到 → B 的准确度被压低 → B 被错误惩罚
3. **过度竞争**：预取和需求请求竞争 LFB/MSHR 资源，导致需求 miss 延迟增加
4. **交叉污染**：引擎 A 的预取以 stride 模式训练的好，但引擎 B（spatial）的额外预取打乱了训练数据

### 缓解策略

- **优先级仲裁**：需求请求 > 预取请求；L1 预取 > L2 预取 > LLC 预取
- **带宽节流**：预取带宽超过一定比例时，自动减小预取度和距离
- **引擎孤立训练**：每个引擎基于过滤后的数据训练，排除其他引擎预取的干扰

## 6.6 软件预取（PREFETCH 指令）

### x86 PREFETCH 系列

| 指令 | 提示 | 典型用途 |
|------|------|---------|
| PREFETCHT0 | 预取到所有缓存层级 (L1+L2+L3) | 即将使用、需要最快访问 |
| PREFETCHT1 | 预取到 L2 及以上 | 即将使用、但不需要 L1 |
| PREFETCHT2 | 预取到 L3 及以上 | 稍后使用，避免污染 L1/L2 |
| PREFETCHNTA | Non-Temporal Access 预取 (到最近一级, 标记为非时态) | Streaming 数据，用后即弃 |

### 使用场景与陷阱

**有效场景**：
- 已知步长遍历且提前知道下一个访问地址时（manual stride prefetch）
- 链表遍历中提前加载下一个节点（指针追踪 latency hiding）
- 矩阵乘法中预处理下一个 tile

**常见陷阱**：
- **预取过密**：每元素都 PREFETCH，带宽浪费多于收益（PREFETCH 不是免费魔法）
- **预取过早**：距离过大，数据被驱逐——可能需要分块（blocking/tiling）以控制工作集大小
- **预取已命中地址**：对已在缓存中的数据 PREFETCH，无效且浪费指令槽
- **PREFETCHNTA 的处理器差异**：不同处理器对 NTA 的实现各异——某些处理为 "允许 cache 但快速驱逐"，有些直接绕过缓存

## 6.7 AMD Zen 预取系统小结

| 层级 | 预取器 | 特征 |
|------|--------|------|
| L1 | Next-line + IP-based stride | 保守、低延迟、2-3 行提前 |
| L2 | AMP（Stride+Stream+Spatial 自适应） | 动态选择引擎、自适应节流 |
| L3 | BOP + 跨核心空间预取 | 简单偏移检测、共享模式学习 |

**IBS 反推**：通过 AMD IBS（Instruction-Based Sampling），可观察到某个 miss 是否由一个预取引起、以及该 miss 的预取距离/命中率等——结合 AMDuProf 的 L2/L3 预取计数器进行全面评估。

## 6.8 关键小节

- 预取利用历史模式展望未来：硬件预取器在 1-3 次观测后即可开始预取
- 覆盖率和准确度的平衡是预取设计的核心难题——过度激进导致带宽浪费和污染
- 预取距离和度需要动态反馈调节，紧跟内存系统当前负载
- 多引擎共存时会出现交互劣化，需优先级系统和反馈环管理
- PREFETCH 指令在特定模式中有立竿见影的收益，但易被误用（过度/过早/错层）
- 在现代 OoO 处理器上，软件预取的边际收益通常低于 10 年前的处理器——硬件预取日益增强的同时，剩余改进空间明显缩小
