# 07 — 缓存一致性协议

## 7.1 问题定义

在多核系统中，每个核心拥有私有 L1/L2 缓存，多个核心可能同时缓存同一物理地址的数据。若核心 A 对自己的私有缓存副本写入，核心 B 的副本变为 **stale（过时）**——这是一致性失效。

**缓存一致性协议**定义了一套规则，保证：
1. **单写多读（SWMR）**：对于每个地址，在任何时刻最多有一个核心可以写入，或多个核心可以读取
2. **数据传播（Data Propagation）**：一个核心的写入最终对所有其他核心可见
3. **事务序列化（Transaction Serialization）**：对同一个地址的所有操作，所有核心看到相同的全局顺序

## 7.2 MESI 协议

### 四个基本状态

| 状态 | 名称 | 该核心持有 | 其他核心持有 | 是 dirty？ | 含义 |
|------|------|-----------|------------|-----------|------|
| **M** | Modified | Exclusive copy | No | Yes | 数据被修改，内存中的已过时；驱逐时必须写回内存 |
| **E** | Exclusive | Exclusive copy | No | No | 仅自己持有，数据与内存一致；可静默转为 M（无需总线事务） |
| **S** | Shared | Read-only copy | Yes (others have S) | No | 多个副本均为只读；驱逐时无需写回（静默驱逐） |
| **I** | Invalid | No copy | — | — | 不存在于本缓存，需从内存/其他缓存获取 |

### 状态转换（本地核心操作触发）

```
CPU Read Miss (I):
  → 若其他核心没有副本 → E
  → 若其他核心有 S/E/M → S (其他持有 M 的核心需先降级为 S 或将脏数据写回)

CPU Read Hit (S/E/M):
  → 状态不变

CPU Write Hit (M/E):
  → M (E→M 为静默升级，不需要通知其他核心——因为 E 保证独占)

CPU Write Hit (S):
  → 必须先发送 "Read-for-Ownership" (RFO) 到总线/LLC
  → 所有其他核心失效其 S 副本 → 本核心升级到 M

CPU Write Miss (I):
  → 发送 RFO
  → 获得独占副本 → M
  → 写入
```

### 状态转换（被外部核心触发）

```
外部 Read (另一个核心想读):
  M → S (需要写回脏数据到内存，也称为 "write-back on snoop")
  E → S (静默降级)
  S → S (不变)
  I → I (不变: 无副本可给)

外部 RFO (另一个核心想写):
  M → I (脏数据写回 + 失效)
  E → I (静默失效)
  S → I (静默失效)
  I → I
```

### MESI 的关键实现假设

MESI 假设**总线（或等效的全局有序互连）**作为广播介质，所有核心能 "看到" 同一地址上的事务并按照一致顺序处理。在更复杂的互连（ring/mesh）上，需要额外的序列化点保证全局顺序。

## 7.3 MOESI（AMD）与 MESIF（Intel）

### MOESI——AMD 的实现

MOESI 在 MESI 的基础上增加 **O（Owned）** 状态：

| 状态 | 含义 | 关键行为 |
|------|------|---------|
| O | 修改过且与其他核心共享（Modified + Shared） | 持有脏副本，其他核心有干净的 S 副本。驱逐时需要写回内存，且需通知 S 副本所有者失效。读取请求（外部 Read）时从 O 状态的脏副本转发数据（而非强制写回内存 → 重新读取） |

**O 状态的优势**：行可以在核心间共享修改过的数据而无需立即写回内存。当 Core A 有 M（写入后），Core B 想读同一行：

- MESI：A:M→S + A 的脏数据写回内存 + B 从内存读 → 慢且产生不必要的内存带宽
- MOESI：A:M→O + A 直接将脏数据转发给 B（B 得到 S） → 快速且不占用内存带宽

在 AMD 的 chiplet 设计中（CCD 间跨 Infinity Fabric），O 状态可以消除多次跨 die 的交互——Core A（CCD0）写入，Core B（CCD1）可从 CCD0 直接获得修改过的数据，而非走 CCD0→IOD→内存→IOD→CCD1 的全路径。

### MESIF——Intel 的实现

MESIF 增加 **F（Forward）**状态：

| 状态 | 含义 |
|------|------|
| F | Shared 的 **转发指定核心**。在多个 S 副本中，仅一个核心持有 F 状态（相当于 "第一个应答" 的代表）。若外部核心申请读，仅 F 持有者负责转发数据。|

**F 状态的优势**：利用共享副本做 cache-to-cache 传输（避免内存访问），同时避免多个 S 持有者同时应答导致的碰撞（只有一个 F）。

Intel 自 Nehalem 以使用 MESIF。在多 socket 系统中（多个 socket 可能都有共享副本），F 状态大幅减少了对 UPI 总线的仲裁和 redundant 应答。

## 7.4 Snoop 总线与目录式一致性

### Snoop（侦听式）一致性

在**有序广播互连**（如 shared bus）上，所有核心 "侦听" 总线上的所有一致性请求，在自己的缓存 tag 中查找是否持有被请求的行。如果持有相关行，做出响应（提供数据或失效本地副本）。

**瓶颈**：每个请求都广播到所有核心 → 互连带宽要求与 #core 成正比。超过 8-16 核时不能扩展。

### Directory（目录式）一致性

在**点对点互连**上（Ring/Mesh/Crossbar），不进行全广播。LLC 中维护一个**目录（Directory）**，对每个 cache line 记录：

- 哪些核心持有此行的**共享副本**（bit-vector, 每 bit 对应一个核心/CCX）
- 持有者中是否有**独占/修改**状态

当一个一致性请求到达 LLC（通常在 Home Agent），目录指示需 snoop 的精确核心子集（而非全体），大幅减少互连消息量。

### 混合方案（实际系统）

现代 x86 处理器使用**目录 + 过滤 + 有限广播**的混合：

- **Intel Client (Ring)**：LLC slices 包含 snoop filter（核心级的持有者跟踪）。Ring 本身提供广播，但 snoop filter 缩小了需侦听的核心范围。
- **Intel Server (Mesh)**：分布式目录（各核心/LLC slice 分别跟踪部分地址空间）。Mesh 消息仅发送到需侦听的目标节点。
- **AMD Zen (Crossbar/IF)**：片上的一致性通过 CCD 内的 Probe Filter + IOD 中的大型目录结合。片上广播限于一个 CCD（8 核），跨 CCD 走 IOD 内目录查找。

## 7.5 Snoop Filter / Probe Filter 的工程细节

### 容量与溢出

Snoop Filter（SF）的条目数通常等于或大于 LLC 的 cache line 数。但**不总是**能完全覆盖：

- **Non-Inclusive**：LLC 中的行某时刻被驱逐，但某核心 L1/L2 仍持有副本 → SF 必须仍然保持该行的跟踪。若 SF 容量在 LLC 驱逐后也告满，必须驱逐 SF 条目——这意味着该核心 L1/L2 的副本 "不可见"，后续一致性请求需对该核心做**广播**（或反向失效）
- **Inclusive**：LLC 驱逐时，该行必定不在任何核心的私有缓存中（MESI 保证），因此 SF 与 LLC 1:1 大小完全足够

### Snoop Filter Lookup 延迟

在 AMD Zen 中，Probe Filter 查找发生在 L3 tag lookup 的同期。若需要跨 CCD 查找，IOD 中的 Coherent Master 通过 Infinity Fabric 发消息到目标 CCD 的 Probe Filter——额外的 Infinity Fabric 跳转显著增加延迟（~50-80 ns 仅通信延迟，不含 tag 查找）。

这解释了跨 CCX/CCD L3 hit 延迟 ~110-150 ns 的原因：Probe Filter 查 → 跨 IOD 通信 → 目标 CCD 查其 L3 → 数据经 IOD 返回。

## 7.6 原子操作与 LOCK 前缀

### x86 LOCK 语义

LOCK 前缀（应用于 ADD/INC/XCHG/CMPXCHG 等特定指令）保证：

- 操作的**原子性**：读取-修改-写入（RMW）序列不可被其他 agent 的冲突访问打断
- 操作的**全局可见性**：操作完成后对所有核心可见（隐含全屏障）

### 实现机制

- **缓存命中（缓存锁）**：若目标 cache line 在本核心 L1D 中处于 M/E 状态，在内部执行原子 RMW，整个序列在 cache 内部原子完成（阻止外部 snoop 直到操作结束）。延迟仅 ~20-30 cycle。
- **缓存未命中（总线锁或 split-lock 模拟）**：现代处理器通常不使用物理 BUS LOCK# 信号（性能灾难）。而是发起 RFO 获得独占权限后，在 L1D 内部执行原子操作。若 line 跨越 cache line 边界（split lock），触发更重型的处理（序列化逻辑或微码辅助）。

### AMD vs Intel LOCK 实现的差异

两者在缓存命中情况下使用缓存锁。主要差异在 split-lock 的处理：Intel 在较新微架构中默认对 split lock 触发一次 #AC 异常（由内核处理，通常为 SIGBUS），AMD 允许 split-lock 通过微码慢路径执行。

## 7.7 伪共享（False Sharing）

### 现象

两个核心各自修改同一 cache line（64 B）中**不同地址**的独立数据。由于一致性协议以 cache line 为粒度，每次写入均导致另一核心的副本失效——形成 cache line "乒乓"（ping-pong）。

```
Line [ core_A's_counter (8B) | core_B's_flag (8B) | ... ]
Core A: counter++ → RFO → Core B 的副本 I
Core B: flag = 1  → RFO → Core A 的副本 I
Core A: counter++ → RFO → Core B 的副本 I
...
```

即使两个核心访问的是没有任何逻辑关联的独立变量，冲突仍发生——硬件无法知道它们是 "无关的"。

### 性能影响

每次失效+RFO 的延迟代价约 50-100 cycle（片上）、跨 socket 更甚（200+ ns = 500+ cycle）。若在热循环中出现，对 IPC 的影响可以量化为 10-100× 的降低。

### 检测与修复

- **检测**：`perf c2c`（cache-to-cache）分析工具，追踪 RFO 和 HITM 事件；`AMDuProfPcm` 的 cross-CCX snoop 指标
- **修复**：对齐填充（`__attribute__((aligned(64)))`）、将独立变量置于不同 cache line（C `struct` 中添加 padding）、per-thread 变量 + 累加（减少共享）
- **高级**：使用 C++ `alignas(64)`、`std::hardware_destructive_interference_size`，或 Padded 包装

## 7.8 跨 Socket 一致性

### 目录缓存的角色

在双 socket 及以上的系统中，每个 socket 的 Home Agent 维护整个系统的一致性目录。由于目录条目数庞大（每个 socket 可能缓存系统任一行的副本），目录条目保存在 DRAM 的一部分，但**片上了一级目录缓存**（Directory Cache）。

目录缓存 miss 意味着需要从内存读目录条目 → 进一步延迟 → 一次一致性操作（跨 socket 读）的延迟可能是单 socket 内存访问的 2-3 倍。

### 跨 Socket RFO 的完整路径

```
Core A (socket 0) 发 RFO 到 addr X
→ Socket 0 LLC: miss
→ Socket 0 Home Agent 查目录 → 发现 socket 1 持有 M
→ UPI/IF 消息到 socket 1 Home Agent
→ Socket 1 HA 查目录 → 发 snoop 到 Core B
→ Core B: M→I, 数据写回到 socket 1 LLC 或转发
→ 数据经 UPI/IF 送到 socket 0
→ 数据写回到 Core A 的 L1D (M)
```

在 AMD EPYC 上，这个过程还涉及 IOD → IOD → CCD 的多跳链路。

## 7.9 一致性的性能可见面

| 指标 | 硬件事件 | 分析视角 |
|------|---------|---------|
| L3 RFO hit rate | L3 RFO access / miss | 写操作中的一致性工作量 |
| Cross-CCX snoop | Snoop HIT on other CCX | 数据在 CCX 间的共享/竞争程度 |
| HITM (Modified Hit) on snoop | 监听到 M 状态的次数 | cache line 在不同核心间弹跳的频率 |
| Probe Filter miss | PF miss count | 冷目录追踪或压力过大的信号 |
| Remote socket traffic | UPI/IF bandwidth utilization | 跨 socket 一致性通信的带宽占用 |

## 7.10 关键小节

- MESI 是基础：四个状态 + 转移规则形成一致性基础。MOESI（AMD）和 MESIF（Intel）增加状态处理共享修改行的 cache-to-cache 共享
- 侦听式适用于小规模多核、目录式适用于大规模系统——实际系统混合两者，以目录减少广播、以侦听处理动态共享
- Snoop Filter/Probe Filter 跟踪数据在私有缓存中的存在性，容量溢出导致 broadcast 退化
- 原子操作通过缓存锁（M/E 状态下的命中）实现低延迟；split-lock 溢出到微码导致严重性能惩罚
- 伪共享导致 cache line 乒乓，性能退化 10-100×——在高性能代码中应视为优先排查项
- 跨 socket 一致性延迟是单 socket 访问的 2-3 倍，根源在于额外的 IOD↔IOD 和目录查找延迟
