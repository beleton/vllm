# 访存延迟测量

## 目标

- 当前页只回答两件事：
  - 常见工具各自测到什么。
  - 当前机器上哪些延迟量级可以直接采用。
- `AMDuProfPcm` 用于看 `L3 miss` 总延迟主要由哪些返回源贡献。
- `AMDuProfCLI IBS OP` 用于估算 `L3 miss` 样本里 `another CCX cache` 与 `local memory` 的平均访问延迟。
- 当前平台：`AMD EPYC 9745`，`family 0x1a`，`model 0x11`。

## 访问链路与排队点

- 一次 demand load 先做地址翻译；若 `DTLB/STLB` 未命中，会先发生 `page walk`。
- 地址翻译完成后，请求依次查 `L1D -> L2 -> L3`；若仍未命中，或需从别的核心取得最新副本/所有权，请求进入一致性与 uncore/fabric 域。
- 对当前 `EPYC 9005` 一类 chiplet 服务器，`CPU die` 到 `I/O die`、以及 `2P` 之间的互连都走 `Infinity Fabric`。
- 若数据最终来自 DRAM，请求还会经过内存控制器调度、通道/Rank/Bank/Row 选择与 DRAM 时序。
- `L1D miss` 之后，请求会占用 `fill buffer` 一类 miss 跟踪资源；同一 `cache line` 的并发访问还可能并入已有 miss。
- 因此软件工具通常测到的是端到端服务时间或转移时间，不是单一物理 hop 延迟。

- 一级 Cache 内部均配备了专用的 Cache Controller（缓存控制器）来统筹全局调度。面对流水线涌入的大量并发访问，控制器通过将底层 SRAM 物理阵列交错划分为多个独立的 SRAM Bank（存储库） 来实现多端口并行处理。如果并发请求落在不同的 Bank 上，它们可以在同一时钟周期内无缝完成；但若多个请求恰好访问同一个 Bank，就会引发 Bank Conflict（组冲突），此时控制器只能放行其中一个请求，其余请求必须在流水线中阻塞，等待下一个周期重试。
- 当发生 Bank 冲突或读写端口耗尽时，控制器内部的仲裁器会严格按照优先级对请求进行调度。拥有最高优先级的是 Snoop（嗅探）等一致性请求。在多核架构中，当其他核心准备修改某行共享数据时，会通过互连总线向当前核心发来 Snoop 请求以查询或作废本地副本；如果不立刻处理该请求，极易引发 MESI 状态错乱甚至导致整个系统死锁。优先级紧随其后的是 CPU 明确需要的 Demand Load（按需加载） 请求，因为它直接关系到流水线是否能继续往下执行，对延迟极其敏感。排在第三位的是硬件预取（Prefetch），由于它只是对未来数据的猜测，在 Cache 极度繁忙时会被延后甚至直接丢弃。优先级最低的则是脏数据的写回操作，通常只在总线空闲时才会被调度。
- 对于未能命中 Cache 的请求，控制器会将其分配至 MSHR（未命中状态保持寄存器） 中进行排队与追踪。MSHR 是维持 CPU “非阻塞缓存（Non-blocking Cache）”特性的核心硬件，它允许 Cache 在等待外部数据时继续处理其他指令的读写。当某行数据发生首次未命中时，MSHR 会分配一个表项并向下级 Cache 发起请求；如果在此期间，核心又发出了对该同一 Cache Line 内部其他地址的访问，控制器不会再向下级发送重复的请求，而是将这些二次访问直接在 MSHR 的同一个表项下进行合并（Coalescing）。待下级数据最终返回时，MSHR 会一次性唤醒并满足所有挂靠在该表项上的并发请求。
- 最后，当 Cache 容量耗尽、必须踢出（Evict）原有的脏数据以为新请求腾出空间时，直接写回操作往往会占用宝贵的总线带宽并阻塞关键的读取路径。为此，控制器会将这部分被替换的脏数据暂存至 Write Buffer（或 Victim Buffer，写缓冲） 中排队。流水线只需把脏数据扔进缓冲即可继续运转，而 Write Buffer 则会在后台伺机以低优先级、异步的方式将数据平滑地写回至下一级 Cache。

## 工具分工

| 工具 | 能回答 | 不能回答 |
| --- | --- | --- |
| `AMDuProfPcm profile -m l3` | `L3 miss` 延迟由本地 DRAM、远端 DRAM、其他 `CCX cache`、`CXL` 各贡献多少 | 不能按单个线程精确归属；默认不直接导出 raw `latency/requests` |
| `AMDuProfPcm profile -i <xml>` | 各来源 raw `latency/requests`，可进一步算来源平均 `L3 miss` 延迟 | 仍是 `L3/CCX` 硬件域聚合，不是线程视角 |
| `AMDuProfCLI collect -e event=ibs-op,ibsop-l3miss=1,...` | `L3 miss` 样本里的来源级平均访问延迟估算 | 不能直接得到纯本地 `L3 hit` 延迟 |

## 常见软件工具测到的是什么

### `Pointer chasing`

- `pointer chasing` 把地址组织成链表或指针环，下一次访问地址依赖上一次读取结果。
- 这种访问会压低单线程可暴露的内存级并行度，因此更接近串行、有数据依赖的读取延迟。

### `Intel MLC`

- `MLC` 的延迟线程本质上也是 `pointer chasing`。
- `--idle_latency` 更接近低负载条件下，单条有数据依赖读取的端到端服务时间。
- `--loaded_latency` 会在测延迟线程之外持续制造负载，因此结果会显式包含排队与仲裁开销。
- `--c2c_latency` 测的是 `cache line` 通过一致性协议在核心之间转移的时间。

### `lmbench lat_mem_rd`

- `lat_mem_rd` 测的是每次读取的平均纳秒数，覆盖片上缓存、片外缓存、主存和 `TLB miss latency`。
- 它同样是串行、有数据依赖的读取，因此更接近单请求服务时间，不是高并发下的 loaded latency。

### `core-to-core latency`

- 这类工具通常让两个绑核线程在同一条 `cache line` 上反复做 `compare-exchange` 或 `ping-pong`。
- 测得的是一致性协议下 `cache line` 所有权或数据完成转移的时间，包含协议与同步开销。

### 跨 `CCD` 远端 `cache` 读与 `core-to-core latency`

- 跨 `CCD` 的远端 `cache/L3` 读，路径是本地 `L1/L2/L3` 未命中后，经 `GMI -> IOD -> GMI` 到远端 `CCD` 取数并返回。
- `core-to-core latency` 走的是共享 `cache line` 的反复原子读改写路径，远端核心持续参与，且包含同步开销。
- 两者都包含跨 `CCD` 的一致性与 `fabric` 传输。
- 因此 `core-to-core latency` 可作为跨 `CCD` 一致性通信成本的粗略参考，不能直接当作纯远端 `L3 hit` 延迟。

- 若无法修改预取器设置，可用 `./mlc -e --idle_latency`。

## 当前机器可直接采用的量级参考

| 层级/路径 | 大致量级 |
| --- | --- |
| `L1` | 约 `1.7 ns` |
| `L2` | 约 `8.7 ns` |
| 本地 `L3` | 约 `26.2 ns` |
| 本地内存 | 约 `120.2 ns` |
| 跨 `CCD` 远端 `cache` 路径 | 约 `110~150 ns` |

- `L1/L2/本地 L3/本地内存` 四项来自当前机器 `MLC --idle_latency` 的实测结果：
  - `mlc_L1.txt = 1.7 ns`
  - `mlc_L2.txt = 8.7 ns`
  - `mlc_L3_local.txt = 26.2 ns`
  - `mlc_local_memory.txt = 120.2 ns`
- 跨 `CCD` 远端 `cache` 路径的 `110~150 ns` 来自三类现有材料的共同量级：
  - `mlc_L3_other.txt = 112.9 ns`
  - 绑定单 `node` 后的跨 `CCD core-to-core latency` 约 `139~148 ns`
  - `AMD EPYC Rome` 论文里同 `socket` 远端 `cache` 访问约 `102.5~152 ns`
- 跨 `CCD` 远端 `cache/L3` 路径可按约 `110~150 ns` 量级使用，且已接近本地内存。
- 该量级对应的是跨 `CCD` 远端 `cache` 路径，不是当前机器纯跨 `CCD L3 hit latency` 的直接测量。

## PCM：`L3 source latency`

- `l3_xi_sampled_latency.*` 的 `EventCode=0xAC`，`l3_xi_sampled_latency_requests.*` 的 `EventCode=0xAD`。
- 当前平台常见来源至少有：
  - `dram_near`
  - `dram_far`
  - `near_cache_far_cache_near`
  - `near_cache_far_cache_far`
  - `ext_near`
  - `ext_far`
- `L3 Miss Latency From XXX (%)` 的分母是总采样延迟和，因此表示延迟贡献占比，不表示请求数占比。
- 当前平台里，`Local/Remote Memory or I/O` 底层对应的是 `dram_near/dram_far`；`CXL` 另有单独指标。

### 指标与底层事件对应

| 显示指标 | 公式 | 当前平台底层来源 |
| --- | --- | --- |
| `Ave L3 Miss Latency (ns)` | `($L3SampledLatency * 10) / $L3SampledLatencyRequests` | `all_no_other` |
| `L3 Miss Latency From Local Memory or I/O (%)` | `($L3SampledLatencyFromLocalMemory * 100) / $L3SampledLatencyAll` | `dram_near` |
| `L3 Miss Latency From Remote Memory or I/O (%)` | `($L3SampledLatencyFromRemoteMemory * 100) / $L3SampledLatencyAll` | `dram_far` |
| `L3 Miss Latency From another CCX in same node (%)` | `($L3SampledLatencyFromExternalCacheLocal * 100) / $L3SampledLatencyAll` | `near_cache_far_cache_near` |
| `L3 Miss Latency From another CCX in remote node (%)` | `($L3SampledLatencyFromExternalCacheRemote * 100) / $L3SampledLatencyAll1` | `near_cache_far_cache_far` |
| `L3 Miss Latency From Local Extension Memory (CXL) (%)` | `($L3SampledLatencyFromLocalExtensionMemory * 100) / $L3SampledLatencyAll1` | `ext_near` |
| `L3 Miss Latency From Remote Extension Memory (CXL) (%)` | `($L3SampledLatencyFromRemoteExtensionMemory * 100) / $L3SampledLatencyAll1` | `ext_far` |

### raw 事件与来源平均延迟

- 比较不同来源的平均 `L3 miss` 延迟，应直接看 raw `latency` 与 `requests`：

```text
来源平均 L3 miss 延迟(ns)
= 来源 latency 事件 / 来源 requests 事件 * 10
```

例如：

```text
local_memory_avg_latency(ns)
= L3SampledLatencyFromLocalMemory
  / L3SampledLatencyRequestsFromLocalMemory
  * 10
```

- 当前常用中间量如下：

| 中间量 | 事件/含义 |
| --- | --- |
| `$L3SampledLatencyAll` | `0x0303C00000403FAC`，`all_no_other` 采样延迟和 |
| `$L3SampledLatencyRequestsAll` | `0x0303C00000403FAD`，`all_no_other` 采样请求数 |
| `$L3SampledLatencyFromLocalMemory` | `0x0303C000004001AC`，`dram_near` 采样延迟和 |
| `$L3SampledLatencyRequestsFromLocalMemory` | `0x0303C000004001AD`，`dram_near` 采样请求数 |
| `$L3SampledLatencyFromRemoteMemory` | `0x0303C000004002AC`，`dram_far` 采样延迟和 |
| `$L3SampledLatencyRequestsFromRemoteMemory` | `0x0303C000004002AD`，`dram_far` 采样请求数 |
| `$L3SampledLatencyFromExternalCacheLocal` | `0x0303C000004004AC`，同节点 `another CCX cache` 采样延迟和 |
| `$L3SampledLatencyRequestsFromExternalCacheLocal` | `0x0303C000004004AD`，同节点 `another CCX cache` 采样请求数 |
| `$L3SampledLatencyFromExternalCacheRemote` | `0x0303C000004008AC`，远端节点 `another CCX cache` 采样延迟和 |
| `$L3SampledLatencyRequestsFromExternalCacheRemote` | `0x0303C000004008AD`，远端节点 `another CCX cache` 采样请求数 |

- `AMDuProfPcm --help` 已说明 `-p/--tid` 只适用于 `Core metrics`；因此 `L3 source latency` 只能按硬件域采集，不能按单个线程归属。

## IBS：来源级平均延迟反推

- 固定采样条件：

```bash
-e event=ibs-op,ibsop-l3miss=1,call-graph
```

- 只有把样本限制到 `L3 miss`，下面的来源延迟反推公式才成立。

```text
another_ccx_avg_cycles
  = IBS_LD_L1_DC_MISS_LAT_AVE
    * (%IBS_LD_PEER_CACHE_HIT_LAT / IBS_LD_PEER_CACHE_HIT_RATE_%)

local_memory_avg_cycles
  = IBS_LD_L1_DC_MISS_LAT_AVE
    * (%IBS_LD_LOCAL_DRAM_HIT_LAT / IBS_LD_LOCAL_DRAM_HIT_RATE_%)
```

### 采样与报表


## 边界

- 当前页涉及的 `PCM/IBS/MLC/lmbench/core-to-core` 结果，本质上都是端到端服务时间、来源级观测延迟或一致性转移时间，不是固定不变的物理链路裸延迟。
- 对 `another CCX cache`、`local memory` 之类来源做平均延迟时，结果会受样本当时的 `page hit/miss`、资源争用、系统负载、频率状态和拓扑影响。
- `PCM` 的 `L3 Miss Latency From XXX (%)` 只能回答“总 miss 延迟主要由谁贡献”，不能回答“该来源请求数占比是多少”。
- `IBS` 的反推结果更适合比较来源绝对延迟；不要把 `PCM` 的来源占比直接写成“该来源单次访问一定更慢”。
- 当前没有公开的 `PCM` 指标能直接给出纯本地 `L3 hit` 延迟。
- 当前最接近的公开口径在 `IBS` 域，但它合并了共享 `L3 hit` 与同一 `CCX` 内其他 `L1/L2 hit`：

```text
same_ccx_local_cache_avg_latency(cycles)
= IBS_LD_LOCAL_CACHE_HIT_LAT
  / IBS_LD_LOCAL_CACHE_HIT
```

- 这里的表述应为 `same-CCX local-cache hit latency (IBS)`，不应记为 `local L3 hit latency`。

## 联读规则

1. 先看 `Demand DC Fills From XXX (pti)`，判断访问量主要落到哪里。
2. 再看 `Ave L3 Miss Latency (ns)` 与 `L3 Miss Latency From XXX (%)`，判断这些路径对总 miss 代价贡献多少。
3. 若要比较 `another CCX cache` 与 `local memory` 的来源平均延迟，再看 `IBS` 反推结果或 `PCM raw latency/requests`。
