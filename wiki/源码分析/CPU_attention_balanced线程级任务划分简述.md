# CPU attention `balanced` 与 `acc-local-l3` 线程级任务划分简述

`balanced` 的任务划分先发生在调度阶段。这一阶段不会直接把工作绑定到物理线程，而是先遍历所有请求，按每段 `q token` 当前可见的 `KV` 区间累计工作量，再逐步生成一批 `workitem_group`。每个 `workitem_group` 对应某个请求上一段连续 `q token` 的 attention 计算，以及它对应的一段 `KV` 计算范围。生成这些 `workitem_group` 之后，调度器会把它们按顺序装入若干逻辑线程桶。这里的“逻辑线程桶”只是调度阶段的任务槽位，不是后面固定执行的物理线程。

因此，每个逻辑线程桶里挂了多少个 `workitem_group`，描述的是调度结果，不是某个物理线程最终执行了多少工作。连续非空的逻辑线程桶数量会被单独统计出来，运行时再据此定位每个逻辑线程桶对应的整段 `workitem_group`。

真正执行 attention 时，会先启动一组 OpenMP 线程，但运行时任务并不是“一个线程拿一个 workitem”。`balanced` 会先把 attention 工作沿两个维度展开：一个维度是 `kv_head`，另一个维度是非空逻辑线程桶。因此，一个运行时 task 对应的是“一个 `kv_head` + 一个逻辑线程桶”。只要这两个量固定了，这个 task 要处理的就是该逻辑线程桶里挂着的整段 `workitem_group`，并且在整个 task 执行期间，`kv_head` 保持不变。

具体到任务领取方式，所有 OpenMP 物理线程都共享同一个全局计数器，谁先空闲谁就先领取下一个 task。线程拿到 task 之后，会先还原出“哪个 `kv_head`、哪个逻辑线程桶”的组合，然后顺序处理这个桶里的全部 `workitem_group`。同一个逻辑线程桶里可以同时挂多个请求的 `workitem_group`，所以一个 task 也可能顺序处理多个请求，但整个过程中 `kv_head` 不变。哪个物理线程最终处理哪个 `kv_head × 逻辑线程桶` 组合，不是在调度阶段预先定死的，而是由运行时全局抢任务决定的。

因此，`balanced` 的关键特征不是“每个物理线程固定负责一段 token”或者“每个 `kv_head` 固定绑到一组线程”，而是先在调度阶段把工作整理成较均匀的逻辑线程桶，再在执行阶段把任务展开成 `kv_head × 逻辑线程桶`，最后由统一线程池动态抢占。这种设计优先保证全线程池的负载均衡，不保证 `kv_head` 与 `L3/CCX` 的局部绑定。

现有 `acc-local-l3` 不改 attention 的数学计算内核，也不重写底层 `workitem_group` 和归约任务的生成逻辑；它仍然复用原有调度阶段产出的这批任务。它真正改的是线程组织方式和任务领取范围。在线程启动后，先按局部缓存拓扑把线程划成若干 `subgroup`。然后为每个 `kv_head` 指定一个起始 `subgroup`，并用 `group_span` 决定它覆盖多少个连续 `subgroup`。`group_span=1` 时，一个 `kv_head` 只在一个局部线程组内执行；`group_span>1` 时，一个 `kv_head` 可以交给多个相邻 `subgroup` 联合处理。

进入执行阶段后，`acc-local-l3` 不再让全线程池去抢同一批任务，而是先限制“只有覆盖到该 `kv_head` 的 `subgroup` 内线程才有资格执行这个 `kv_head`”。在这个覆盖范围内部，线程再通过该 `kv_head` 自己的局部计数器，动态领取原有逻辑线程桶对应的任务和归约项。也就是说，现有 `acc-local-l3` 不是把 `balanced` 的全局动态均衡完全改成静态分派，而是把动态领取范围从“全线程池”收缩到“负责该 `kv_head` 的局部线程池”。同一个 `kv_head` 覆盖到多个 `subgroup` 时，当前实现会在这些 `subgroup` 的联合线程池里对原有逻辑线程桶做唯一领取，而不是重复执行同一批任务。

因此，两者在线程级的核心差异可以直接概括为：`balanced` 是全线程池上的全局动态均衡；现有 `acc-local-l3` 是先按 `L3/CCX` 局部域限制 `kv_head` 的可执行线程范围，再在这个局部范围内做动态均衡。前者优先追求整体负载均衡，后者优先约束共享 `K/V` 工作集的活动范围。
