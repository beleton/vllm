# Enhancing Similarity Search Throughput by Dynamic Query Reordering 解读

**一句话概述**：论文面向流式相似检索任务，提出在查询进入索引前先放入有限缓冲区，按查询之间的相似性动态重排执行顺序，使连续查询尽量访问相同索引分区并复用缓存，从而在允许一定排队延迟的场景下提升吞吐。论文实验使用 M-Index 磁盘型 metric-space 索引，不是 HNSW 实现；其价值在于“请求重排 + 缓存复用”的系统思想。

## 论文基本信息

- 论文：`Enhancing Similarity Search Throughput by Dynamic Query Reordering`
- 作者：Filip Nalepa、Michal Batko、Pavel Zezula
- 机构：Masaryk University
- 会议/出版：DEXA 2016，LNCS 9828，2016
- 研究对象：流式 kNN 相似检索查询的执行顺序优化
- 实验索引：M-Index，基于 metric space（度量空间，一种只要求对象之间存在距离函数的相似性建模方式）
- 原始资料：`wiki/原始资料/papers/HNSW/Enhancing Similarity Search Throughput by Dynamic Query Reordering.pdf`

## 背景

相似检索用于在图像、文本、视频等非结构化数据中按内容查找相近对象。与数据库中的精确匹配不同，相似检索通常先把对象表示为特征向量或其他可计算距离的对象，再根据距离函数返回最近对象。

论文讨论的是 `kNN`（k-nearest neighbors，k 近邻查询）：给定一个查询对象，系统返回数据库中距离它最近的 `k` 个对象。若数据量很大，直接把查询对象与所有数据库对象比较成本很高，因此会使用相似检索索引减少实际访问的数据量。

论文采用的抽象是 `metric space`。该模型不要求对象必须是普通向量，只要求任意两个对象之间能计算距离。图像描述符、文本特征、音频特征都可以放入这一模型。索引会把数据库对象划分为多个分区，查询时只访问可能包含近邻的部分分区。

论文的场景不是交互式单查询优化，而是流式处理：查询对象不断到达，每个查询都要执行一次相似检索。例如：

- 网页爬虫持续收集图片，并需要按图像内容生成文本标注；
- 垃圾邮件过滤系统持续把新邮件与已有垃圾邮件知识库比较；
- 新闻通知系统持续把新文章与用户兴趣档案比较。

这些场景的核心指标是单位时间处理多少查询，也就是吞吐。单个查询不一定要立即执行，系统可以接受有限排队延迟。论文利用这一点，把“查询到达顺序”与“查询执行顺序”分开，通过局部重排换取更好的缓存命中。

## 研究问题

论文研究的问题是：给定一个持续到达的相似检索查询流，如何在保证每个查询最终被处理、且排队时间不超过上限的前提下，重排查询执行顺序，使整体处理时间最短、吞吐最高。

论文的关键假设是：

```text
相似的查询往往访问索引中的相似分区。
```

若查询 `q1` 和 `q2` 距离很近，索引为了处理它们通常会读取相近的一组数据分区。若先处理 `q1`，这些分区被放入缓存；随后处理 `q2`，`q2` 可能直接复用这些缓存分区，减少磁盘访问。论文将优化目标转化为：让执行序列中相邻查询尽量相似。

本文后续所说的缓存，均指索引程序在进程内存中维护的分区缓存：M-Index 从 HDD 读取 bucket / partition 后暂存，后续查询复用同一分区时可减少磁盘读取。它不同于由硬件自动管理的 CPU L3 Cache；论文也未讨论 OS page cache 的控制。

该问题与常见缓存优化有三点差异：

1. 论文不缓存最终查询答案，而是缓存索引访问过的数据分区，因此不会降低查询结果准确性。
2. 论文不假设输入流天然包含连续相似查询，而是主动在缓冲区中寻找相似查询并重排。
3. 论文允许有限延迟，但不能让冷门查询长期饥饿。

## 问题模型

论文把输入建模为无限查询流：

```text
s = (q1, q2, ...)
```

每个 `qi` 是一个待检索对象。系统对每个查询执行 `NN(qi, k)`，返回数据库中距离它最近的 `k` 个对象。

系统维护一个最大容量为 `N` 的缓冲区 `B`。查询到达后先进入缓冲区，索引空闲时从缓冲区中选择一个查询执行。选择策略就是论文要设计的 `pop` 函数。

### 最大延迟约束

只按相似性选择查询会导致饥饿：小簇或孤立查询可能长期不被选中。论文引入 `MD`（maximum delay，最大允许延迟）：

- 查询进入缓冲区时记录时间戳；
- 每次选择查询时，如果缓冲区中存在等待时间超过 `MD` 的查询，必须处理等待最久的查询；
- 否则可以按重排策略选择更有利于缓存复用的查询。

该约束让算法适用于“可以等待一段时间，但不能无限等待”的流式系统。

### 处理时间目标

论文将处理 `m` 个查询所需时间记为 `processingTime`。该时间由两部分组成：

- 查询本身执行时间；
- 缓冲区管理开销，包括插入、聚类、选择等。

论文认为相似检索查询本身代价远高于缓冲区管理，因此重点优化查询执行顺序带来的缓存收益。

## 系统设计

论文系统包含两部分：

1. 查询缓冲区：保存尚未执行的查询，并根据策略选择下一个查询。
2. metric index：负责实际 kNN 查询，内部包含磁盘上的索引分区和分区缓存。

索引把数据库划分为多个分区：

```text
P = {p1, p2, ..., pn}
```

执行一个查询 `q` 时，索引会访问其中一部分分区，记为 `I(q)`。如果 `I(q)` 中的分区已经在缓存里，查询就能减少磁盘读取。

### 缓存效用

论文定义 `cacheUtility(q, cache)` 表示查询 `q` 需要访问的分区中有多少比例已经在缓存中：

```text
cacheUtility(q, cache) = |I(q) ∩ cache| / |I(q)|
```

该值越高，查询越可能更快完成。论文在实验中验证：随着缓存中命中分区比例增加，查询时间显著下降。

缓存内容采用 `LRU`（least recently used，最近最少使用）策略更新。查询访问过的新分区进入缓存，最久未访问的分区被淘汰。缓存大小用可容纳的对象数量限制，而不是用字节数建模。

### 相似查询与相似分区

论文使用以下关系作为设计依据：

```text
d(q1, q2) 接近 0  =>  I(q1) 与 I(q2) 接近
```

含义是：两个查询对象越相似，索引访问的分区集合越可能重叠。若执行序列中相邻查询相似，前一个查询加载到缓存的分区更可能被后一个查询复用。

论文进一步定义 `similarCount`，统计执行序列中相邻查询相似的次数。目标不是寻找全局最优排列，而是用低开销贪心策略尽量增加连续相似查询段的长度。

## 查询聚类

### M-Index 与 pivots

M-Index 是已有的 metric-space 相似检索索引，不是本文提出的算法。论文引用的是 Novak、Batko、Zezula 在 2011 年发表的 M-Index 工作。M-Index 属于索引结构/访问方法，用于支持精确或近似相似检索；本文实验中使用的是 approximate kNN 模式，并用最大候选对象数作为停止条件。

M-Index 的构建阶段会先确定一组 `pivots`（支点，作为距离参照的对象）。数据库对象插入索引时，系统计算对象到这些 pivots 的距离，并按距离排序得到 pivot permutation（支点排列），该排列用于决定对象进入哪个 bucket。查询时也计算查询对象到同一组 pivots 的距离，用于剪枝和减少需要访问的 bucket 数量。

本文没有说明 M-Index 实验中 pivots 的具体选取算法、数量或采样策略。一般而言，metric-space 索引选择 pivots 的依据是让它们能较好地区分数据对象，例如覆盖不同区域、减少对象之间的距离排序混淆、提高剪枝效果；具体策略依赖索引实现和数据集。本文不研究 pivot 选择本身。

为了在缓冲区中快速找到相似查询，论文不对所有查询两两计算距离，而是复用 M-Index 的 pivots 做 pivot-based clustering（基于支点的聚类）。查询到达缓冲区时，系统计算该查询到所有 pivots 的距离，按距离从近到远排序，并用得到的支点排列作为聚类标识。相同或相近排列对应的查询被认为可能访问相近的索引分区。

该聚类方式与 M-Index 匹配，因为 M-Index 本身也使用支点距离进行索引分区和剪枝。查询进入缓冲区时计算出的支点距离后续还能在查询执行中复用，因此聚类开销较低。

## 重排算法

论文提出三类主要执行策略，并用一个无优化基线作对比。

### 基线 B

基线策略按查询到达顺序逐个执行，不使用缓冲区重排，也不利用论文提出的分区缓存复用策略。它代表普通流式查询执行方式。

### Densest First

`DF`（densest first，最密集簇优先）是最简单的贪心重排：

1. 查询进入缓冲区后被分配到簇；
2. 若当前簇为空，选择缓冲区中查询数量最多的簇；
3. 连续处理该簇中的查询；
4. 簇处理完后，再选择新的最大簇。

该策略的含义是：一个簇中查询越多，连续处理它们越可能得到更长的相似查询序列，前一个查询加载的数据更可能被后续查询复用。

DF 的问题是可能违反延迟目标。若某些小簇一直不是最大簇，其中查询会等待很久。因此 DF 需要加入超时处理。

### Densest First with Timeouts

`DFT`（densest first with timeouts，带超时处理的最密集簇优先）在 DF 基础上处理最大延迟约束：

- 如果出现超时查询，先处理等待最久的查询；
- 超时查询处理后，在“原当前簇”和“超时查询所属簇”之间选择较大的簇继续执行。

DFT 比 DF 更关注超时查询所属簇，避免处理完超时查询后立即回到原簇，导致该超时簇中的其他查询继续等待。

### Full Greedy

`F`（full greedy，完整贪心）是论文最终算法。它不只看簇大小，还估计处理某个簇后多久会被打断。打断有两类来源：

1. 当前簇被处理完；
2. 处理期间其他簇出现超时查询，系统必须切出去处理。

对每个候选簇 `C`，论文估计：

```text
clusterTime(C) = c * (|C| - 1) + d
```

其中 `d` 表示处理该簇第一个查询的时间。第一个查询通常没有缓存收益，所以较慢。`c` 表示后续查询在缓存稳定后每个查询的时间。

论文还估计该簇外最早超时会在多久后发生：

```text
earliestTimeout(Bt, C)
```

最终，该簇可连续处理的时间近似为：

```text
min(clusterTime(C), earliestTimeout(Bt, C))
```

完整贪心算法选择该值最大的簇。该策略能把小但即将超时的簇提前处理，而不是机械选择最大簇。

## 超时查询的缓存策略

当某个超时查询来自当前簇之外时，系统必须处理它。处理后有两个选择：

1. 不缓存超时查询访问的数据，继续处理原当前簇；
2. 缓存超时查询访问的数据，转去处理超时查询所在簇。

论文的判断标准是：哪种选择能带来更长的连续相似查询段。若算法决定处理完超时查询后回到原当前簇，超时查询访问的数据不会被缓存，因为后续不会继续执行它所在的簇，缓存这些数据可能污染当前簇需要的缓存内容。若算法决定切换到超时查询所在簇，则缓存超时查询访问的数据，以便该簇后续查询复用。

该设计是论文区别于简单“超时就插队”的关键点。它把延迟约束与缓存复用放在同一个决策中处理。

## 正确性与结果精度

论文强调该方法不改变查询结果。缓存的是索引分区数据，而不是近似答案；查询仍然由原索引执行。重排只改变不同查询之间的执行顺序，不改变单个查询内部的 kNN 计算逻辑。

需要注意的是，实验使用的是 M-Index 的 approximate 10-NN 查询。近似性来自索引本身的候选集停止条件，不是来自重排或缓存。

## 实验设置

### 索引与实现

实验使用 M-Index。M-Index 将 metric-space 数据划分为磁盘上的 bucket（桶，索引分区），查询时根据查询对象到支点的距离剪枝，只读取候选 bucket。论文使用 M-Index 的 approximate kNN 模式，并用最大访问候选对象数作为停止条件。

实现使用 Java 和 MESSIF 库。实验机器为 Intel Xeon 2.00 GHz，8 GB RAM，数据描述符存储在 HDD 上。

该设置说明论文优化的主要瓶颈是磁盘分区读取和分区缓存复用。

### 数据集与查询

论文使用 Profimedia 图像数据生成三个描述符数据集：

| 数据集 | 规模 | 描述符 |
|---|---:|---|
| 1M Caffe | 100 万 | Caffe 图像特征，4096 维 |
| 1M MPEG-7 | 100 万 | MPEG-7 图像描述符 |
| 10M MPEG-7 | 1000 万 | MPEG-7 图像描述符 |

实验中另行构造图像流，查询对象持续进入缓冲区。每个查询执行 approximate 10-NN。

### 缓存参数

缓存大小按可缓存描述符数量设置：

- 1M Caffe：最多缓存 40,000 个描述符，占数据库 4%；
- 1M MPEG-7：最多缓存 40,000 个描述符，占数据库 4%；
- 10M MPEG-7：最多缓存 90,000 个描述符，占数据库 0.9%。

候选集大小：

- 1M Caffe、1M MPEG-7：每个 approximate 查询最多访问 1,000 个候选对象；
- 10M MPEG-7：缓冲区大小实验中使用 2,000 个候选对象，最终 full greedy 对比实验也使用 2,000 个候选对象。

### 评估指标

论文主要评估：

- 查询处理时间：处理固定数量查询所需分钟数；
- 吞吐加速比：相同时间内处理查询数相对基线的比例；
- cache utility：查询访问分区中缓存命中的比例；
- median delay：查询进入缓冲区到被处理的中位等待时间；
- timeout 数量：触发最大延迟约束的查询数。

论文没有报告 recall 曲线，也没有研究多线程扩展、CPU cache miss、NUMA 或 chiplet 指标。

## 实验结果

### 缓存效用对查询时间的影响

论文首先验证核心假设：缓存命中的分区比例越高，查询时间越短。

实验对三个数据集运行 approximate 10-NN，并人为改变查询访问 bucket 中已有多少比例在缓存里。结果显示，随着缓存命中比例上升，查询时间显著下降。该实验支撑了后续设计：若重排能让连续查询访问重叠分区，吞吐就会提高。

该实验只证明“命中正确分区时查询更快”，不证明任意缓存都有效。缓存必须包含后续查询会访问的索引分区。

### 缓冲区大小的影响

论文随后测试缓冲区大小。没有设置最大延迟约束，每个实验运行 30 分钟。

结果趋势是：

- 缓冲区越大，系统越容易找到较大的相似查询簇；
- 相似查询簇越大，连续处理时缓存复用越充分；
- cache utility 和吞吐随缓冲区增大而上升；
- median delay 也随缓冲区增大而上升。

该结果揭示了方法的核心权衡：吞吐提升来自等待和重排，缓冲区越大，吞吐潜力越高，但单个查询等待时间越长。

### 四种策略对比

论文最终对比四种策略：

| 策略 | 含义 |
|---|---|
| B | 基线，按到达顺序执行 |
| DF | 选择最大查询簇连续处理 |
| DFT | DF 加入超时后续簇选择 |
| F | 完整贪心，选择预计最长不被打断的簇 |

#### 1M Caffe

实验参数：

- 缓冲区大小：8,000；
- 缓存：40,000 描述符，占数据库 4%；
- 最大延迟：15 分钟；
- 查询数：100,000；
- 每查询候选对象数：1,000。

处理 100,000 个查询的时间：

| 策略 | 时间 |
|---|---:|
| B | 176.05 分钟 |
| DF | 62.43 分钟 |
| DFT | 50.62 分钟 |
| F | 47.73 分钟 |

完整贪心相对基线处理时间减少到约 1/3.69。论文报告 full greedy 的 cache utility 为 0.62，中位等待时间为 128 秒。超时数量从 DF 的 13,408 次降到 F 的 1,491 次。

该结果说明：只按最大簇处理已经有显著收益；加入超时后的继续策略和完整贪心进一步减少被超时打断的次数。

#### 1M MPEG-7

实验参数与 1M Caffe 相同：

- 缓冲区大小：8,000；
- 缓存：40,000 描述符，占数据库 4%；
- 最大延迟：15 分钟；
- 查询数：100,000；
- 每查询候选对象数：1,000。

处理 100,000 个查询的时间：

| 策略 | 时间 |
|---|---:|
| B | 101.62 分钟 |
| DF | 36.68 分钟 |
| DFT | 33.97 分钟 |
| F | 27.33 分钟 |

完整贪心相对基线达到 3.72 倍处理时间改善。论文报告 full greedy 的 cache utility 为 0.66，中位等待时间为 79 秒，超时数量为 169 次。

#### 10M MPEG-7

实验参数：

- 缓冲区大小：10,000；
- 缓存：90,000 描述符，占数据库 0.9%；
- 最大延迟：30 分钟；
- 查询数：100,000；
- 每查询候选对象数：2,000。

论文只展示 B 与 F：

| 策略 | 时间 |
|---|---:|
| B | 256 分钟 |
| F | 119.63 分钟 |

完整贪心约为基线 2 倍以上。论文报告 full greedy 的中位等待时间为 548 秒，cache utility 为 0.38，超时数量为 2,838 次。

该数据集规模更大，缓存只覆盖数据库 0.9%，cache utility 低于两个 1M 数据集，因此加速比下降。结果符合论文机制：缓存容量相对工作集越小，重排能制造的有效复用越少。

## 论文结论

论文结论是：在允许有限延迟的流式相似检索场景中，动态查询重排能显著提高吞吐。核心机制是把相似查询连续执行，使它们访问的索引分区在缓存中被复用。完整贪心算法在实验中最高达到约 3.7 倍吞吐改善，同时满足最大延迟约束。

该方法不改变单个查询结果，不依赖近似答案缓存。它依赖三个条件：

1. 查询之间存在可发现的相似簇；
2. 相似查询访问的索引分区高度重叠；
3. 系统能够容忍秒级到分钟级等待。

## 局限性

1. 论文不是 HNSW 论文。实验索引是 M-Index，数据分区在 HDD 上，缓存目标是减少磁盘 bucket 读取。
2. 实验平台较旧，只有单机 Intel Xeon 2.00 GHz、8 GB RAM、HDD。结论不能直接外推到现代全内存 HNSW、SSD-resident ANN 或多 CCD CPU。
3. 论文关注吞吐，不适合严格低延迟交互式检索。实验中 full greedy 的中位等待时间可达到 79 秒、128 秒、548 秒。
4. 论文没有报告 recall 变化。虽然重排不改变单查询逻辑，但实验查询本身是 approximate 10-NN，候选集停止条件可能影响精度。
5. 论文没有评估多线程并发、CPU cache miss、NUMA、L3 本地性或 chiplet 拓扑。
6. 算法依赖查询聚类质量。若输入流中相似查询很少，或相似查询不访问重叠分区，重排收益会下降。

## 对当前 HNSW/Chiplet 研究的启发

该论文不能作为 HNSW 在 Chiplet CPU 上优化有效的直接证据，但提供了一个可迁移的系统问题：

```text
请求调度能否把访问路径相近的查询放在时间或拓扑上相邻的位置，从而提高局部缓存复用。
```

对 HNSW 来说，类比关系如下：

| 论文中的对象 | HNSW/Chiplet 中的可能对应物 |
|---|---|
| M-Index bucket | HNSW 中被访问的节点、邻接表、向量数据 |
| HDD + 分区缓存 | DRAM + L3 cache，或 SSD + DRAM cache |
| 相似查询连续执行 | 相似 query 分配到同一 CCD 或相邻时间窗口 |
| 查询缓冲区 | serving 层 batching、队列调度、请求重排 |
| 最大延迟 | 在线服务的排队延迟 SLO |

若要把思想用于当前 HNSW 方向，需要重新验证以下事实：

1. 相似 query 是否在 HNSW 中访问大量重叠节点和 cache line；
2. 这些重叠访问是否发生在 L3 可保留的时间窗口内；
3. 把相似 query 放到同一 CCD 是否提高本地 L3 hit，而不是只增加队列等待；
4. 在线服务允许的延迟预算是否足够支撑重排；
5. 重排本身的聚类开销是否低于收益。

该论文更适合作为“query-level locality scheduling”的背景文献，而不是 HNSW 索引结构或 graph traversal 优化文献。对 Chiplet 研究而言，最有价值的是它把相似检索吞吐优化从单查询算法扩展到查询流调度，并明确揭示了吞吐和延迟之间的可量化权衡。
