# QVCache: A Query-Aware Vector Cache 解读

**一句话概述**：QVCache 将向量检索中的“重复查询”从完全相同的请求扩展为语义相近的请求，在后端向量数据库前增加一个小型内存缓存层；当新查询能在缓存中的局部向量集合里得到可信结果时，直接返回缓存结果，否则访问后端并用后端结果异步更新缓存和阈值。论文的核心贡献不是改造 HNSW 图或 DiskANN 图，而是提出一种与后端无关的查询级向量缓存机制。

## 背景

### 向量检索

向量检索把文本、图片、商品、用户行为等对象编码为高维向量，再用距离函数衡量相似性。给定查询向量 `q`，系统返回数据集中距离 `q` 最近的 `k` 个向量，这就是 `kNN`（k-nearest neighbor，k 近邻查询）。

精确 kNN 需要把查询向量和全部数据向量逐一比较。若数据集有 10 亿个向量，每个向量有 100 到 1000 个维度，单次查询需要大量随机读和距离计算，成本很高。因此生产系统通常使用 `ANN`（Approximate Nearest Neighbor，近似最近邻搜索）。ANN 允许返回结果和精确 kNN 有少量差异，用更少访问和更低延迟换取可接受的准确率。

论文使用 `recall`（召回率）衡量准确性。以 `10-recall@10` 为例，精确结果中有 10 个真实最近邻，系统返回 10 个结果；若其中 9 个是真实最近邻，召回率就是 0.9。

### 高召回率下的系统瓶颈

向量检索系统常面临三类成本：

1. **距离计算成本**：每访问一个候选向量，都要计算它与查询向量的距离。
2. **随机内存访问成本**：图索引或倒排索引访问路径不连续，硬件预取难以发挥作用。
3. **存储或远程访问成本**：大规模索引无法完全放入内存时，需要访问 SSD 或远程服务。

高召回率通常要求搜索更宽、更深。以图索引为例，系统为了减少漏掉真实近邻的概率，会扩展更多图节点和候选集合。召回率提高后，访问的节点变多，随机内存访问、SSD I/O 或网络请求都可能上升。

全内存索引可以降低延迟，但内存成本随数据集规模线性增长。磁盘型或混合型向量数据库降低了内存压力，但高召回率查询会出现随机 I/O 放大。云向量数据库还会引入网络往返延迟。QVCache 关注的正是这一成本和延迟矛盾。

### 传统缓存为何不能直接用于向量检索

传统数据库缓存通常把“请求”当作离散键。完全相同的 SQL、页面或对象 ID 再次出现时，系统直接返回缓存结果。

向量检索不满足这一前提。用户改写一句自然语言、修改一个提示词、换一种商品描述，得到的查询向量通常不完全相同。完全相等的查询向量很少重复，精确键值缓存几乎没有命中率。

但这些不同查询可能表达同一意图。论文称这种现象为 `temporal-semantic locality`（时间上的语义局部性）：在一个较短时间窗口内，语义相近的查询会重复出现。例子包括：

- 电商搜索中，用户用不同说法搜索同类商品；
- RAG 系统中，用户围绕同一主题多轮追问；
- 推荐系统中，短时间内出现相似兴趣请求；
- 季节性或热点事件导致相近查询集中出现。

QVCache 的出发点是：向量检索的重复性不是“字节完全相同”，而是“语义足够接近”。若两个查询向量足够近，它们的近邻集合可能高度重叠。系统可以利用这种重叠，把前一个查询带来的向量保存在小缓存里，后续相近查询直接在缓存中完成。

### 相似缓存

`Similarity caching`（相似缓存）允许系统用相近请求的缓存对象回答当前请求。它和普通缓存的差别是：普通缓存只接受完全相同的键，相似缓存接受距离小于阈值的对象。

难点在于阈值选择：

- 阈值太小，缓存命中少，退化成普通缓存；
- 阈值太大，缓存会用不够相似的结果回答查询，召回率下降；
- 向量空间的密度不均匀，同一个阈值在稠密区域和稀疏区域的含义不同；
- 查询分布会随时间变化，固定阈值需要反复人工调参；
- `k` 不同，结果集合大小不同，合适阈值也不同。

QVCache 的主要设计就是围绕这些阈值问题展开。

## 研究问题

论文研究的问题是：在不修改后端向量数据库索引结构的前提下，能否在前端增加一个内存受限的查询级缓存，使语义相近的向量查询直接从缓存返回，从而降低延迟和后端负载，并尽量保持后端原有召回率。

这个问题包含四个具体要求：

1. **后端无关**：不能绑定某一种索引结构。系统应能放在 DiskANN、FAISS、pgvector、Qdrant、Pinecone、SPANN 等不同后端之前。
2. **缓存命中可信**：缓存不能只追求命中率，必须判断缓存候选是否足够接近后端结果，否则会损害 recall。
3. **资源有界**：缓存查找不能变成另一个无限增长的 ANN 索引；内存和查找延迟应由缓存配置决定，而不是由完整数据集规模决定。
4. **自适应工作负载**：不同数据集、不同空间区域、不同 `k`、不同时间阶段的合适阈值不同，系统应在线学习。

论文的目标不是降低单次后端查询内部的图遍历开销，也不是改造 HNSW 或 Vamana 的节点布局。它通过让一部分查询不进入后端，减少整体服务成本。

## 总体设计

### 系统位置

QVCache 位于客户端和后端向量数据库之间。后端只需提供两个常见接口：

```text
search(Q, k) -> (ID[], distance[])
fetch(ID[])  -> Vector[]
```

`search` 返回查询向量 `Q` 的 top-k 近邻 ID 和距离。`fetch` 根据 ID 取回对应原始向量。QVCache 不要求后端暴露内部图结构、倒排列表、页面布局或缓存策略。

### 查询流程

一次查询进入 QVCache 后有两条路径。

**缓存命中路径**：

1. 查询向量先进入 QVCache。
2. QVCache 在多个内存 mini-index 中搜索候选近邻。
3. QVCache 判断候选集合是否可信。
4. 若可信，直接返回缓存候选的 ID 和距离，不访问后端。

**缓存未命中路径**：

1. QVCache 搜索缓存后认为结果不可信。
2. 查询转发到后端向量数据库。
3. 后端返回 top-k ID 和距离。
4. QVCache 立即把后端结果返回给用户。
5. QVCache 异步根据这些 ID 向后端取回向量，插入缓存。
6. QVCache 异步用后端返回的距离更新阈值。

异步填充很关键。若缓存 miss 时还要同步拉取向量、插入图索引、更新阈值，miss 延迟会高于后端延迟。QVCache 把这些工作放到后台，使 miss 路径尽量接近后端原始查询成本。

### 缓存内容

QVCache 缓存的是后端返回的向量及其 ID，不是简单缓存“某个旧查询的完整答案”。命中时，它会在缓存向量集合上执行一次小规模 ANN 搜索，再返回当前查询在缓存中的 top-k 候选。

这一点影响很大：

- 它可以组合不同历史查询带来的向量；
- 它不依赖完全重复的查询；
- 它的命中判定需要检查当前查询到缓存候选的距离是否足够小；
- 缓存本身需要一个小型向量索引，而不是普通哈希表。

## mini-index 设计

### 为什么不是一个大缓存索引

若把所有缓存向量放入一个不断增长的内存 ANN 索引，查找和删除都会变复杂。QVCache 选择把缓存拆成多个 `mini-index`（小型索引）。每个 mini-index 是一个动态 ANN 图，论文使用 FreshVamana。

FreshVamana 是支持在线插入和并发查询的动态图索引，适合缓存不断填充的场景。但 FreshVamana 的单点删除需要先标记删除，再后台 consolidation 重新整理图和回收内存。频繁删除会引入额外线程开销和内存膨胀。

QVCache 不使用细粒度删除，而是把整个 mini-index 作为淘汰单位。

### 填充策略

当一次后端查询返回 `k` 个向量时，QVCache 尽量把这 `k` 个向量放入同一个 mini-index，而不是分散到多个 mini-index。原因是这些向量来自同一次查询，未来相近查询很可能同时需要它们。放在同一个 mini-index 中，后续缓存查找更容易在少量 mini-index 内完成。

QVCache 维护 mini-index 的冷热元数据，默认使用 LRU（least recently used，最近最少使用）思想：

- 最近被命中或填充的 mini-index 被视为 hot；
- 长时间未使用的 mini-index 被视为 cold；
- 填充时优先从 hot 到 cold 找有足够空间的 mini-index；
- 若所有 mini-index 都满了，淘汰最冷的整个 mini-index，再把新向量插入其中，并把它提升为 hot。

整块淘汰避免了 FreshVamana 的细粒度删除开销，但会带来信息损失。mini-index 越大，一次淘汰丢掉的缓存向量越多。mini-index 越多，查找时可能要扫描更多索引。论文把这是一个容量分区权衡。

### 查找策略

缓存查找按 mini-index 的热度顺序进行。论文讨论三种策略：

1. `EAGER`：找到第一个可信命中后停止。延迟低，但可能漏掉其他 mini-index 中更好的候选。
2. `EXHAUSTIVE`：扫描所有 mini-index，再合并候选并重排。召回更稳，但延迟随 mini-index 数量线性增加。
3. `ADAPTIVE`：根据近期命中率切换策略。命中率高时用 EAGER，命中率低时用 EXHAUSTIVE。

若缓存总容量为 `N`，拆成 `nmini-index` 个 mini-index，每个容量为 `cmini-index`，论文给出最坏查找成本趋势：

```text
C(N) ∝ nmini-index * log(cmini-index)
```

这个式子表达的是：每查一个 mini-index 需要一次小图搜索，单个小图搜索随 mini-index 容量近似对数增长；扫描的 mini-index 越多，总成本越高。

EAGER 的意义是用热度排序减少实际扫描数。在语义局部性强的 workload 中，新近填充的 mini-index 往往也是下一批查询需要的 mini-index，因此通常扫描前一两个 mini-index 就能命中。

## 缓存命中判定

### 基本规则

QVCache 搜索缓存后得到 `k` 个候选向量及其距离。它用第 `k` 个候选，也就是候选集合里最远的那个距离，判断这组结果是否可信。

论文的命中规则可写为：

```text
dcache[k] <= (1 + D) * theta[k][R]
```

含义如下：

- `dcache[k]`：当前查询到缓存中第 k 个候选的距离。
- `R`：当前查询所在的向量空间区域。
- `theta[k][R]`：针对结果大小 `k` 和区域 `R` 学到的距离阈值。
- `D`：偏差因子，用来调节命中率和 recall 的取舍。

直观解释：若缓存中第 k 个候选已经离查询足够近，说明缓存中存在一个覆盖当前查询的局部近邻集合，可以把它当成缓存命中。若第 k 个候选太远，缓存结果可能缺少真正近邻，应访问后端。

### 为什么使用区域阈值

向量空间通常不均匀。有些区域向量很密，近邻之间距离很小；有些区域向量稀疏，最近邻也可能相隔较远。

如果使用单一全局阈值，会出现两类错误：

- 对稠密区域阈值过大，缓存会接受不够近的候选，recall 下降；
- 对稀疏区域阈值过小，缓存本来可以命中却被判为 miss，命中率下降。

QVCache 为不同空间区域维护不同阈值，称为 spatial thresholds（空间阈值）。这比全局阈值更适合非均匀向量分布。

### 为什么阈值还要依赖 k

`k` 越大，系统需要返回的结果越多。第 10 个近邻通常比第 1 个近邻远，第 100 个近邻通常更远。不同 `k` 下合适阈值不是线性关系，也不能从 `k=1` 的阈值简单推导出 `k=10` 或 `k=100` 的阈值。

QVCache 对每个出现过的 `k` 单独学习阈值，即 `theta[k][R]`。

### 偏差因子 D

`D` 是用户可调的性能-准确性旋钮：

- `D` 增大，条件放宽，cache hit ratio 上升；
- `D` 增大也可能接受更远的候选，recall 下降；
- `D` 过小，命中率下降，更多查询落到后端。

论文实验中常见有效范围是 `[0, 0.5]`，但不同数据集使用了不同设置。例如 Section 6.2 中 SIFT 和 SpaceV 使用 `D=0.25`，其他数据集使用 `D=0.075`。这说明 QVCache 虽然能学习阈值，但仍有一个需要调节的全局偏差旋钮。

## 在线阈值学习

### 学习信号

缓存 miss 时，查询会访问后端。后端返回的 top-k 结果距离可视为当前区域的真实参考。QVCache 用后端返回的第 k 个距离更新对应阈值：

```text
theta[k][R] <- (1 - alpha) * theta[k][R] + alpha * dbackend[k]
```

其中：

- `dbackend[k]` 是后端返回的第 k 个近邻距离；
- `alpha` 是适应率；
- `alpha` 越大，新查询对阈值影响越大；
- `alpha` 越小，阈值越平滑，但适应分布变化更慢。

论文称该更新受 Adam 优化器的动量思想启发，但这里不是训练神经网络，只是用指数滑动方式更新距离阈值。实验中默认 `alpha=0.9`。

### 连续学习

阈值更新发生在缓存 miss 后，且持续运行。这样可以适应非平稳 workload。例如电商系统中，夏季查询集中在空调、风扇、制冷设备，冬季查询转向取暖设备。区域访问频率和局部距离分布都会变化，阈值需要随时间调整。

### 空间区域计算

直接在原始高维空间划分区域不可行。若向量有 128 维，每维分 8 个桶，所有组合是 `8^128`，无法预分配阈值。

QVCache 用两步降低开销：

1. **PCA 降维**：PCA（Principal Component Analysis，主成分分析）把高维向量投影到较低维空间，保留主要变化方向。论文实验常用 `dreduced=16`。
2. **懒初始化**：只为实际出现过查询的区域分配阈值。没有查询到达的区域不占内存。

例如论文报告 SpaceV 上 `dreduced=16`、`nbuckets=8` 时，理论区域数是 `8^16`，但实际活跃区域最多约 50,000 个，阈值内存约 200KB。

PCA 需要离线训练投影矩阵，但不需要使用完整数据集。论文称对 SIFT 数据集用 0.1% 抽样训练 PCA 约 10 分钟，而构建对应 ANN 索引约需一周，因此额外训练成本相对较小。

## 更新与一致性边界

QVCache 主要面向查询缓存。对于原始向量的插入和删除，论文选择直接转发给后端，不在 QVCache 内部同步处理。后端更新后的向量会在后续 cache miss、cache fill 和 mini-index 淘汰中逐步反映到缓存。

这一设计简化了缓存层，但也意味着：

- QVCache 不是完整的可更新向量数据库；
- 高频更新场景需要额外一致性设计；
- 若业务要求删除后立即不可被检索，论文当前设计不足；
- 作者把直接支持向量插入和删除列为未来工作。

## 论文提出的评估框架

### 为什么需要新 workload

标准 ANN benchmark 通常给定一批固定查询，每个查询只执行一次，然后报告平均延迟和 recall。这适合评估索引本身，但不适合评估缓存。缓存依赖重复访问，若 benchmark 中没有时间局部性和语义局部性，任何查询级缓存都会显得无效。

论文提出一个可控 workload 生成框架，用来模拟不同程度的时间-语义局部性。

### 查询扰动

给定原始查询 `q`，从数据集中随机采样一个向量 `r`，生成扰动查询：

```text
q' = (1 - eta) * q + eta * r
```

`eta` 是噪声比例：

- `eta` 越小，扰动查询越接近原查询；
- `eta` 越大，扰动查询和原查询越不同；
- `eta=0.01` 时，DEEP 数据集上 top-10 邻居平均重叠约 95.12%；
- `eta` 接近 0.5 时，base query 与扰动 query 的近邻集合重叠接近 0。

该方法让查询向量不同，但仍能控制其语义相近程度。

### 滑动窗口工作集

论文把查询集合切成多个 split。每个窗口包含若干 split 的扰动副本。窗口内查询被打乱后发送给系统，并重复 `Nrepeat` 次。之后窗口以 `stride` 向前滑动，替换一部分 split。

参数含义：

- `WINDOW_SIZE`：当前工作集大小；
- `Nrepeat`：短时间内同一工作集重复出现多少次；
- `stride / WINDOW_SIZE`：工作集漂移速度；
- `Nround`：整个过程重复多少轮，用来观察长期缓存效果；
- `eta`：相近查询之间的语义距离。

这个框架能分别控制“查询是否相近”“相近查询是否集中到达”“工作集是否漂移”“缓存是否足够大”。

## 实验设置

### 实现与硬件

论文用 C++ 实现 QVCache，并提供 Python 绑定。实验环境是 Docker 容器中的 Linux 系统：

- CPU：Intel Xeon Gold 5118，2.30GHz，24 个物理核心
- 内存：376GB DDR4
- 存储：Dell Express Flash PM1725a 1.6TB NVMe SSD

该平台不是 AMD chiplet CPU。论文未报告 CCD、NUMA、L3 分片等拓扑相关指标。

### 数据集

| 数据集 | 向量数 | 维度 | 距离函数 | 查询数 |
|---|---:|---:|---|---:|
| SIFT | 1,000,000,000 | 128 | L2 | 10,000 |
| SpaceV | 100,000,000 | 100 | L2 | 29,316 |
| DEEP | 10,000,000 | 96 | L2 | 10,000 |
| GIST | 1,000,000 | 960 | L2 | 1,000 |
| GloVe | 1,000,000 | 100 | Cosine | 10,000 |

SpaceV 和 DEEP 原始数据集为 10 亿规模，论文分别取前 100M 和 10M 向量。

### 后端系统

论文使用多种后端验证后端无关性：

- DiskANN：磁盘型图 ANN 系统，作为主要后端；
- FAISS：全内存向量检索库；
- Qdrant：向量数据库；
- pgvector：PostgreSQL 向量扩展；
- Pinecone：云托管向量数据库；
- SPANN：内存-磁盘混合向量检索系统。

### 指标

论文主要报告：

- Cache hit ratio：查询中由 QVCache 直接回答的比例；
- Average hit latency：缓存命中查询的平均延迟；
- P50 latency：整体查询延迟中位数；
- Query throughput：吞吐量，单位 QPS；
- 10-recall@10 或 k-recall@k：查询准确性；
- Vectors in cache：缓存中已取回的向量数量。

论文说明未重点报告 P99，因为当缓存命中率低于 99% 时，P99 通常由 cache miss 决定，基本反映后端延迟。

## 实验结果解读

### 自适应查询感知缓存

Section 6.2 使用以下 workload 参数：

```text
Nsplit = 10
eta = 0.01
Nrepeat = 3
WINDOW_SIZE = 4
stride = 1
Nround = 1
```

QVCache 配置：

```text
alpha = 0.9
nbuckets = 8
dreduced = 16
search strategy = ADAPTIVE
cache capacity = 100,000 vectors
nmini-index = 4
cmini-index = 25,000
```

结果显示，当工作集连续保持 3 个 window step 时，cache hit ratio 逐步升高。每 3 个 step 后窗口滑动，约 25% 工作集被替换，hit ratio 出现约 25% 的下降。这符合滑动窗口生成逻辑，也说明 QVCache 的命中率主要来自工作集复用。

缓存命中查询的延迟通常在 0.1 到 1ms。结合较高命中率，QVCache 在 DiskANN 后端上把 P50 latency 降低约 60 到 300 倍。代价是 recall 有 2 到 5 个百分点下降，可通过降低 `D` 改善，但会牺牲命中率。

### 不同 k 值

论文在 SIFT 上测试 `k=1`、`k=10`、`k=100`，缓存容量随 `k` 线性缩放。

结果显示 QVCache 能适应不同 `k`，并保持较高命中率和较高 recall。`k` 越大，后端查询越贵，缓存收益越明显。论文报告 `k=100` 时 P50 latency 最多降低约 950 倍。

这一结果支撑了 `theta[k][R]` 的设计。若不为不同 `k` 独立学习阈值，大 `k` 场景会更难同时维持命中率和 recall。

### 不同数据集

Figure 5 比较了 DiskANN 单独运行和 DiskANN 加 QVCache 在五个数据集上的表现。总体规律是：

- hit ratio 随窗口内重复逐步上升，随窗口滑动周期性下降；
- hit latency 保持亚毫秒级；
- P50 latency 明显低于后端单独运行；
- throughput 随 hit ratio 上升而提高；
- recall 相对后端有轻微下降，但多数情况下保持在接近后端的水平；
- Vectors in cache 随工作集填充上升，并受缓存容量限制。

GIST 的维度为 960，缓存命中延迟高于低维数据集，但仍低于后端延迟。GIST recall 相对下降也更明显，说明高维、分布复杂的数据对空间阈值学习更有挑战。

### 不同后端

Figure 6 在 DEEP 上比较不同后端。QVCache 都只作为前端缓存，不修改后端内部实现。

主要结果：

- Pinecone 是云托管服务，后端延迟约 100ms，客户端侧 QVCache 避免网络往返后，P50 latency 最多降低约 1000 倍。
- Qdrant、SPANN、pgvector 等混合或磁盘相关后端也有明显收益，论文分别报告最高约 100 倍、300 倍、500 倍的 P50 latency 降低。
- FAISS 是全内存后端，QVCache 仍报告最高约 40 倍降低。原因是缓存只搜索小型 hot set，搜索空间远小于完整内存索引。

该实验说明 QVCache 的收益来自“绕过后端完整查询路径”，而不是只减少磁盘 I/O。即使后端全在内存中，小工作集搜索仍可能比全量索引搜索快。

### 空间阈值与全局阈值

Figure 7 在 SIFT 上比较单一全局阈值和空间阈值。

结果：

- 空间阈值下，recall 相对后端最多下降约 2 到 3 个百分点；
- 全局阈值下，recall 最高下降约 16 个百分点。

原因是全局阈值无法适应不同区域的局部密度。稠密区域需要更严格阈值，稀疏区域需要更宽松阈值。空间阈值可以在不同区域分别学习。

### mini-index 粒度

Figure 8 固定总缓存容量为 100,000 向量，在 SpaceV 上改变 mini-index 数量。

观察到：

- mini-index 数量增加，平均命中延迟上升，因为查找可能扫描更多 mini-index；
- mini-index 数量过少时，一次淘汰丢失太多向量，Vectors in cache 曲线出现大幅下跌；
- 论文选择 `nmini-index=4` 作为延迟和淘汰损失之间的折中点。

该实验对应系统设计中的核心权衡：mini-index 越细，淘汰更平滑但查找更贵；mini-index 越粗，查找索引少但淘汰破坏大。

### 缓存容量与工作集

Figure 9 在 SIFT 上分析缓存容量和 mini-index 大小。

论文估算该 workload 的窗口工作集约为 60,000 向量。若缓存容量小于工作集，频繁淘汰导致 hit ratio 明显下降。若缓存容量达到或超过工作集，hit ratio 保持较高。

`N=120,000` 时，第二轮开始后仍能保留第一轮填充的向量，hit ratio 维持更好。`N=60,000` 虽刚好容纳当前工作集，但无法保留更早一轮的向量，第二轮需要重新填充。

论文给出的配置建议是：

- 先估算 workload 的工作集大小 `w`；
- 每个 mini-index 容量可设为 `w`；
- 总容量通过增加 mini-index 数量扩展；
- 在 EAGER 策略下，实际扫描数量通常约为 1 到 2 个 mini-index，查找成本可近似为 `c * log(w)`，其中 `c` 是小常数。

### 偏差因子 D

Figure 10 在 SIFT 上改变 `D`。

结果符合预期：

- `D` 增大，hit ratio 上升；
- recall 下降；
- 当 `D` 增大到一定程度后，hit ratio 收益趋于饱和，recall 损失继续存在。

论文没有给出统一经验值，而是采用在线调节：从 0 开始，每次增加 0.025，观察 hit ratio 是否还有明显提升，直到收益不明显为止。

这说明 QVCache 不是完全免调参系统。它自动学习局部阈值，但仍需要业务根据 recall 预算设置 `D`。

### 空间划分与降维敏感性

Figure 11 在 GIST 上测试 `dreduced` 和 `nbuckets`。

GIST 维度为 960，是论文数据集中最高维的数据。实验显示：

- 把 `dreduced` 提高到 128 或更高，只带来约 3 到 4 个百分点 recall 改善，但明显降低 hit ratio；
- 把 `nbuckets` 从 8 提高到 128，平均 recall 改善约 5 个百分点，但 hit ratio 大幅下降。

原因是空间划分过细会过拟合。每个区域看到的查询太少，学到的阈值接近单个查询的局部统计，无法泛化到后续相似查询。较粗划分虽然不够精细，但能让多个相近查询共享阈值，命中率更高。

### 内存开销

Table 2 报告 SIFT 上不同 mini-index 配置的内存开销。总体趋势是：

- 内存随缓存总容量线性增长；
- mini-index 数量越多，图结构和元数据额外开销越大；
- 100,000 向量容量大约需要 100 到 200MB；
- 1M 向量容量在 SIFT 上约需 1 到 2GB；
- 阈值表内存很小，已计入表中；SpaceV 约 50,000 个阈值消耗约 200KB。

论文摘要称内存 footprint 为 megabyte-scale。结合实验，较准确表述应是：阈值元数据是 KB 到 MB 级，缓存整体在 100K 向量配置下是 100 到 200MB 级，在 1M 向量配置下可到 GB 级；相对完整内存 ANN 索引仍很小。

### 缺少时间-语义局部性时的压力测试

Section 6.10 提高扰动比例 `eta` 到 0.6，并把缓存容量设为 1M 向量以避免淘汰干扰。

`eta=0.6` 时，base query 与扰动 query 的 top-k 近邻几乎不重叠。即便如此，QVCache 的 recall 下降仍小于 4%，且 hit ratio 约在 0.75 左右。

论文给出的解释是：两两查询不相似，不代表整个 workload 的候选向量集合没有重叠。在高并发和大量查询下，不同查询可能共同引用一批热门向量。实验中总查询为 84,000，若完全无重叠且 `k=10`，理论上会插入 840,000 个向量；实际 `eta=0.4` 和 `eta=0.6` 插入少于 300,000 个向量，说明全局层面仍存在共享。

这个结果扩展了 QVCache 的适用范围：它不只依赖相邻查询高度相似，也能利用全局热门向量集合。但该结论来自合成 workload，不等同于所有真实业务都有同样重叠。

## 设计价值

### 与后端索引解耦

QVCache 不进入后端内部，不依赖 HNSW、Vamana、IVF 或树结构。只要后端能搜索和按 ID 取回向量，就可以接入。这降低了系统部署门槛，也使同一缓存思想能用于本地库、数据库扩展和云服务。

### 把缓存对象从请求键改为向量空间区域

传统缓存以请求键为单位，QVCache 以查询向量附近的局部结果集合为单位。这个转变适合自然语言和 embedding workload，因为这些 workload 的重复往往是语义层面的。

### 用后端反馈学习可信边界

QVCache 不人工指定“距离小于多少算相似”，而是利用 miss 时后端返回的第 k 个距离更新阈值。后端本身成为监督信号来源。这样可以跨数据集、跨区域、跨时间自动适应。

### 有界缓存

缓存大小、mini-index 数量、mini-index 容量都由配置限定。查找延迟随缓存工作集增长，而不随完整数据集增长。对于 10 亿规模索引，只缓存 10 万到 100 万个 hot vectors 就可能覆盖短期工作集。

## 局限

### workload 主要是合成生成

论文强调真实系统存在时间-语义局部性，但核心实验使用扰动查询和滑动窗口生成 workload。该框架可控、可复现，但它仍是合成 workload。真实业务的查询分布、会话结构、热门向量共享程度、更新频率可能不同。

因此，论文证明的是：在存在可控时间-语义局部性的条件下，QVCache 能有效；它没有充分证明所有生产 RAG、推荐或搜索 workload 都天然达到同等 hit ratio。

### recall 损失不是零

QVCache 的目标是保持接近后端的 recall，但不是严格等价后端结果。实验中常见 recall 下降为 2 到 5 个百分点，空间阈值比全局阈值好，但仍有损失。

对于严格准确性要求的场景，必须把 QVCache 的 `D`、阈值学习和业务 recall 预算一起评估。不能只看 P50 latency 降低倍数。

### P99 讨论不足

论文没有系统报告 P99，理由是命中率低于 99% 时 P99 被 miss 决定。这一解释合理，但生产系统通常正是关心尾延迟。若 cache hit latency 很低，但 miss 仍触发后端高尾延迟，用户看到的 P99 可能改善有限。

QVCache 更直接改善 P50、均值、吞吐和后端负载。若要改善 P99，需要命中率极高，或配合后端尾延迟优化。

### 更新一致性尚未解决

论文不直接处理原始向量插入和删除，只转发给后端。对删除敏感、强一致或高更新率场景，这一设计不足。

### 仍需全局偏差调参

空间阈值由系统学习，但 `D` 仍是人工控制的 recall-hit ratio 旋钮。不同数据集实验使用了不同 `D`。生产部署需要在线监控 recall 或使用影子查询评估，否则难以安全调节。

### 内存表述需要区分元数据和完整缓存

阈值表确实很小，但缓存向量和 mini-index 结构本身可达到 100MB 到 GB 级。相对完整后端索引仍然小，但不是所有配置都是“几 MB”。

### 不是 Chiplet 或 HNSW 内部优化论文

论文实验平台不是 AMD chiplet CPU，也没有使用 L3 miss、跨 CCD 访问、NUMA locality、cache line 共享等指标。它不能直接证明 HNSW 在 Chiplet CPU 上存在跨 CCD 局部性优化空间。

## 与当前 HNSW/Chiplet 研究的关系

### 可借鉴内容

QVCache 对当前 HNSW 方向有三点可借鉴。

第一，论文明确把“相似 query 在短时间内共享近邻集合”作为系统优化对象。当前 HNSW 多线程查询是 row 级并行，不同线程同时执行不同 query。若相似 query 的图访问路径或候选向量集合重叠，把相似 query 调度到同一 CCD 或同一 L3 域，可能提高本地 L3 复用。这与项目当前保留的“同一 CCD 内相似 query 并行调度缺失”方向相关。

第二，论文的 workload 生成框架可作为本地实验参考。通过 `eta` 控制 query 相似度，通过 `WINDOW_SIZE` 和 `stride` 控制工作集漂移，可以系统测试相似 query 是否导致 HNSW 访问路径重叠、cache line 复用或 L3 residency 提升。

第三，论文把工作集大小作为缓存配置核心。当前 Chiplet 平台每 CCD 约 32MiB L3；HNSW 节点块和访问路径也可按工作集估算。如果相似 query 的活跃节点集合接近或小于单 CCD L3，才有可能通过调度获得稳定收益。

### 不可直接迁移的内容

QVCache 通过缓存命中绕过后端查询。若当前研究目标是优化 hnswlib 的查询执行路径，QVCache 会改变问题本身：大量 query 不再执行 HNSW graph search，无法用于证明 HNSW 内部在 chiplet 上的优化收益。

论文的 speedup 数字也不能迁移到当前平台。40 到 1000 倍降低主要来自绕过 DiskANN、Pinecone、pgvector 等后端路径，尤其包括 SSD 或网络开销。当前 hnswlib 全内存查询的瓶颈不同，不能预期同等数量级收益。

mini-index 分区也不能直接等同于 CCD 分区。QVCache 的 mini-index 是缓存淘汰和查找粒度，不是硬件拓扑粒度。若要把 mini-index 思想改造成 per-CCD hot set，需要重新验证 recall、负载均衡、跨 CCD 请求、线程调度和缓存一致性。

### 对本项目的直接启发

适合转化为本项目实验的问题是：

```text
相似 query 是否访问相同或相近的 HNSW 第 0 层节点集合？
```

若答案为否，query-aware 调度很难带来 Chiplet L3 收益。若答案为是，下一步才是：

```text
把相似 query 放到同一 CCD，是否提高本地 L3 命中并降低延迟？
```

还需要区分两类优化：

- **请求级缓存**：像 QVCache 一样直接用缓存结果回答查询，改变后端执行次数；
- **请求级调度**：所有查询仍执行 HNSW，只改变相似 query 的执行位置和顺序。

当前 Chiplet 研究更接近第二类。QVCache 主要提供 workload locality 建模和 query-aware 系统思想，不提供直接的硬件拓扑优化证据。

## 结论

QVCache 的核心结论是：向量检索 workload 中存在语义层面的重复，前端缓存不应只做精确键匹配，而应做相似查询缓存。通过小型内存 mini-index、区域化在线阈值学习、按 `k` 区分阈值、懒初始化空间区域，QVCache 可以在有时间-语义局部性的 workload 中用较小内存换取显著 P50 latency 和吞吐收益。

论文设计的关键不是某个具体 ANN 索引，而是把“当前查询能否由缓存中的局部向量集合可靠回答”形式化为可学习的命中判定问题。实验显示，在 DiskANN、FAISS、pgvector、Qdrant、Pinecone、SPANN 等后端上，QVCache 都能通过绕过后端查询降低延迟，但通常带来小幅 recall 损失。

对当前 HNSW/Chiplet 主线，QVCache 的最大价值是提供相似 query workload 建模方法和 query-aware hot set 思路。它不能直接作为 chiplet-aware HNSW 优化证据，也不能把论文中的 40 到 1000 倍收益迁移到全内存 hnswlib 查询。后续若借鉴该论文，应先验证相似 query 在 hnswlib 中是否共享第 0 层访问节点、cache line 或 L3 工作集，再讨论 CCD 级调度。
