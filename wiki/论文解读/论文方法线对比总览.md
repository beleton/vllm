## 一、Chiplet 架构相关

### 1.1 Chiplet 任务/数据放置与缓存优化

#### CHARM: Chiplet Heterogeneity-Aware Runtime Mapping System

**会议/年份**：EuroSys 2026

**核心思想**：CHARM 是一个去中心化 chiplet-aware 运行时系统。每个 worker 线程独占一个物理核，独立读取 PMU 的 `ANY_DATA_CACHE_FILLS_FROM_SYSTEM` 事件率，与阈值比较后决定增大或减小 `spread_rate`——扩散到更多 chiplet 换取更大聚合 L3，或收紧到更少 chiplet 增强局部性。`UpdateLocation()` 通过确定性公式将唯一 worker ID 映射到无冲突的 `(chiplet, slot, core)` 三元组。同时用 coroutine 替代大量 OS 线程，降低 context switch 开销。覆盖图计算（BFS/PageRank/SSSP）、SGD、OLAP（DuckDB+TPC-H）、OLTP（ERMIA+YCSB/TPC-C）四类 workload。

**核心结论**：CHARM 在图计算上最高加速 2.81x，SGD 上 3.85x，OLAP 上 2.34x；OLTP 无收益（瓶颈在同步/提交而非 cache）。收益的充要条件是 workload 的访存瓶颈在 cache/memory 层级能被 chiplet-aware 放置改变。

**可沉淀知识**：
- **去中心化调度模式**：每个 worker 独立根据 PMU 计数器决策自身 `spread_rate`，通过确定性 ID→core 映射避免冲突。该模式可迁移到任何需要 per-worker 自适应放置的场景
- **PMU 驱动的放置决策**：`All DC Fills` 等硬件计数器可直接参与运行时策略选择，而非仅用于事后分析。对 chiplet 优化而言，PMU 信号选择应直接对应目标瓶颈（remote cache fill、local DRAM access、interconnect traffic）
- **Locality vs 聚合容量的权衡建模**：不是"永远越局部越好"，而应显式建模为受工作集大小与 L3 容量关系驱动的动态选择。这是 chiplet 优化的核心决策维度
- **应用特征筛选准则**：chiplet 放置有效的前提是访存瓶颈在 cache/memory 层级且可被放置改变。若瓶颈在同步/提交/I/O，chiplet 放置无效。这对评估 LLM 推理各阶段是否适合 chiplet 优化有直接参考意义
- **Coroutine 替代 OS 线程**：将"一个任务 = 一个 OS 线程"替换为"固定线程池 + coroutine 复用"，独立于 chiplet 放置收益，可叠加使用

#### OLAP on Modern Chiplet-Based Processors

**会议/年份**：PVLDB 2024

**核心思想**：提出 WICP（Worker per Chiplet）部署策略——每 chiplet 一个独立 worker 进程，线程只绑定本 chiplet 核心，各 worker 数据不跨 chiplet 共享地址空间。WICP 的深层机制不是"更好的线程绑定"，而是将 Worker 边界对齐到 chiplet 边界，改变了引擎层面的数据分片、执行计划和 OS 内存策略——把 WIM 下无结构的跨 chiplet cache coherence（64B 粒度、反复触发、引擎不感知）替换为显式 exchange（MB 级批量 DMA、算子边界触发一次、之后全部本地）。根据工作集大小进一步选择 WICP_Local（线程集中单 chiplet）或 WICP_Mixed（线程分散多 chiplet）。在 Presto、SingleStore、SparkSQL 上评估。

**核心结论**：SparkSQL on Intel Sapphire Rapids 最高达 6.97x speedup。WICP_Mixed 相对 WICP_Local 的分界线在单 chiplet L3 容量（32 MB）附近。

**可沉淀知识**：
- **隐式 cache coherence vs 显式 bulk transfer**：chiplet CPU 上非结构化的跨 chiplet 共享内存访问（cache coherence 协议）的代价远大于结构化批量交换。优化方向不是消除通信，而是改变通信模型：隐含→显式、细粒度→粗粒度、反复→一次性。该原理适用于任何需要跨 chiplet 数据交换的场景
- **Worker 边界作为局部性容器**：局部状态（task queue、buffer、hash table、中间结果）与 Worker 边界对齐，能实现 DRAM 局部性 + L3 局部性 + 线程-Split 映射的三层对齐。纯线程绑核无法复现，因为 Split 分配无 NUMA 感知、JVM 堆粘连单 NUMA node、引擎执行计划不感知 chiplet 拓扑
- **部署粒度不应停在 NUMA 层级**：NUMA 级放置（WIN）只能消除跨 socket DRAM 访问，触及不到 socket 内部 chiplet 间的 L3 分片和通信差异。chiplet 级放置（WICP）覆盖了同 NUMA 域内被忽略的层级
- **工作集与 L3 容量的三段判据**：< 单 chiplet L3 → Local；单 chiplet L3 < 工作集 < 聚合 L3 → Mixed；> 聚合 L3 → 两者趋同。该判据在 CHARM、Sorting 论文中均独立出现，可作为通用启发式
- **Chiplet 数作为最优部署粒度**：最优 Worker 数接近 chiplet 数（非 NUMA node 数、非 core 数）。少于 chiplet 数时仍有跨 chiplet 共享问题，多于 chiplet 数时调度/协调开销上升

#### Optimizing Sorting for Chiplet-Based CPUs

**会议/年份**：ADMS 2024

**核心思想**：将传统"register/cache/DRAM"三层内存模型显式拆为"register/local-L3/remote-L3/DRAM"四层，在此基础上对 LSB Radix-Sort 和 Comparison-Sort 做四项 chiplet-aware 改动：(1) 去掉采样，按并行度均匀切分输入；(2) 线程绑定到 chiplet 内核心，按工作集大小选择 Chiplet_Local 或 Chiplet_Mixed；(3) 分区缓冲留在本地 chiplet L3；(4) 去掉跨 NUMA data shuffling。核心洞察是：shuffling 主动把数据搬到远端主存，之后所有 pass 的访问都是远端命中；去掉 shuffling 后 cache coherence 被动处理，远端比例远低于主动搬迁。

**核心结论**：Comparison-Sort 最高 4.5x，Radix-Sort 最高 2x。Data shuffling 占 NUMA-aware 排序总时间 15%–32%。去 shuffling 后 chiplet-aware 方案的远端 chiplet cache fill 降低了 75%–80%。

**可沉淀知识**：
- **四层内存模型**：在 chiplet CPU 上必须区分 local-L3 和 remote-L3 命中（两者都叫 L3 hit，性能差数倍）。算法设计应以四层而非三层为基础
- **主动搬迁的隐性代价**：跨 chiplet 数据搬迁不仅消耗搬迁本身的带宽，更破坏源 chiplet 上已有的 L3 局部性——搬迁后数据在原 chiplet L3 中的副本失效，后续 pass 全部变成远端访问。该原理适用于任何多轮访问工作集的场景
- **多轮 pass 放大跨 chiplet 代价**：若一轮 pass 的远端访问占比不高，但数据被多轮反复扫描和重写，跨 chiplet 代价会被 pass 数放大。评估 chiplet 优化收益时需考虑访问频率放大因子
- **工作集+并行度双约束**：Chiplet_Local vs Chiplet_Mixed 的选择不仅取决于工作集大小，还取决于所需线程数是否超过单 chiplet 核心数。即使工作集可放入单 chiplet L3，若所需线程数超过单 chiplet 核数，也须使用 Chiplet_Mixed
- **"in-cache"语义分裂**：传统算法假设"in-cache = 快速"，chiplet 架构上应替换为"in-local-chiplet-cache = 快速，in-remote-chiplet-cache = 较慢"

#### P-MOSS: Scheduling Main-Memory Indexes Over NUMA Servers

**会议/年份**：SIGMOD 2026

**核心思想**：将 B+-Tree 按 key range 切成多个 `index slice`，用 Decision Transformer（GPT-1 backbone）根据 PMU token（front-end、cache、memory、interconnect 四类硬件计数器）为每个 slice 预测 worker core，slice 的 index nodes 放到该 core 本地 NUMA node。Router core 按 query predicate 路由请求到对应 worker core。策略更新时通过 `migrate_pages` 迁移 index pages。

**核心结论**：在五类 NUMA 服务器上相对 OS baseline 平均 1.92x 吞吐提升。单 slice 迁移平均 0.1s，inference 最多 1.5 分钟。在未见硬件（IBM Power）和未见数据（OSM）上仍有效。

**可沉淀知识**：
- **"数据分片 + core binding + NUMA page placement + PMU 反馈"的软件路径**：P-MOSS 不要求新硬件，在现有 chiplet/NUMA CPU 上通过纯软件机制实现四者联合优化。这是当前 vLLM CPU 推理可参考的完整技术栈设计
- **可路由数据分片是前提**：P-MOSS 有效的前提是存在稳定分片（key range）、请求可路由（predicate→slice）、分片可迁移（页面迁移成本 < 收益）。对 LLM 推理而言，需要找到同等特征的数据结构——例如 KV cache block、检索索引分片等
- **PMU token 设计方法论**：将四类硬件组件（front-end/cache/memory/interconnect）的计数器分别编码为 token，让模型学习它们与调度决策的关联。这比单看 L3 miss 更全面
- **控制面成本约束**：P-MOSS 的推理/微调周期是分钟级，页面迁移是 0.1s 级——适合 workload 变化慢、策略可复用的场景。对 per-batch 或 per-request 级调度不适用
- **Baseline 设计规范**：应同时覆盖 OS 默认、NUMA-aware 数据放置、shared-nothing core+data 放置。只与 OS 默认比较不足以证明 chiplet-aware 调度有效

#### TiNA: Tiered Network Buffer Architecture

**会议/年份**：ASPLOS 2026

**核心思想**：在 Intel Sapphire Rapids SNC 模式下，NIC DCA ways 容量随 chiplet 切分而减少——SNC 下本地 DCA ways 仅 2 MB（non-SNC 为 8 MB），长突发流量下 active mbuf size 超过本地 DCA 容量后触发 DMA leak 和 DMA bloat，SNC 反而不如 non-SNC。TiNA 建立 Local-tier 和 Remote-tier 两级网络 buffer：active mbuf size 小于本地 DCA 容量时用 Local-tier（低延迟），超出时用 Remote-tier 利用其他 chiplet 的 DCA ways（大容量），并在 TiNA-stack 中通过 sequence number 保序。

**核心结论**：相比 SNC 平均降低 mean latency 25%、tail latency 18%；相比 non-SNC 平均降低 mean latency 28%、tail latency 22%。

**可沉淀知识**：
- **"本地低延迟 vs 聚合容量"的模式在 I/O 路径同样成立**：CHARM/OLAP/Sorting 对通用 cache 工作集的 Local/Mixed 权衡，在 NIC DMA buffer 路径上以 DCA ways 容量为对象再次出现。该模式是 chiplet 架构的跨领域共性规律
- **容量溢出路径的逆转效应**：SNC 在短 burst 下更快，但 active mbuf size 超过本地 DCA ways 后 DMA leak/bloat 会逆转优势。任何"固定 local"策略都应检查容量溢出路径——当活跃工作集超出本地域容量时，locality 优势可能被溢出代价反转
- **消费速率影响放置策略分界**：processing rate 下降会使数据生命周期变长，放置策略的 break-even point 会前移。评估 chiplet 优化时不能只看数据规模，还要看消费/处理速度
- **放置决策必须在数据到达路径上完成**：TiNA 的 packet placement 必须在 NIC receive path 中完成，软件侧精确值到达时已错过时机。对 chiplet 优化的启示：调度决策的延迟必须匹配数据到达速率

### 1.2 Chiplet 通信与分区

#### Effects of Poor Workload Partitioning on System Performance for Chiplet-Based Systems

**会议/年份**：Electronics 2026

**核心思想**：将 DNN 推理表达为 task graph `G = (T, E)`，任务映射到 chiplet 的过程构成分区 `pi`。用 partitioning quality `Q`（0% = 随机映射，100% = 最优映射）控制系统实验，观察跨 chiplet latency、traffic、congestion、throughput 和 energy efficiency 的变化。核心发现：poor partitioning 下，强通信任务被分散到远距离 chiplet，跨 chiplet edge cut 增加，NoI 拥塞随 chiplet 数量非线性放大——16-chiplet poor partitioning 达到 320% congestion，85% 执行时间花在跨 chiplet 通信上。

**核心结论**：8-chiplet ResNet-50 下，Q=100% 相对 Q=0% 的 throughput 提升 8.75x（28→245 images/s），inter-chiplet traffic 降低 87.4%。16-chiplet 系统需要 Q≥95% 才能可持续运行。

**可沉淀知识**：
- **chiplet 优化前先把 workload 表达为通信图**：任务节点、通信边权、关键路径、可 co-location 的强通信边。若通信图可被 co-location 降低 edge cut，partitioning 才有优化空间
- **chiplet 数量增加后通信代价非线性放大**：2-chiplet 和 4-chiplet 下 naive mapping 尚可运行，8+ chiplet 下可能进入拥塞崩溃。当前 EPYC 9745 的 8 CCD/socket 已处于需要关注通信图的规模
- **多指标评估体系**：不能只看平均 latency，应同时报告 traffic share、link utilization、communication overhead、throughput 和 energy。单一 L3 miss rate 不足以解释系统级退化
- **co-location 的收益上限很高，但对非通信密集型 workload 有限**：对 DNN/tensor 等 structured communication workload 有效，对 memory-bound 或 control-flow dominated workload 可能仅 1.5x–2x

#### MEMPLEX: A Memory System with Replication and Migration of Data

**会议/年份**：ICS 2025

**核心思想**：在多 chiplet NUMA + HBM/DDR 系统中，每个 HBM node 的一小部分（默认 1/16）作为该 chiplet 私有的 sectored DRAM cache，剩余与外部 DDR 组成 shared flat address space。访问路径上先按 cache line 粒度从远端复制请求数据到本地 DRAM cache；DRAM cache eviction 时，根据 sector 访问热度（Access Counter）和迁移流量预算（remote access counter，`Om = 2*Nall - Nvalid - Ndirty + 1`）决定是否将完整 4KB sector 迁移到本地 HBM。复制降低首次访问成本，迁移处理反复访问的数据。

**核心结论**：4-chiplet 系统平均 IPC speedup 5%，local HBM 访问占比从 61% 提升到 90%，remote traffic 降低 80%，dynamic memory energy 降低 44%。16-chiplet 系统平均 speedup 增至 10%。DRAM Cache-Only（全部 HBM 当 cache）平均仅 1% 收益。

**可沉淀知识**：
- **复制与迁移分层**：cache line 级复制降低首次访问成本，sector 级迁移处理反复访问数据。对 chiplet 软件优化的启示：不应在首次访问时就决定数据归属，而应让运行时累积访问统计后再决定
- **迁移成本必须显式计入远端流量模型**：MEMPLEX 不用"访问热度"单一判据，而是用 `Om` + remote access counter 联合约束迁移决策。软件侧 chiplet 调度也应考虑策略调整本身产生的数据搬迁开销
- **全部当 cache 不一定是好策略**：DRAM Cache-Only（全部 HBM 当 cache）平均仅 1% 收益，远低于 MEMPLEX 的 5%。说明"牺牲主存容量来换取更大 cache"不是无条件的更优策略，需按容量比例权衡
- **远端访问来源需拆分统计**：应区分 local HBM、remote HBM、external DDR（对应 AMD EPYC 上本地 DRAM、同 socket 其他 CCD DRAM、其他 socket DRAM），而非只看总 memory traffic
- **硬件依赖性**：MEMPLEX 需要 DCC、DCTA、remap table 等硬件支持，不可直接在软件侧复现。但分层复制/迁移的方法论和迁移成本模型可迁移

#### A Comprehensive Literature Review of AI-Driven Application Mapping and Scheduling Techniques for NoC Systems

**核心思想**：综述将 NoC application mapping 分为 static、dynamic、hybrid、machine learning-based 四类。提出 chiplet fabric 需要 `cluster → chiplet → PE` 的层次化映射语言。指出学习型映射必须检查训练成本、推理延迟、状态观测成本、故障泛化和约束满足。

### 1.3 硬件基线

#### AMD EPYC Rome 与 Intel Cascade Lake SP 内存性能

**会议/年份**：ICPE 2022

**核心思想**：用 `BenchIT/x86-membench` 的 pointer-chasing 和 STREAM 系统测量 Rome（chiplet 架构，CCD+CCX+I/O-die）与 CLX（单片 mesh 架构）的 cache/NUMA/跨 socket 延迟与带宽。Rome 上访问层级至少需区分：CCX 本地 L3（~19.5 ns）、同 CCD 另一 CCX（~102–126 ns）、同 socket 其他 NUMA node（~115–152 ns）、其他 socket（~203–218 ns）。部分远端缓存访问已慢于本地主存（~110 ns）。

**核心结论**：Rome 的本地 L3 延迟更低、整 socket 带宽更高（8 通道 vs 6 通道），但访问层级更多、远端代价更大、更依赖线程绑定；CLX 远端访问额外代价更小（跨 SNC 仅 +6 ns），适合更多核心共享数据的场景。

**可沉淀知识**：
- **chiplet 架构的延迟分层是 chiplet-aware 方法成立的硬件前提**：同 socket 内延迟从 19.5 ns（本地 L3）到 152 ns（远端 NUMA），差异近 8x。若延迟分层不存在（如 ARM Graviton 3 单 compute chiplet），chiplet 优化无意义
- **"先测层级延迟和来源，再决定优化粒度"的方法**：不能直接复用 Rome 的具体数值，但可复用测量方法——先确定当前平台的延迟/带宽分层，再判断优化应落在哪一层
- **CCX/L3 是真正的低延迟共享域**：对 Rome 系 chiplet CPU，真正低延迟共享 L3 的粒度只有 CCX 内 4 个核（对应后续 Milan/Genoa/Bergamo 的 CCD 内 8/16 核共享 32 MiB L3）。跨 CCD 的 L3 访问延迟可接近甚至超过本地主存
- **线程绑定和数据放置是一级问题而非可选优化**：论文明确指出即使在单 NUMA 暴露下也应显式 pinning，避免隐藏的远端延迟

### 1.4 微架构诊断

#### The Fake-Busy and True-Idle Problems of Running Graph Applications on Chiplet-Based Multi-Cores

**会议/年份**：ISPASS 2025

**核心思想**：区分图应用在 chiplet OoO 多核上的两种 pipeline 低效状态——fake-busy（投机跳过 branch-resolving load 填满 ROB/LQ）和 true-idle（指令等待 branch-load，ROB 里堆 stalled instructions）。通过 gem5 仿真和 ROB/LQ 容量敏感性实验（352→176 entries），发现减少 50% ROB 容量平均只增加 12.3% 执行时间，排除极端 benchmark 后仅 4.3%，说明大量 pipeline 资源被无效占用。

**可沉淀知识**：
- **性能归因不能只看队列利用率**：ROB/LQ 满不代表在做有效工作。对分支密集、load 依赖强的不规则 workload，需区分有效执行、投机占用和无效占用。这对 chiplet 架构上评估长延迟 off-chiplet 访问的影响有方法论价值
- **分支预测质量与 chiplet 延迟的交互**：长延迟 off-chiplet load + 分支误判 = 大量投机指令填充 pipeline = 真正的并行度被稀释。该效应在 attention 等 streaming kernel 上不显著，但在图计算、KV cache 随机访问等场景可能突出
- **该论文主要作为诊断框架参考**，不提供放置算法或调度策略

### 1.5 CPU LLM Serving 框架

#### Sandwich: Separating Prefill-Decode Compilation for Efficient CPU LLM Serving

**核心思想**：prefill（计算密集，IPC 高）和 decode（memory-bound，共享资源竞争严重）应使用不同的 service configuration（模型分区 + core utilization 的组合）。用 TopoTree 抽象硬件拓扑——叶子是 processing unit，非叶子表示共享资源。通过 `group(n,t,d)` 补全系统工具未暴露的共享层级（如 Kunpeng 每 4 核共享 L3-Tag），通过 `remove(n,d)` 枚举减少共享结构竞争的 core 子集。prefill 侧对动态 shape GEMM 做 computation slice + polymerization 联合编译优化；decode 侧用 trace latency simulation 从 TopoTree 候选配置中选择。

**核心结论**：相对 vLLM 可支持最高 4.45x 更严格的 SLO，token generation throughput 平均提升 2.01x。但收益来自 communication、service configuration、kernel tuning、split-k 的组合，不能单独归因于绑核。

**可沉淀知识**：
- **prefill 和 decode 不应共用同一执行计划**：两个阶段的计算/访存特征不同，优化对象和 placement 策略可能不同。这对当前 attention-only 和 PD_Test 的扩展方向有直接指导意义
- **decode 不一定适合使用所有 cores**：active core 数量和物理位置会影响 memory controller、LLC tag 等共享资源竞争。该结论打破了"更多核心=更优"的直觉
- **硬件拓扑可抽象为树，用 group/remove 枚举搜索空间**：该方法适合在现有 CPU 上离线搜索最优 core utilization 和 model partition，不需要新硬件
- **离线 tuning 成本需纳入可行性评估**：kernel tuning 平均约 3 小时，service configuration tuning 平均约 22 分钟。若模型、平台或请求分布频繁变化，需重新评估 tuning 成本

---

#### ArcLight: Many-Core CPU NUMA-Aware LLM Inference

**核心思想**：在 many-core ARM CPU 上从三个层面联合做 NUMA-aware 设计：(1) 内存侧：为每个 NUMA node 单独分配本地 buffer，activation 用双缓冲按 layer parity 交替；(2) 线程侧：引入可拆分/合并的 thread group，区分 local barrier 与 global barrier；(3) 计算侧：跨 NUMA tensor parallel（Wq/Wk/Wv 按 head row-partition，Wo/Wdown column-partition），Scatter/Gather 切换并行子图，异步子图执行减少线程空转。

**核心结论**：相对 llama.cpp 最高 46% 吞吐提升。prefill 收益小于 decode（prefill 偏 compute-bound，TP 主要缓解 memory access wall）。

**可沉淀知识**：
- **locality 不能只依赖 OS first-touch**：框架需要显式控制 tensor/buffer 放置。仅把线程均匀分散到各 NUMA node 但不能保证 tensor 绑定，计算位置与数据位置仍会失配
- **线程组织、内存放置和计算图切分要一起设计**：不是只改绑核或只改内存分配的"单点优化"
- **prefill 和 decode 的收益预期需分开评估**：论文明确给出 prefill 优势更小的条件化结果，该规律对当前 chiplet 研究中区分 prefill/decode 有参考价值
- **粒度是 NUMA node 和整模型图执行**，不是 CCD/L3 slice 或 attention kernel 内任务分片。论文平台是 ARM Kunpeng-920，不是 x86/AMD EPYC

### 1.6 GPU Attention 拓扑映射

#### GPU Attention NUMA Effects on Chiplet-Based GPUs

**核心思想**：将共享同一组 K/V 的 workgroup 集合定义为 ACC（Attention Compute Cluster）。在 MHA 中一个 head 对应一个 ACC，在 GQA 中共享 K/V 的 query heads 组成一个 ACC。通过 Swizzled Head-first Mapping 让同一 ACC 尽量落在同一 XCD，提高本地 L2 复用并减少重复 HBM 读取。不改 attention 数学，只改 workgroup ID 到 (batch, head, block) 的映射逻辑。

**核心结论**：MHA H_Q=128、N_CTX=128K 时 Swizzled Head-first 保持 90%–96% L2 hit rate，Naive 方法大幅下降。GQA 下 KV heads 数与 XCD 数匹配时 Swizzled Block-first 也强。

**可沉淀知识**：
- **共享工作集驱动映射抽象**：先识别"谁共享数据"，再设计映射。GPU 中的 ACC 可对应 CPU prefill 中共享同一 `kv_head` 或共享重叠 K/V 前缀的一组任务。这是 chiplet 优化的通用方法论——先定义共享工作集单元，再将单元与硬件局部域对齐
- **映射策略需同时考虑模型分组结构与硬件局部域数量**：最优映射不是固定的，取决于"模型维度（head 数、group 数）"与"硬件维度（CCD 数、XCD 数）"是否匹配
- **不改算法数学、只改任务映射即可获得缓存复用收益**：该方法论适用于任何"多任务共享同一只读数据集"的场景

## 二、HNSW 相关

### 2.1 HNSW 原论文

**核心思想**：提出 Hierarchical Navigable Small World——用多层近邻图组织向量。节点按指数衰减概率分布随机分配最高层，上层节点少、边长（负责大跨步导航），第 0 层包含全量节点、边短（负责局部精细搜索）。查询从顶层入口点贪婪下探，第 0 层用 efSearch 控制宽度的 best-first search。插入时用启发式邻居选择（选方向多样化的邻居，避免多边挤在同一方向）保证跨簇连通性。搜索复杂度从 NSW 的 $O((\log N)^2)$ 降到 $O(\log N)$。

**核心结论**：HNSW 在 SIFT/GloVe/CoPhIR/DEEP 等多个向量数据集上优于 FLANN、Annoy、VP-tree。与 Faiss OPQ+IMI+PQ 相比搜索更快、精度更高但内存更大。

**可沉淀知识**：
- **HNSW 图结构天然适合分层放置**：上层导航图小而访问频繁（适合 per-CCD replica），第 0 层邻接表和向量决定主要访存量（适合 trace-guided layout），入口点是全局瓶颈（必须所有查询可达）
- **层次化访问热度差异**：上层热、下层冷——热结构可复制到各 chiplet 本地，冷大图按 partition 分片。该思想与 HM-ANN 的"热上层放 fast memory、冷 L0 放 slow memory"一致
- **图搜索的访存模式是随机跳跃**：沿近邻边遍历，每步访问不同节点。在 chiplet CPU 上，若图数据跨 CCD 分布，每次跳转可能触发跨 CCD L3 访问。这是 chiplet-aware HNSW 优化的潜在杠杆点
- **参数系统是实验必须控制的变量**：M、Mmax0、efConstruction、efSearch 必须固定或系统扫描，不能在不同配置间直接比较硬件布局收益

---

### 2.2 Graph-Based Vector Search 实验评估

**核心思想**：将 graph-based ANN 方法归纳为五类设计范式——Seed Selection、Incremental Insertion、Neighborhood Propagation、Neighborhood Diversification、Divide-and-Conquer。在 7 个真实数据集和最高 10 亿向量规模上评估 12 种方法，结论是 HNSW、Vamana、ELPIS 属于综合表现最强的方法组，但方法排名受数据规模、recall 目标、图构建方式和实现优化影响。

**核心结论**：邻域多样化（ND）是核心变量——RND 和 MOND 表现最好；数据集难度（LID/LRC）会改变方法排序；实现优化（如 contiguous block allocation）会改变同类方法的性能排序。

**可沉淀知识**：
- **HNSW 是强 baseline 但不是唯一 baseline**：chiplet-aware HNSW 实验应至少包含 HNSW 优化实现、Vamana、ELPIS 作为对照，只优于未优化 HNSW 不足以说明 chiplet 优化有效
- **ND、SS、DC 是必须控制的算法变量**：chiplet-aware layout 的收益应证明相对普通 ND/SS/DC 优化仍有增量
- **数据集难度指标 LID/LRC** 可用于选择 HNSW 实验数据集，避免只在简单数据上得出过强结论
- **图 ANN 性能不能只归因于搜索阶段**：seed selection、图构建、邻域多样化、分区策略和内存布局均影响最终曲线。chiplet 实验需分别控制这些变量

---

### 2.3 Graph Reordering for Cache-Efficient Near Neighbor Search

**核心思想**：不改变 HNSW 图结构和搜索算法，只通过图重排序（graph reordering）改变节点在内存中的排列，使 beam search 中常被连续访问的节点在内存中更接近。比较 Gorder（优化邻域重叠）、RCM（降低邻接矩阵带宽）和多种轻量级 degree/hub 类方法。HNSW 层次搜索只占查询时间 2.9%±1.9%，主要访问模式来自第 0 层 beam search。

**核心结论**：Gorder 和 RCM 在 SIFT100M/DEEP100M 上稳定带来 10%–40% 查询加速。Gorder 将 SIFT100M 的 L3 miss 从 6.5% 降至 4.0%，TLB miss 从 3.85% 降至 2.14%。轻量级 degree/hub 方法不稳定，部分数据集会退化。重排序成本低于 HNSW 图构建（Gorder 快约 10x）。

**可沉淀知识**：
- **HNSW 对内存布局和 cache miss 敏感——可被纯软件布局优化改善**：仅改变节点编号就能在不改 recall 的情况下降低查询延迟。这是 chiplet-aware HNSW 的基础前提——若普通布局优化已无收益空间，chiplet 级布局更难有效
- **chiplet-aware HNSW 实验必须把普通 graph reordering 作为强 baseline**：若 chiplet-aware layout 只优于原始插入顺序，而不优于 Gorder/RCM 或 trace-guided 重排序，不能说明 CCD/L3 拓扑感知策略有独立价值
- **单向量存储越小，图局部性收益可能越强**：使用 PQ、SQ、float16 或低维 embedding 时，应单独评估压缩后的节点布局收益
- **缓存层次指标模板**：L1/L2/L3 miss、TLB miss、节点遍历与距离计算代码段 cache miss——后续 Zen 平台应补充 L3 miss source、IBS load latency 等来源级指标

---

### 2.4 Data Ordering and Intrinsic Dimensionality 对 HNSW Recall 的影响

**核心思想**：固定 HNSW 参数（M=16, efConstruction=128），研究数据内在维度和插入顺序对 recall 的影响。合成向量实验显示内在维度升高（接近 full rank）时 recall 约下降 50%。在 7 个标准检索数据集和 16 个 embedding 模型上，按 descending LID（先插入高 LID 向量）的 recall@10 平均高于 ascending LID 2.6–6.2 个百分点，最大差异 12.8 个百分点。真实电商图像数据中按商品类别形成的非随机插入顺序也会改变 recall。

**核心结论**：HNSW 的 recall 不是只由 M、efConstruction、efSearch 决定——数据内在维度、插入顺序和局部几何结构同样显著影响图质量。提高 efSearch 不能完全消除构图阶段由插入顺序造成的结构差异。

**可沉淀知识**：
- **chiplet-aware HNSW 的任何分片/复制/布局改造都可能改变 recall**：如果改造涉及图构建、节点排列或入口点选择，必须同时报告 recall@k 变化。只测查询延迟而不控制构图条件，可能把图质量差异误判为硬件布局差异
- **增量建库的插入顺序可能与 LID 或局部簇结构相关**：若按类别、时间或业务批次增量插入，后续性能评估应同时记录插入顺序
- **LID 可作为数据集难度的预判指标**：高 LID 数据集需要更大 M 或 efConstruction 才能达到相同 recall。chiplet 实验中若使用不同数据集，需先标定 LID 分布
- **模型排行榜在 exact KNN 和 HNSW 近似检索下可能不同**：选 embedding 模型时不能只依赖 exact KNN 评测

---

### 2.5 HM-ANN: Heterogeneous Memory ANN

**核心思想**：面向单机 DRAM（96GB）+ Optane PMM（1.5TB）异构内存的十亿级 ANN 检索。将 HNSW 式分层图改造为适配快慢内存的结构：(1) 用 top-down insertion + bottom-up hub promotion（按第 0 层度数选择高阶 hub 提升到上层）替代随机层级；(2) 热上层图放 fast memory（DRAM），冷第 0 层图和全量向量放 slow memory（PMM）；(3) L1 搜索多入口 + L0 并行 multi-start 1-greedy search；(4) 性能模型选参。

**核心结论**：BIGANN/DEEP1B 上相同 accuracy 下比 HNSW 快 2x、比 NSG 快 5.8x。PMM 随机访问延迟约 DRAM 的 3x、带宽约 1/6——此差异是 HM-ANN 的前提。

**可沉淀知识**：
- **"热导航结构靠近计算，冷大图放远"的思想**：可迁移到 per-CCD navigator replica、hot hub replica 或第 0 层 cold graph partition 设计
- **Hub 节点的识别方法**：用第 0 层度数、访问频率或 trace 热度选择需要复制或靠近本地的 HNSW 节点
- **多入口并行搜索**：可减少单一路径的慢访问，但需固定 recall 并报告候选合并成本
- **CCD 本地 L3 不是 PMM/DRAM 的等价物**：PMM 与 DRAM 是 3x 延迟差、可显式管理的大容量层；CCD 本地 L3 与远端 CCD L3 的差异更小（~24 ns vs ~106 ns），且不可显式分配。HM-ANN 的 fast/slow placement 不能原样实现，但方法论可迁移
- **Bottom-up promotion 改变了图结构**：若用于 chiplet 研究，必须区分"图质量改善"与"硬件局部性改善"

---

### 2.6 d-HNSW: Disaggregated Memory HNSW

**核心思想**：在 RDMA-based disaggregated memory 系统中，将 HNSW 拆成两级：(1) meta-HNSW（从全量数据均匀采样 500 向量，构建三层轻量索引，SIFT1M 上仅 0.37MB）缓存在 compute pool，做粗粒度 partition 选择；(2) sub-HNSW 和原始向量放在 memory pool。加上 RDMA-friendly layout（连续内存 + overflow space）、query-aware batched loading（batch 内相同 sub-HNSW 去重）、doorbell batching 减少 RDMA round trips。

**核心结论**：SIFT1M/GIST1M 上相对 naive d-HNSW 最高降低 117x/121x 查询延迟。主要收益来自将逐节点远端读取转化为 partition 级批量 RDMA 读取（network round trips 从 3.547 降到 4.75e-3）。

**可沉淀知识**：
- **HNSW 在远端内存场景下应避免逐节点远端读取**：可用轻量代表索引先做 partition 选择，再批量读取候选 partition。该模式可对应 chiplet CPU 上"meta-HNSW 放本地 L3/DRAM + sub-HNSW 按 CCD 分片放本地 DRAM + 跨 CCD 批量读取"的设计
- **batch 内共享访问去重**：批量查询中，不同 query 可能需要相同 sub-HNSW，显式去重可减少重复跨域读取。对 LLM serving 中 batch prefill 共享 K/V 的场景有类比价值
- **索引布局应按远端读取粒度设计**：不能只按本地指针结构序列化，需考虑跨域传输的连续性和批量效率
- **d-HNSW 瓶颈是 RDMA network round trip**，不是 CCD 间访问或 L3 miss——不能直接外推 117x/121x 结论到 chiplet CPU。但"分层访问 + partition 粒度批量传输"的方法论可迁移

## 三、其他

### A CPU-Centric Perspective on Agentic AI

**核心思想**：Agentic AI 在 LLM 推理之外引入了大量 CPU 工具处理——检索、摘要、代码执行、Web/API 访问等。论文在 Intel Emerald Rapids + NVIDIA B200 上系统测量 5 类 Agentic workload，发现 CPU 工具处理可占端到端延迟高达 90.6%（Haystack ENNS 检索），大 batch 下 CPU 能耗占比可达 44%。提出两种调度优化：CGAM（micro-batching，将 batch 拆为 Bcap 大小的 micro-batch 顺序执行）降低 P50 延迟最高 2.1x；MAWS（CPU-heavy 用 multi-processing、LLM-heavy 用 multi-threading）降低异构混合负载 P99 延迟。

**核心结论**：Agentic AI 的性能瓶颈不能只从 GPU kernel 视角分析。CPU 工具阶段的三类限制——cache coherence、synchronization、over-subscription——在大 batch 下会主导 CPU 侧扩展性。LangChain multi-processing 只比 multi-threading 快 1.6x（非 128x），原因是 GIL 在三个关键阶段（URL 抓取、LexRank 子进程、LLM HTTP 推理）都被绕开。

**可沉淀知识**：
- **Agent/RAG/Tool sandbox 场景中 CPU 工具阶段是一等 workload**：若当前研究扩展到 Agentic AI，需把 CPU 工具处理（检索、摘要、代码执行）作为 chiplet 优化的候选对象，而不仅是 attention kernel
- **CPU 工具的并行方式选择准则**：大共享语料检索→multi-threading；CPU-bound 且内存可复制→multi-processing。该准则对 chiplet 场景下不同工具阶段的 worker 部署有参考价值
- **batch size 的吞吐增益递减判据**：用 `T(B)/T(B/2)` 判断吞吐增益是否进入低收益区（λ=1.1），避免盲目增大 batch
- **异构请求分类**：CPU-heavy 与 LLM-heavy 请求应使用不同的 CPU 资源策略——前者保留并行资源，后者降低 CPU footprint。对 chiplet 调度的启示：不同请求类型可能需要不同 placement 策略
- **该论文没有验证 chiplet/CCD 局部性**：不能直接支持"Agentic AI 适合 chiplet L3 优化"的结论。需要新增实验测量 CPU 工具阶段的 LLC miss、remote NUMA/CCD access、IPC 等指标

## 四、专题：Chiplet 三篇论文对照与 Attention 结论验证

### 4.1 三篇论文的核心对照

| 维度 | OLAP (PVLDB'24) | Sorting (ADMS'24) | CHARM (EuroSys'26) |
|------|-----------------|-------------------|---------------------|
| 优化对象 | OLAP worker 部署 | 排序算法流程 | 通用并行任务调度 |
| 关键机制 | WICP 独立进程切断 coherence | 去 shuffling + Local/Mixed | PMU 驱动 spread_rate |
| 应用特征 | 表扫描/Join/Repartition 多轮重读 | 多轮 pass 反复扫描/重写数据 | 图计算不规则访问 + SGD 大工作集 |
| 最高 speedup | 6.97x (SparkSQL) | 4.5x (Comparison-Sort) | 3.85x (SGD) |
| 跨 chiplet 开销占比 | 34% (SparkSQL 互联拥塞) | 20%–32% (shuffling) | 百万次量级 remote chiplet access |

### 4.2 三条共性规律

**共性 1：L3 局部性 vs 聚合容量的权衡是核心决策维度**

三篇论文的优化问题可归结为同一权衡：按 chiplet 收紧任务获更低访问延迟（Local），还是跨 chiplet 分散任务获更大聚合缓存（Mixed）。

- OLAP Fig.10：数据 < 32MB（单 chiplet L3）时 WICP_Local 带宽更高；超过后 WICP_Mixed 更优
- Sorting Fig.3/Fig.13：相同的 Local vs Mixed 边界在 32MB 处出现
- CHARM Algorithm 1：`spread_rate` 的增减直接由 remote cache access rate 驱动，本质是同一决策

**共性 2：避免跨 chiplet 数据移动是共同优化方向**

- OLAP：WICP 强制数据局部性，缓解 SparkSQL 下 34% 时间的互联拥塞
- Sorting：去掉 data shuffling 是 ablation 中贡献最大的优化项
- CHARM：chiplet-aware 调度将 remote chiplet access 降低 1–3 个数量级

**共性 3：跨 chiplet 数据访问开销在关键路径上占比显著**

三种 workload 前提相同：存在显著的跨 chiplet 数据访问开销，可通过改变 chiplet 级放置来消除。形式分为两类：

1. **同一份只读数据被多个 chiplet 上的线程反复访问**（OLAP 表扫描被 join 重读、排序多轮 pass、图遍历邻居反复触碰）。硬件 cache coherence 在各 chiplet L3 中复制多份，副本占用 L3 容量，coherence 消息占用互联带宽。Chiplet 放置通过限制"谁读哪份数据"消除副本扩散
2. **数据在不同 chiplet 之间主动搬迁**（排序 shuffling、OLAP WIM 下跨 chiplet 不均分配）。搬迁后原 chiplet L3 中副本失效，后续访问全部变成远端

**"working set 在 L3 容量边界附近"不是 chiplet 优化的必要条件**。OLAP 的 coherence 消除和 Sorting 的 shuffling 消除在 L3 边界之外仍然有效。L3 容量边界只决定 Local vs Mixed 的二阶选择。判断 workload 是否值得做 chiplet 优化的主条件是跨 chiplet 数据访问开销在关键路径上的占比。

### 4.3 Chiplet 优化适用性筛选框架（三筛法 + 两条补筛）

**第一筛：关键路径上的跨域访问占比**。用 PCM/PMU 测量目标阶段的 demand fill 来源分布。跨 chiplet 访问占比有意义的份额时，chiplet 级放置才有杠杆。三篇论文 workload 中跨 chiplet 通信占 15%–34%，attention 仅 0.14%–0.81%。

**第二筛：瓶颈是否能被放置改变**。跨 chiplet 访问占比高不代表放置一定有效。需确认访问来自"数据与处理它的线程不在同一 chiplet"，且软件有权改变任务或数据的位置。

**第三筛：复用与容量敏感性**。用 CAT/STREAM/工作集 sweep 判断目标数据是否依赖 L3 复用。若数据只是 streaming 通过 L3（如 Attention K/V），改善 L3 occupancy 或 L3 miss/task 可能不改变端到端延迟。

**第四筛：并行度与调度补空能力**。本地化会减少可参与执行的核心范围。若局部化降低并行度、负载均衡或跨组补空能力，locality 收益可能被调度损失抵消。

**第五筛：控制面成本**。CHARM 为 500ms 级 PMU 调整，P-MOSS 推理/微调为分钟级，Sandwich tuning 为离线小时级。控制周期必须匹配 workload phase 长度。

### 4.4 Attention 与三篇论文应用的对比

| 特征 | OLAP/Sorting/Graph | CPU Attention |
|------|-------------------|---------------|
| Working set 与 L3 关系 | 在 L3 容量边界附近 | fit in L2（head 维度）或 streaming 无复用（seq 维度） |
| 数据复用模式 | 同一数据被多次访问，以只读共享为主。复用放大 coherence 代价 | K/V streaming access，每元素只读一次。无复用意味着 coherence 副本扩散的代价不被放大 |
| 副本扩散后果 | 多 chiplet L3 中同时驻留同一数据副本，挤占本地 L3，coherence 消息占用互联带宽 | 副本存在但影响小——每 cache line 读一次后成为冷数据 |
| L3 容量敏感度 | 高——复用期间数据必须留 L3 | 低——CAT 0001 将 L3 压到 1/16 仅退化 0.03%–2.11% |
| 优化杠杆点 | 数据布局 + 任务放置 → 控制 coherence 流量与 L3 命中率 | 内存带宽/计算吞吐 → L3 命中率和 coherence 流量不是瓶颈 |

### 4.5 并行度与工作集的共同约束

三篇论文没有把 Local vs Mixed 简化为"只看工作集是否小于单 chiplet L3"。工作集大小决定本地 L3 与聚合 L3 的取舍；所需线程数或任务并行度决定单 chiplet 是否有足够核心承载任务。

- Sorting：双条件——输入可放入单 chiplet L3 且所需线程数不超过单 chiplet 核数 → Local；线程数超过或输入超过单 chiplet L3 → Mixed
- OLAP：WICP_Local 与 WICP_Mixed 使用相同 core 数，只改变 core 在 chiplet 内集中还是跨 chiplet 分散
- CHARM：`UpdateLocation` 显式检查 `spread_rate` 覆盖的物理核心数是否足够容纳全部 worker thread

对小工作集、计算密集型任务，应先看所需并行度：若单 chiplet 核心数不足以提供目标计算吞吐，即使工作集可放入单 chiplet L3，也需扩到更多 chiplet。三篇论文的实测收益不能直接外推到 compute-bound kernel——因为其收益主要来自降低跨 chiplet 数据访问。

### 4.6 对寻找新研究方向的启示

**先找到跨 chiplet 数据访问在关键路径上的环节，再考虑 chiplet 级放置优化。** Attention 上行不通不代表其他环节不行。后续扫描方向：

- **Decode**：L3 Miss% 远高于 prefill（96.51% vs 49.43%），但需 CAT 实验确认是否对 L3 容量不敏感
- **KV cache 管理 / 分布式 prefill 数据交换**：涉及跨 rank 或跨 chiplet 数据搬迁——若搬迁 volume 使跨 chiplet 通信成为可观测瓶颈，chiplet-aware 放置可能适用
- **Whole-model serving 全链路**：线程池调度、内存分配、batch 拼装等环节可能另有跨 chiplet 通信的环节，需 full-stack profiling
- **Agentic AI 工具阶段**：ENNS 检索、LexRank 摘要、Bash/Python 执行——这些 CPU 工具可能有不同访存特征

## 五、跨主题的共同规律

### 5.1 "本地低延迟 vs 聚合容量"是 Chiplet 架构的跨领域共性模式

该模式在以下论文中独立出现：

| 论文 | 本地域 | 聚合域 | 切换信号 | 时间尺度 |
|------|--------|--------|----------|----------|
| CHARM | 单 chiplet L3 | 多 chiplet 聚合 L3 | remote cache fill PMU | 500ms |
| OLAP | WICP_Local | WICP_Mixed | 工作集 vs 单 chiplet L3 | 静态部署 |
| Sorting | Chiplet_Local | Chiplet_Mixed | 输入规模与线程数 | 静态/半静态 |
| TiNA | Local-tier DCA | Remote-tier DCA | active mbuf size | 微秒级 |
| HM-ANN | Fast memory (DRAM) | Slow memory (PMM) | hub 度数 + 内存容量 | 构建时确定 |

该模式不能简化为"越本地越好"——当工作集超过本地容量、并行度超过本地域核心数、或共享资源竞争超过计算收益时，需要扩大或改变执行域。

### 5.2 通信图与共享工作集

| 论文 | 图节点 | 边或共享对象 | 优化目标 |
|------|--------|-------------|----------|
| GPU Attention | workgroup | 共享 K/V 的 ACC | 提高同 XCD L2 复用 |
| Effects | DNN task | task graph communication edge | 降低 edge cut 和 NoI congestion |
| P-MOSS | index slice / worker core | query predicate → key range | 请求路由与数据本地化 |
| OLAP | worker / fragment | scan、join、repartition 数据流 | 消除 coherence 与跨 chiplet 访问 |

共同点：先定义"谁共享数据或通信频繁"，再决定映射。没有明确通信图时，绑核策略容易退化为静态拓扑启发式。

### 5.3 决策机制谱系

| 决策类型 | 代表 | 适用场景 | 风险 |
|----------|------|----------|------|
| 静态容量阈值 | Sorting、OLAP Local/Mixed | 输入规模和并行度已知 | 无法适应 phase 变化 |
| PMU 动态反馈 | CHARM、P-MOSS | 策略可在线调整，PMU 与瓶颈相关 | 采样/迁移/推理开销可能抵消收益 |
| 离线搜索 | Sandwich | 模型、平台、请求分布稳定 | tuning 成本高 |
| 硬件实时决策 | TiNA、MEMPLEX | packet 或 cache miss 路径 | 依赖硬件支持 |

## 六、当前课题结论
- CHARM、OLAP、Sorting 三篇的对照结论：chiplet 放置有效的前提是跨域访问或数据搬迁在关键路径上占比显著，且能被放置改变。Attention 不满足这一前提
- GPU Attention NUMA Effects 支持"共享工作集驱动映射"这一抽象，但不能证明 CPU attention 的静态 L3/CCD 分组有效
- Sandwich 和 ArcLight 指向全链路 CPU LLM serving 优化：prefill/decode 分相、model partition、core utilization、内存放置和通信实现联合设计
- HNSW 相关论文（Graph Reordering、HM-ANN、d-HNSW）提供了一套"先识别热结构→再按硬件层次放置→用普通布局优化做 baseline"的方法论，对 chiplet-aware HNSW 实验设计有直接参考价值
