# 当前研究主线

## 课题与平台
相比单片架构 CPU，Chiplet 架构把核心和 `L3` 物理分散到多个 `CCD/CCX`。当前课题是结合这一架构特征优化 CPU LLM 推理服务，并形成论文产出。实验平台为 `2 x AMD EPYC 9745 128-Core Processor`，`lscpu` 显示共有 `16` 个 `L3 instance`、总 `512 MiB L3`，可按每个物理 CPU `8` 个约 `32 MiB` 的本地 `L3 slice` 理解；使用框架是 `vllm`。

## 方法启发
`CHARM` 的直接启发是 Chiplet CPU 上存在“局部性”和“聚合缓存容量”的权衡，但其工作负载是图处理、统计分析和数据库，只能借作调度思路。`Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects` 将共享同一组 `K/V` 的 workgroup 集合定义为 `ACC`，虽然平台是 GPU，但可借鉴“按共享 `K/V` 工作集做拓扑放置”的方法线。

## 主线判断
### 科研判据与工程实现的区分
当前主线需要始终区分两个问题：
1. `chiplet-aware locality` 策略本身是否有科研价值。这里要回答的是：把共享同一 `K/V` 工作集的 attention task 收敛到更小的本地 `L3/CCD` 域后，是否能稳定改善 locality，并进一步改善 attention 或推理性能。
2. 当前 `acc-local-l3` 实现是否足够好。这里要回答的是：现有实现里是否混入了额外的调度、负载均衡、同步或执行效率损失，导致策略收益被抵消。

当前阶段的主要结论只能写在第一层：现有数据尚未证明这条 locality 策略在当前 `cpu attention` 上具有稳定性能收益。这个结论不等于“当前 `acc-local-l3` 实现已经最优”或“任何实现都不会从该策略获益”。

### PD阶段访存特征不同
`PD_Test` 已确认 `decode` 的 `L3` 压力高于 `prefill`：`prefill_B16_I1024_O1` 的 `L3 Miss %=49.43`、`Ave L3 Miss Latency=180.12 ns`，`decode_B16_I1_O1024` 为 `96.51` 和 `326.57 ns`。同一 `prefill` 阶段内部，不同长度的访存特征并不稳定：`prefill_B16_I128_O1` 为 `8.82/287.01 ns/same-node another CCX %=25.42`，`prefill_B16_I512_O1` 为 `14.55/177.99 ns/11.65`，`prefill_B16_I1024_O1` 为 `49.43/180.12 ns/2.91`。`L3 Miss %`、`Ave L3 Miss Latency` 和 miss 来源占比不会随长度单调变化，`L3 Miss %` 低也不代表 miss 代价低。

### 跨CCD访问代价于访问内存几乎相当
当前机器上，本地 `L3` 约 `26.2 ns`，本地内存约 `120.2 ns`，跨 `CCD` 远端 `cache/L3` 路径约 `110~150 ns`；`AMD EPYC Rome` 论文给出的同向数据为本地 `L3 19.5 ns`、本地内存 `110 ns`、同 `socket` 远端 `cache` 约 `102.5~152 ns`。在 AMD Chiplet 架构上，同一 `socket` 不是低延迟共享域，低延迟共享范围更接近本地 `L3/CCD`，跨 `CCD` 后访问代价已接近本地内存。

### CPU attention优化思路
源码层面，legacy `CPU attention` 的 `prefill` 确实存在“同一 `kv_head` 下多个线程重复读取重叠 `KV` 前缀”的局部性模式，这一结论适用于 `VEC / VEC16 / AMX`。`balanced` 与 `acc-local-l3` 共用同一套 legacy `workitem/tile/softmax/reduction`，`acc-local-l3` 只改变某个 `kv_head` 的任务可由哪些线程领取，不改 attention 数学 kernel，也不减少 legacy 任务总数。目前可直接写成两点：
1. `balanced` 下，同一 `kv_head` 的 legacy task 可以被多个 `CCD` 领取。直接后果是同一份只读 `KV` 更容易在多个 `CCD` 的本地 cache 中同时驻留，形成缓存副本和容量压力。由于 `KV cache` 在 attention kernel 中只读、不写，同一 `kv_head` 被多个 `CCD` 计算时，主效应是数据冗余，因此预期不会出现大量由一致性维护驱动的跨 `CCD` 往返访问，优化的重点不在减少跨CCD访问。
2. 优化的核心思路：`acc-local-l3` 的规则是先按 `(numa_node, socket_id, l3_cache_id)` 把线程划成 `subgroup`，再按 `kv_head_to_subgroup[kv_head_idx] = (kv_head_idx * group_span) % subgroup_num` 给每个 `kv_head` 指定允许领取任务的 `subgroup` 起点，只有覆盖到该 `kv_head` 的 `subgroup` 能领取它的 legacy slot 和 reduction item。在当前机器、`qhead=32 / kvhead=16 / TP=2 / group_span=1` 的配置下，每个 rank 的 `8` 个本地 `kv_head` 分别落到 `8` 个本地 `subgroup`，可按“1 个 `kv_head` 固定在 1 个 `CCD/L3 slice` 上执行”理解。这样同一 `kv_head` 的 `KV` 副本数更少，`balanced` 下“一个 `CCD` 同时承接多个 `kv_head`”带来的本地 `L3` 容量竞争也更轻；而一个 `workitem` 内可能包含多个 `q_tile`，后续 `q_tile` 继续扫描同一段 `KV` 时，更容易从本地 `L3` 复用。

### attention-only 当前数据
`P3_AttnOnly/qhead_32_kvhead_16/NPS1_TP2/prefill-like/global-fixed/batch_1` 的当前 PCM 与时延结果说明，`balanced` 在 `q1024/q2048/q4096` 下的 `Demand DC Fills From another CCX in same node` 仅为 `0.14/0.07/0.03 pti`，同时 `All Demand DC Fills` 为 `9.19/8.71/6.38 pti`，`Demand DC Fills From Local L2` 为 `8.73/8.41/6.16 pti`。远端补线存在，但主体 demand 访问仍以本地 `L2` 为主；同批 `L3 Miss Latency From another CCX in same node (%)` 偏高，只能说明少量 `L3 miss` 更偏向 remote CCX 来源，不能推出大多数 demand load 都在跨 `CCD`。

`benchmark_acc_local_l3_batch1_qhead32_kvhead16_span1_qlen256.log` 与 `benchmark_balanced_batch1_qhead32_kvhead16_qlen256.log` 显示，在 `qhead=32 / kvhead=16 / TP=2 / group_span=1 / qlen=256` 下，`acc-local-l3` 没有出现直接的并行度损失。两边 `local_num_kv_heads` 都是 `8`，trace 都是 `96` 条 attention task，每个 `kv_head` 都对应 `12` 个 workitem group；`acc-local-l3` 下每个 `kv_head` 虽只落在一个 subgroup，但每个 `kv_head` 仍动用了 `12` 个唯一线程，`balanced` 也是 `12` 个唯一线程，总计都只有 `96` 个唯一线程参与 attention trace，同批 benchmark 的 `slowest_rank_mean_ms` 为 `2.014 ms` 对 `2.266 ms`。在这一配置下，`group_span=1` 没有像早先 `local_num_kv_heads < subgroup_num` 的 case 那样直接减少 active subgroup 或 attention task 并行度。

`acc-local-l3` 将 `Demand DC Fills From another CCX in same node` 压到 `0.12/0.05/0.03 pti`，对应时延却是 `-3.01%/+30.17%/+16.41%`，且 `q2048/q4096` 的 `IPC (Sys + User)` 从 `2.67/1.94` 降到 `2.23/1.77`。`acc-local-l3` 试图压低的跨 `CCD` 补线份额本来就不大；长序列慢点仍与更低 `IPC` 同时出现，但现有 `qlen256` trace 不能把慢点直接归因为 `kvhead=16` 下并行度被压缩。当前仍待继续核查的方向是共享 `L3/refill` 资源争用、`kv_head` 间完成时间失衡，以及 `balanced` 全局抢任务相对 `acc-local-l3` 局部抢任务的补空能力差异。

## 证据与入口
源码主证据是 `csrc/cpu/cpu_attn_impl.hpp` 中 legacy `CPU attention` 的共享 `KV` 工作集与 workitem 切分逻辑，以及 `csrc/cpu/cpu_attn_acc_locality_impl.hpp` 中 `acc-local-l3` 的 subgroup / task 组织逻辑。实验主证据是 `test_results/PD_Test/Qwen3-30B-A3B/PCm_res/`、`test_results/P2_AttnOnly/Qwen3-30B-A3B/NPS1_TP2/summary.md`、`test_results/P3_AttnOnly/Qwen3-30B-A3B/NPS1_TP2/` 和 `test_results/P3_AttnOnly/Qwen3-30B-A3B/NPS1_TP2_group_span4/`。背景与方法入口优先看 [Chiplet背景知识](../术语与背景/Chiplet背景知识.md)、[AMDuProf背景速记](../术语与背景/AMDuProf背景速记.md)、[Chiplet 架构下 L3 指标关注重点与高 L3 Miss 归因边界](./Chiplet架构下L3指标关注重点与高L3Miss归因边界.md)、[相关工作论文筛选与研究方向建议](./相关工作论文筛选与研究方向建议.md)；实现入口优先看 [CPU attention 并行计算过程 线程任务 workitem 与 tile](../源码分析/CPU_attention并行计算过程_线程任务workitem与tile.md) 和 [CPU attention acc-local-l3 新 kernel 实现说明](../源码分析/CPU_attention_acc_locality新kernel实现说明.md)；实验与复现入口优先看 [Qwen3-30B-A3B attention-only TP 实验步骤](../实验方案/Qwen3-30B-A3B_attention-only_TP实验步骤.md) 和 [2026-04-05 Qwen3-30B-A3B P3_AttnOnly acc-local-l3 对照观察](../实验结果解读/2026-04-05_Qwen3-30B-A3B_P3_AttnOnly_acc-local-l3对照观察.md)。

## 适用边界
当前阶段性判断绑定于 `Qwen3-30B-A3B`、本机约 `32 MiB` 的本地 `L3 slice`、`NPS1_TP2`、以及 `attention-only` 与 `PD_Test` 两套口径。现有证据还不足以推广到更多 batch、更多 `NPS/TP` 或真实服务全链路吞吐，也不能写成 `decode` 的主要问题已定位到远端 `DRAM`、只要把任务收进同一 `CCX/L3` 就一定会提升全链路吞吐，或现有 `NPS1_TP2` 结果已足够外推到更多 `NPS/TP`。
