# 当前研究主线

## 课题
- 相比单片架构 CPU，Chiplet 架构把核心和 `L3` 物理分散到多个 `CCD/CCX`，当前目标是研究如何结合这种架构，优化 CPU LLM 推理服务，并最终产出学术论文。
- 当前机器是 `2 x AMD EPYC 9745 128-Core Processor`，`lscpu` 口径下共有 `16` 个 L3 instance，总 `512 MiB L3`，可按每个物理 CPU `8` 个约 `32 MiB` 的本地 L3 slice 理解。使用的框架是 vllm。

## 当前启发论文
- `CHARM`
  - 核心启发是 Chiplet CPU 上存在“局部性 vs 聚合缓存容量”的权衡。
  - 但其工作负载是图处理、统计分析和数据库，不是 LLM 推理，因此只能提供调度思路。
- `Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects`
  - 论文把共享同一组 `K/V` 的 workgroup 集合定义为 `ACC`。
  - 论文研究的是 GPU 平台，但可以借鉴“把共享 `K/V` 工作集作为拓扑放置单元”这条方法线。

## 当前观察
### Prefill / Decode 阶段整体特征
- `PD_Test` 已确认 `decode` 的 `L3` 压力显著高于 `prefill`。
  - `prefill_B16_I1024_O1`：`L3 Miss %=49.43`，`Ave L3 Miss Latency=180.12 ns`
  - `decode_B16_I1_O1024`：`L3 Miss %=96.51`，`Ave L3 Miss Latency=326.57 ns`
  - 这批数据支持写成“`decode` 比 `prefill` 更容易出现高 `L3 Miss` 和高 `Ave L3 Miss Latency`”，但不支持直接写成“主要由远端 DRAM 驱动”
- `prefill` 内部不同长度的访存特征并不稳定。
  - `prefill_B16_I128_O1`：`L3 Miss %=8.82`，`Ave L3 Miss Latency=287.01 ns`，`same-node another CCX %=25.42`
  - `prefill_B16_I512_O1`：`L3 Miss %=14.55`，`Ave L3 Miss Latency=177.99 ns`，`same-node another CCX %=11.65`
  - `prefill_B16_I1024_O1`：`L3 Miss %=49.43`，`Ave L3 Miss Latency=180.12 ns`，`same-node another CCX %=2.91`
  - 这说明 `L3 Miss %` 低，不代表 miss 代价低；长度变化时，miss 次数和 miss 来源占比可能朝相反方向动

### 跨 `CCD` 远端 `cache/L3` 路径代价
- 当前机器上，本地 `L3` 与跨 `CCD` 远端 `cache/L3` 路径的量级差异很大。
  - 本地 `L3`：约 `26.2 ns`
  - 本地内存：约 `120.2 ns`
  - 跨 `CCD` 远端 `cache/L3` 路径：约 `110~150 ns`
- 这说明跨 `CCD` 远端 `cache/L3` 路径显著高于本地 `L3`，且已接近本地内存，部分路径还可能高于本地内存。
- `AMD EPYC Rome` 论文也给出了同方向观察：
  - 本地 `L3`：`19.5 ns`
  - 本地内存：`110 ns`
  - 同 `socket` 远端 `cache` 访问：约 `102.5~152 ns`
- 当前更稳的主线判断是：在 AMD 的 chiplet 架构上，“同一 `socket`”不是低延迟共享域；真正低延迟的共享范围接近本地 `L3/CCD`，一旦跨 `CCD`，访问代价就会跃升到接近本地内存的量级。

### CPU attention 算子粒度观察
- legacy `CPU attention` 公共路径中，`prefill` 确实存在“同一 `kv_head` 下多个线程重复读取重叠 KV 前缀”的局部性模式，值得继续探索按共享 `K/V` 工作集做局部域放置。
  - 这条源码结论适用于 `VEC / VEC16 / AMX`
  - 但当前不能据此推出三者运行时 `L3` 表现相同，实际严重程度仍需分别看实验
- `P2_AttnOnly/NPS1_TP2` 已给出第一轮 locality 候选证据。
  - 在 `prefill-like/global-fixed/batch_16` 下，`q=128/256/512` 时 `same-node another CCX %=99.13/94.00/61.15`
  - 但同一批结果里，`q=1024/2048` 时 `local memory / I/O %=68.80/77.32`
  - 因此当前更稳的表述是：“按共享 `K/V` 工作集做拓扑感知放置”是值得继续验证的 `prefill` 候选方向；当前 `acc-local-l3` 也是按启发论文 `Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects` 的这条方法线来实现的，但现有数据还不足以证明它已经稳定有效，也不足以证明它能跨 `NPS/TP` 泛化
- 当前证据只支持把 `acc-local-l3` 当成 `prefill` 的候选优化方向，还不足以写成已被证明可稳定泛化到更多 `NPS/TP` 配置。
  - 截至 `2026-04-09`，`P3/NPS1_TP2/prefill-like/global-fixed/batch=16` 的补充 debug 已确认：
    - `group_span=1` 时，当前 slowdown 的直接原因是 `acc-local-l3` 把每个 rank 的 `attention_task_num` 从 `124/128` 压到 `32`；在本地只有 `2` 个 `kv_head`、但 `subgroup_num=8` 时，只有 `2` 个 subgroup 真正参与 attention 主循环
    - `group_span=4` 时，`attention_task_num` 已恢复到接近 legacy 的 `127/128`，但同一个 `kv_head` 覆盖到的多个 subgroup 会重复执行同一批 legacy slot，因此 dry run latency 反而更差

## 边界
- 当前阶段性判断主要绑定：
  - `Qwen3-30B-A3B`
  - 本机 `32 MiB` 本地 L3 slice
  - `NPS1_TP2`
  - `attention-only` 与 `PD_Test` 两套口径
- 还没有足够证据把结论推广到更多 batch、更多 `NPS/TP`、或真实服务全链路吞吐。
- 当前不能直接写成：
  - `decode` 的主要问题已经被定位到远端 DRAM
  - 只要把任务收进同一 `CCX/L3` 就一定会提升全链路吞吐
  - 现有 `NPS1_TP2` 结果已足够外推到更多 `NPS/TP`
