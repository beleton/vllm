## 2. 论文筛选结果

### 2.1 第一层：建议作为主线深读的 `7` 篇

1. `ArcLight: A Lightweight LLM Inference Architecture for Many-Core CPUs`
   - 保留原因：这是正式清单里最直接命中“CPU LLM inference + many-core/NUMA + 线程/内存管理”的论文型资料之一。
   - 对当前课题的价值：可直接对照当前 `TP`、线程绑核、NUMA 内存策略主线。
   - 证据：`相关工作检索清单.md` 中 `ArcLight: A Lightweight LLM Inference Architecture for Many-Core CPUs` 条目。
2. `Sandwich: Separating Prefill-Decode Compilation for Efficient CPU LLM Serving`
   - 保留原因：直接指出 `prefill/decode` 不能共用同一套静态 `per-NUMA` 策略。
   - 对当前课题的价值：和本地 `Prefill/Decode` 分相实验最对口，适合指导“phase-aware”策略而不是统一策略。
   - 证据：`相关工作检索清单.md` 中 `Sandwich: Separating Prefill-Decode Compilation for Efficient CPU LLM Serving` 条目。
3. `Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects`
   - 保留原因：这是当前资料里最直接把“共享同一组 `K/V` 的工作集”映射到“拓扑感知放置”的论文。
   - 对当前课题的价值：虽然平台是 MI300X GPU，但 `ACC` 定义和“同一共享 `K/V` 工作集尽量收敛到一个局部域”的思路，能直接映射到当前 CPU `prefill` 的 `kv_head`/共享前缀局部性分析。
   - 证据：`info/进展.md`“启发论文”第 `2` 条，`wiki/原始资料/papers/GPU_Attention_NUMA_Optimization解读.md` 第 `2-4` 节。
4. `Hydragen: High-Throughput LLM Inference with Shared Prefixes`
   - 保留原因：它把“共享 prefix = 共享 KV 工作集”落实成了系统机制，而不只停留在模型结构。
   - 对当前课题的价值：适合支撑“共享 KV 前缀可以当作 locality 单元”的论证。
   - 证据：`相关工作检索清单.md` 中 `Hydragen: High-Throughput LLM Inference with Shared Prefixes` 条目。
5. `ChunkAttention: Efficient Self-Attention with Prefix-Aware KV Cache and Two-Phase Partition`
   - 保留原因：它把“prefix-aware KV cache + two-phase partition + locality-aware attention”这条链路写得最完整。
   - 对当前课题的价值：很适合拿来对照当前 `block_table/key_cache/value_cache` 路径是否也能做更强的局部性组织。
   - 证据：`相关工作检索清单.md` 中 `ChunkAttention: Efficient Self-Attention with Prefix-Aware KV Cache and Two-Phase Partition` 条目。
6. `CHARM: Chiplet Heterogeneity-Aware Runtime Mapping System`
   - 保留原因：它把 `LocalCache` 与 `DistributedCache` 的切换写得最完整。
   - 对当前课题的价值：适合直接启发后续 `group_span` 或 `L3 subgroup` 扩张策略。
   - 证据：`相关工作检索清单.md` 中 `CHARM: Chiplet Heterogeneity-Aware Runtime Mapping System` 条目。
7. `Optimizing Sorting for Chiplet-Based CPUs`
   - 保留原因：它把“数据规模相对单个本地 L3 / 多 chiplet 聚合 L3 的关系”说得很清楚。
   - 对当前课题的价值：很适合映射当前 `prefill` 不同长度点为何可能对应不同最优放置策略。
   - 证据：`相关工作检索清单.md` 中 `Optimizing Sorting for Chiplet-Based CPUs` 条目；`wiki/原始资料/papers/Optimizing Sorting for Chiplet-Based CPUs.pdf`。

### 2.2 第二层：建议保留为方法支撑的 `7` 篇

1. `GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints`
   - 价值：给“多个 query heads 共享同一组 `KV heads`”提供结构定义，是把 `kv_head` 当作工作集单元的基础。
   - 限制：它不是运行时调度论文，不能直接推出放置策略。
2. `NoMAD-Attention: Efficient LLM Inference on CPUs Through Multiply-add-free Attention`
   - 价值：提供 CPU attention 的另一条优化路线，适合作为“算子公式/数据放置”两条路线的对照。
   - 限制：它不讨论 chiplet/NUMA/L3 局部性。
3. `HeadInfer: Memory-Efficient LLM Inference by Head-wise Offloading`
   - 价值：证明“按 head 粒度管理 KV”可以落成系统设计。
   - 限制：主问题是 GPU 显存与 CPU RAM 协同，不是本地 `L3/CCX`。
4. `KVShare: Semantic-Aware Key-Value Cache Sharing for Efficient Large Language Model Inference`
   - 价值：补足“共享工作集不一定要求严格同前缀”的视角。
   - 限制：更偏服务侧复用策略，不直接回答线程放置问题。
5. `Realizing the AMD Exascale Heterogeneous Processor Vision`
   - 价值：作为 `MI300X` / `XCD` / `NPS` 的硬件背景材料，有助于正确理解 GPU NUMA attention 论文。
   - 限制：它提供的是硬件背景，不是可直接迁移的调度算法。
6. `LFOC+: A Fair OS-level Cache-Clustering Policy for Commodity Multicore Systems`
   - 价值：说明 OS 层基于 cache 行为做运行时聚类是可行的。
   - 限制：与当前 vLLM CPU attention 的映射关系比较间接。
7. `Adaptive NUMA-aware data placement and task scheduling for analytical workloads in main-memory column-stores`
   - 价值：是 topology-aware data placement + task scheduling 的经典基线。
   - 限制：工作负载是分析型数据库，不是 LLM attention。

## 3. 论文与当前研究进展的对齐结论

### 3.1 当前最强的一条论文链

当前最值得继续沿着做的，不是“泛 NUMA 优化”，而是下面这条更具体的链：

`GQA`/`Hydragen`/`ChunkAttention`
-> 定义共享 `KV` 或共享 prefix 的工作集
-> `Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects`
-> 把共享工作集映射到同一局部拓扑域
-> 在 CPU 侧尝试做 `kv_head`/共享前缀感知的 L3 子池调度

这条链和本地证据是能对上的：

- `info/进展.md` 已明确写出：当前 CPU prefill 中，同一 `kv_head` 会展开成多个线程桶，且不同线程可能读取高度重叠的 `KV` 前缀；这条证据来自 `csrc/cpu/cpu_attn_impl.hpp:436-589`、`:1424-1459`、`:1527-1538`、`:1631-1727`。
- `test_results/P2_AttnOnly/Qwen3-30B-A3B/NPS1_TP2/summary.md` 显示，在 `prefill-like/global-fixed/batch_16` 下，`q=128/256/512` 时 `same-node another CCX % = 99.13/94.00/61.15`，说明短到中等长度 `prefill` 确实存在显著的跨 `CCX` 路径占比。

所以，“共享 `KV` 工作集 -> 局部域放置”不是空想，而是已经有论文机制和本地源码/实验现象双重支撑。

### 3.2 当前第二强的一条论文链

`Sandwich`
-> `prefill` 与 `decode` 不能默认共用同一套静态 `NUMA` 策略
-> `CHARM`/`Optimizing Sorting`
-> 最优策略取决于工作集大小，以及“本地 cache 延迟”与“聚合 cache 容量”的平衡

这条链和本地证据也能对上：

- `test_results/PD_Test/Qwen3-30B-A3B/PCm_res/2026-03-26_qwen3-30b-a3b_pd_pcm_summary.md` 显示：`decode_B16_I1_O1024` 相比 `prefill_B16_I1024_O1`，`L3 Miss %` 从 `49.43` 升到 `96.51`，`Ave L3 Miss Latency` 从 `180.12 ns` 升到 `326.57 ns`，但两者 `Remote DRAM Reads %` 都是 `0.03`。
- 同一文档还显示：`prefill` 内部 `I128/I512/I1024` 的来源分布变化很大，不像 `decode` 那样近乎平稳。
- `test_results/P2_AttnOnly/Qwen3-30B-A3B/NPS1_TP2/summary.md` 进一步显示：`prefill-like` 从 `q=512 -> 1024 -> 2048` 时，`same-node another CCX %` 从 `61.15 -> 30.70 -> 21.95` 下滑，而 `local memory / I/O %` 从 `38.53 -> 68.80 -> 77.32` 上升。

因此，当前更合理的判断是：

- `decode` 的高 `L3 miss` 现象是真实的，但现有 whole-run cumulative 结果还不支持把它写成“主要由跨 `CCX` 路径造成”。
- `prefill` 更像是随长度变化发生来源切换，因此比 `decode` 更适合先尝试“拓扑感知局部化”。

这部分是基于本地数据的判断，不是某篇论文原文直接结论。

### 3.3 当前最缺的论文空白

正式清单自己的总结已经指出，当前最缺的还是两类资料：

1. 直接把 `AMD EPYC / vLLM CPU backend` 与 `chiplet / CCD / CCX / L3 slice` 放置策略绑定起来的论文。
2. 直接把 `shared KV prefix` 或 `kv_head` 工作集映射到 `Ave L3 Miss Latency`、`same-node another CCX %`、`Remote DRAM Reads %` 这类 CPU 计数器的论文。

这意味着：后续研究不应声称“文献已经证明当前策略在 AMD EPYC + vLLM 上有效”；更稳的表述只能是“文献提供方法论，本地源码和实验提供了初步可验证靶点”。

## 4. 新的、可行度高的研究方向

### 4.1 方向一：短中长度 `prefill` 的 `ACC-local-L3` 子池调度

- 核心想法：
  - 把共享同一 `kv_head` 或共享前缀 `KV` 的 attention 工作尽量限制在同一个 `L3/CCX` 子池内执行。
- 文献支持：
  - `Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects`
  - `GQA`
  - `Hydragen`
  - `ChunkAttention`
- 本地证据：
  - `info/进展.md` 已确认当前 `prefill` 中存在“同一 `kv_head` 下多个线程重复读取重叠 `KV` 前缀”的模式。
  - `P2` 首轮结果显示 `q=128/256/512` 的 `prefill-like` 有很高的 `same-node another CCX %`。
  - `process.txt` 在 `2026-04-03 16:51:21 +0800` 已记录：`cpu_attn_acc_locality` 新路径已经形成可运行闭环，`benchmark_cpu_attn_mp.py` 也能跑 `--attn-locality-mode acc-local-l3`。
- 为什么现在可做：
  - 这不是从零开始的新方向，仓库里已经有并行新 kernel 路径、metadata header、smoke benchmark 和可观测入口。
  - 证据路径：`csrc/cpu/cpu_attn_acc_locality_impl.hpp`、`csrc/cpu/cpu_attn_acc_locality.cpp`、`vllm/v1/attention/backends/cpu_attn.py`、`benchmarks/kernels/cpu/benchmark_cpu_attn_mp.py`、`process.txt` 的 `2026-04-03 16:51:21 +0800` 记录。
- 当前判断：
  - 这是我认为可行度最高、且最贴近当前课题主线的方向。
- 首轮验证建议：
  1. 先完成 `tasks.json` 中的任务 `54`，在 `attention-only` 上做 `balanced` vs `acc-local-l3` 对照。
  2. 首轮只看 `prefill-like` 的 `q=128/256/512/768/1024`，不急着覆盖全长区间。
  3. 重点看 `same-node another CCX %`、`Ave L3 Miss Latency`、slowest-rank latency 是否同步下降。
- 推断边界：
  - “局部化一定提升吞吐”目前只是推断，不是现有数据已证明的结论。

### 4.2 方向二：`prefill/decode` 相位感知、长度感知的 locality policy

- 核心想法：
  - 不再追求“一个策略覆盖所有 phase/长度”，而是按 `prefill/decode` 和 `q_len/kv_len` 选择不同 locality mode。
- 文献支持：
  - `Sandwich`
  - `CHARM`
  - `Optimizing Sorting for Chiplet-Based CPUs`
- 本地证据：
  - `decode_B16_I1_O1024` 虽然 `L3 Miss %` 很高，但 `Remote DRAM Reads %` 仍是 `0.03`，当前并不支持把 decode 的高 miss 直接解释成“跨 `CCX` 问题”。
  - `prefill-like` 长度拉长后，来源正从 `another CCX` 向 `local memory / I/O` 切换。
- 为什么现在可做：
  - 这条方向更多是“策略选择器/heuristic”，不需要先改 KV cache 管理器。
  - 当前 benchmark 和结果文档已经能支撑按长度点补图和补表。
- 一个可执行的首版口径：
  - `prefill` 短中长度先比较 `balanced` vs `acc-local-l3`
  - 长 `prefill` 暂保守，不默认启用单 L3 收敛
  - `decode` 先以“继续归因为主”，不把 `CCX` 局部化当作第一优先级优化
- 推断边界：
  - 这里的阈值切分是推断，不是论文直接给出的 CPU 阈值。

### 4.3 方向三：把 `group_span` 做成“本地 L3 vs 聚合 L3”自适应开关

- 核心想法：
  - 不是只做 `group_span=1` 的单 `L3/CCX` 收敛，还要尝试在工作集变大时扩成 `group_span=2/4`，把多个局部组拼成更大的聚合 cache 域。
- 文献支持：
  - `CHARM`
  - `Optimizing Sorting for Chiplet-Based CPUs`
- 本地证据：
  - 本机每 `16` 个物理核心共享约 `32 MiB` 本地 `L3`，这是当前 `group_span` 是否需要扩大的硬件边界。
  - `process.txt` 在 `2026-04-03 16:51:21 +0800` 已明确写出：下一步需要先判断当前 subgroup 映射是否值得继续扩展到 `group_span > 1`。
  - `benchmark_cpu_attn_mp.py` 与 `benchmark_cpu_attn.py` 已经暴露 `attn_locality_group_span` 接口。
- 为什么现在可做：
  - 实现层已经留了接口，后续主要是实验筛选和小规模 heuristic 扩展。
- 但优先级不应太高：
  - 只有当方向一先证明 `group_span=1` 的 `acc-local-l3` 至少在一段 `prefill` 区间内有效，扩 `group_span` 才有意义。

### 4.4 方向四：`NPS/TP` 与 rank 内 locality mode 的协同设计

- 核心想法：
  - 把“rank 级分散到多少 chiplet”与“rank 内是否局部化到单个 `L3/CCX` 子池”分开控制，再看两层策略是否互补。
- 文献支持：
  - `ArcLight`
  - `CHARM`
- 本地证据：
  - `info/进展.md` 已明确把下一步优先级写成：先补 `NPS2_TP4 / NPS4_TP8`，再补 `per-rank-fixed`，避免把“工作量变小”和“局部性变化”混在一起。
  - 当前仓库已经有 attention-only 多进程基准和 `global-fixed/per-rank-fixed` 口径。
- 为什么现在可做：
  - 这条方向几乎不要求新增服务逻辑，更多是实验矩阵设计问题。
  - 若想回答“局部 L3 收敛”和“分散到更多 chiplet 用聚合容量”是否正交，这条方向最直接。
- 适合的首轮问题：
  - `NPS2_TP4 + balanced` 是否已经足够好。
  - `NPS2_TP4 + acc-local-l3` 是否优于单独做其中一项。
  - `per-rank-fixed` 是否只是减少了每 rank 工作量，而不是改善了 locality。

## 5. 暂不建议优先投入的方向

1. 语义级 `KV` 共享
   - 如 `KVShare` 这类方向更偏服务侧复用策略，当前本地证据还没有指向它是 `L3/CCX` 问题的主矛盾。
2. `KV` 在 CPU/GPU 之间按 head/offload
   - 如 `HeadInfer`，这更适合异构内存/显存受限场景，不是当前 CPU-only chiplet 主线。
3. 近似 attention / `LSH` 路线
   - 如 `MagicPIG`，问题设定已经变了，不适合用来回答当前“精确 attention 的拓扑局部性”问题。

## 6. 建议执行顺序

1. 先把论文深读焦点收敛到 `Sandwich`、`GPU NUMA Attention`、`Hydragen`、`ChunkAttention`、`CHARM`、`Optimizing Sorting`。
2. 优先完成任务 `54`，验证 `acc-local-l3` 在 `attention-only` 上是否真的打中短中长度 `prefill`。
3. 若任务 `54` 有正信号，再做“phase-aware/length-aware policy”。
4. 只有当 `group_span=1` 已经证明有价值，再扩 `group_span > 1`。
5. 最后再做 `NPS/TP × locality mode` 协同矩阵，避免同时动太多变量。

## 7. 一句话结论

从当前相关工作和本地进展一起看，最值得押注的不是“泛 NUMA 优化”，而是：

`shared-KV workset` 驱动的 `prefill` 局部化
`+`
`phase/length-aware` 的策略切换
`+`
在必要时从单 `L3` 扩到聚合 `L3` 的自适应分组

这三者都能在现有源码和实验入口上继续推进，不需要先做大规模架构重写。
